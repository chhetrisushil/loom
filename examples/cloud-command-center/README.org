#+title: Cloud Command Center — Example App
#+author: Sushil Chhetri

A reference application for the Loom framework. It demonstrates a complete durable AI workflow: incident detection → metrics and log collection → human approval gate → automated remediation. The full lifecycle runs in the browser using in-memory stores — a demo choice; the store interfaces are async-first, so the same runtime backs onto ~SqliteEventStore~ or a BYO Postgres/Redis backend unchanged (see ~db-command-center-server~).

* What This App Demonstrates

* Using the App

The app simulates a cloud incident response workflow:

1. *Click "Simulate Incident"* — starts the ~InvestigateIncident~ flow for incident ~cpu-001~.
   - The workflow fetches metrics and logs (via mock handlers).
   - Projection state updates in real time: CPU gauge, memory gauge, connection count, event timeline.
   - After analysis, the workflow suspends and waits for human approval.
   - The badge changes from *running* to *suspended*.

2. *Click "Approve Remediation"* (or the approval card in the blueprint) — resumes the workflow.
   - The workflow applies the remediation step.
   - The timeline updates with the resolution summary.
   - The badge changes to *completed*.

3. *Click "Reset"* — clears the current execution to start a new one.

* How handler$ Works Here

Each tool file co-locates the step definition with its mock implementation:

#+begin_src typescript
export const FetchMetricsStep = step$({
  id: "fetch-metrics",
  toolId: "metrics-tool",
  inputSchema: ...,
  outputSchema: ...,
  handler: handler$(async (_input, _ctx) => ({
    cpu: { current: 87, threshold: 80 },
    memory: { usedMb: 14_000, totalMb: 16_000 },
    connections: { active: 450, max: 500 },
  })),
});
#+end_src

In ~main.tsx~, a single ~registerFlow()~ call is sufficient — no separate ~effectRuntime.register()~ calls are needed:

#+begin_src typescript
// registerFlow auto-registers LazyEffect for every step with handler$
workflowRuntime.registerFlow(
  InvestigateIncidentFlow.definition,
  InvestigateIncidentFlow.runner
);
#+end_src

At build time, ~@loom/compiler~ (wired in ~vite.config.ts~) extracts each ~handler$(fn)~ into a separate lazy chunk. Unused steps never load their implementation.

* Configuration

The Vite config (~vite.config.ts~) applies two settings required for workspace package interop:

#+begin_src typescript
import { loomPlugin } from "@loom/compiler";
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [loomPlugin(), react()],
  resolve: { conditions: ["require", "default"] },
  optimizeDeps: {
    include: [
      "@loom/blueprint-runtime",
      "@loom/core",
      // ... all @loom/* runtime packages
    ],
  },
});
#+end_src

- ~loomPlugin()~ runs first (enforce: "pre") to transform ~handler$()~ calls before React processes JSX.
- ~resolve.conditions~ enables pnpm workspace package resolution (packages publish CJS only).
- ~optimizeDeps.include~ forces Vite to pre-bundle the CJS workspace packages into ESM, fixing the "does not provide an export named" browser error.
