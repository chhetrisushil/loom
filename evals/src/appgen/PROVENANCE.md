# Provenance: appgen plan dataset (slice S3)

- **Files:** `cases.ts` (10 intents, each with the fixture it runs against, the shape it must leave behind, and a
  hand-written model script), `cassettes/*.json` (one cassette per intent), `subject.ts` (the case runner and the
  fixture builder), `typecheck.ts` (the tight `tsc --noEmit` host), `measure.ts`, `author.ts`, `containment.test.ts`.
- **Labeller:** Claude (Sonnet subagent), reviewed by Claude (Sonnet), as the implementing agent of ADR 0131 slice S3, for the repo owner.
- **Date:** 2026-10-17.
- **Source:** original synthetic text. The intents mix the `@loom/appgen` directive grammar ("Create a refund-reviewer.
  Step check policy. Pause for approval.") with free-form requests, over a net-new app and a three-flow "support-desk"
  fixture that is generated by `generateFlows` at run time (no committed fixture files). No real user data, no
  third-party text.

## THE CASSETTES ARE HAND-AUTHORED. NO MODEL WAS CALLED.

Every model response in `cassettes/` was written by hand as a `script` in `cases.ts` (what a sensible planner would
answer for that intent). `pnpm eval:author` then runs the REAL `planChangesModel` (its reasoning ladder, semantic
validation and self-repair loop) over that script through a `CassetteProvider` in record mode and stores each
request/response pair. No provider, no network and no API key was involved, and the user has not approved live
recording. A local Gemma tier (the plan's original recording tier for `@loom/appgen-model`) was NOT run; the cassettes
replace it. A test regenerates every cassette from its script and requires the committed file to match byte for byte.

**What this measures:** given a model that answers like this, does `planChangesModel` accept it (or reject it and
repair it), does `applyChanges` turn the ChangeSpec into a FilePlan that applies inside the fixture, do the generated or
edited flow files typecheck, and does the resulting app have the flows, steps and gates the intent asked for. The
deterministic planner (`planChangesDeterministic`) runs over the same intents as a reference arm that needs no model.

**What it does NOT measure:** a model's quality. The script always does the sensible thing, so the model arm's scores
are close to 1.0 by construction; the gates are tripwires for the PLANNING, VALIDATION and APPLY code regressing. The
planner prompt (`buildSystem`) is pinned at its default: a cassette is keyed by the exact request, so a legitimate
prompt change MISSES (the signal); regenerate with `pnpm eval:author` and review the diff.

## Metrics

- **validity** - a plan is valid when ALL of: the model's own answer was accepted (`ChangeSpec.planner === "model"`;
  `planChangesModel` silently returns the deterministic plan when the model's is unusable, which would otherwise score as
  the model's), `applyChanges` produced a FilePlan whose paths all stay inside the fixture directory, and every
  `app/flows/*/flow.ts` typechecks (`typecheck.ts`: strict, one shared compiler host, `@loom/core` and `zod` declarations
  from the workspace's built `dist`, no repo build). An invalid plan carries its underlying reason (the validator's issue
  list, or the `TS` code and message).
- **coverage** - mean over cases of the recall of the expected items (flow, step, approval gate, UI surface present;
  deleted flow absent) read back with `scanApp` from the APPLIED app, not from the ChangeSpec.

## Label rules

1. Each case's `expected` is written from the INTENT (what the user asked for), as a delta on the fixture, before any
   planner ran over it. Items use `flow:<id>`, `step:<flow>/<step>`, `approval:<flow>`, `ui:<flow>`; `absent` lists
   items that must be gone.
2. Pre-existing fixture content is never listed (it is trivially present); only what the intent adds or removes.
3. Step and flow ids in `expected` are the kebab-case slug a sensible planner would pick; where the intent is the
   directive grammar the ids are exactly what the grammar derives.

## Measured gap, recorded not hidden

`edit-remove-digest`: "Remove the digest flow." The model arm cannot plan a delete: `@loom/appgen-model`'s prompt and
JSON schema offer `create | extend | modify` only (and `tryParseChangeSpec` coerces anything else to `create`), so a
planner that follows the prompt answers with a no-op `extend`. The deterministic arm does handle it (`remove <flow>`).
The case is kept with the label the USER intent implies (the flow must be gone); the model arm's coverage is 0.9 because
of it. If the prompt learns to delete, raise the floor in `thresholds.ts`.

Also found while writing the fail-proofs: `validateChangeSpec` does not reject a capability with DUPLICATE step ids, so
such a plan is accepted and generates `const <id>Step` twice; only the typecheck catches it (fail-proof `(a3)`).

## Security finding: symlinked flow file escape

`applyChanges` itself writes nothing, but a `flow.ts` that is a SYMLINK to a file outside the project is scanned, planned
as an in-place edit, and a write to that path (the CLI's lexical `resolveInside` check cannot see it) overwrites the
outside file. Pinned exactly in `containment.test.ts` (it asserts the escape happens today).

Scope of the pin: it covers the APPGEN-LEVEL path only (`scanApp` -> `applyChanges` -> a harness write standing in for
the CLI writer); `@loom/evals-internal` does not depend on `@loom/cli`. A fix in `@loom/appgen` (the scanner no longer
offers a symlinked flow as editable) turns it red, which is the prompt to flip it to `expect(outsideChanged).toBe(false)`.
The CLI WRITE path (`tools/cli/src/appgen.ts` `resolveInside` + the writer) is covered by `tools/cli`'s own regression
tests in the fix (branch `fix/appgen-symlink-escape`), not by this pin; a CLI-only fix would leave this pin green.
