#+title: Loom
#+author: Sushil Chhetri

*The execution kernel for intelligent software — durable, event-sourced, deterministic.*

Loom treats an intelligent workflow as a *process that unfolds over time*, not a request that returns once. Every decision it makes is appended to an immutable event log — so any execution can *pause for a human, resume on another machine, replay bit-for-bit for debugging, fork to explore alternatives,* and be *evaluated against its own history*. You write the intelligence in plain TypeScript; Loom provides the durable spine that makes it trustworthy in production.

#+begin_quote
*The durable event log is the moat.* Durability, resumability, deterministic replay, branching, evals, and time-travel debugging are all just different lenses on one append-only log.
#+end_quote

#+begin_quote
🧵 *Loom 2.0* evolves the runtime into the *execution kernel for intelligent software* — a stable syscall ABI, an enforced authority boundary, metered resources, model routing/elevation, tiered memory, and horizontal scale-out — all additive and opt-in. See [[file:docs/loom-2.0/00-overview.md][docs/loom-2.0/]] and [[file:docs/adr/0016-loom-2.0-execution-runtime-and-decision-seam.md][ADR 0016]].
#+end_quote

- ⏸️  *Durable suspend / resume* — a flow can wait days for a human, survive a restart, and continue from exactly where it left off. Completed steps are never re-run.
- 🔁  *Deterministic replay* — state is a pure fold of the event log; the same events always reconstruct the same state. *Non-determinism is allowed only when logged* (P9) — so routing/optimizing still replays bit-for-bit.
- 🌱  *Git-style branching* — fork an in-flight execution, simulate alternatives concurrently, and promote a winner. Branch-only, no merge.
- 🤖  *Agentic, end to end* — LLMs, ReAct agents, MCP tools, and agent-to-agent calls are all durable, replayable *effects*. *Reasoning* adds cheap-first model routing with confidence-based elevation; *tiered memory* adds working/semantic/procedural recall.
- 🛡️  *A real kernel* — a versioned syscall ABI, a capability *protection ring* (ungranted effects are denied), *resource accounting + quotas* (tokens/$/latency), and *fault supervision* (circuit breakers).
- 📈  *Scale out* — the same interfaces on single-node SQLite or a network Postgres store with cross-node live subscribe (~LISTEN/NOTIFY~).
- 🎨  *Bring your own renderer* — the same backend renders in React, Angular, Web Components, or the terminal.
- 🧩  *One composition root* — ~defineConfig~ wires an app from a static config; the ~loom~ CLI, testing kit, evals, deploy-simulation, and a pluggable-compute seam surround it.

* Quick start

#+begin_src sh
npm create loom-app@latest my-app && cd my-app && pnpm install
#+end_src

Define a flow — schema-checked steps plus an ordinary ~async~ runner:

#+begin_src ts
import { z } from "zod";
import { step$, handler$, flow$ } from "@loom/core";
import type { FlowRunner, RegisteredFlow } from "@loom/workflow-runtime";

const greet = step$({
  id: "greet",
  inputSchema: z.object({ name: z.string() }),
  outputSchema: z.object({ message: z.string() }),
  handler: handler$(async (input) => ({ message: `Hello, ${input.name}!` })),
});

const runner: FlowRunner<{ name: string }, { message: string }> = (ctx, input) =>
  ctx.run(greet, input);

export const helloFlow = {
  definition: flow$({
    id: "hello", name: "Hello", version: "1.0.0",
    inputSchema: z.object({ name: z.string() }),
    outputSchema: z.object({ message: z.string() }),
    steps: [greet],
  }),
  runner,
} as RegisteredFlow;
#+end_src

Wire it with ~defineConfig~ and run it:

#+begin_src ts
import { defineConfig } from "@loom/app";
import { helloFlow } from "./hello";

const app = defineConfig({ storage: { kind: "memory" }, flows: [helloFlow] });
const state = await (await app.runtime.start(helloFlow, { name: "Ada" })).waitForCompletion();
console.log(state.variables._output); // { message: "Hello, Ada!" }
await app.close();
#+end_src

*The three moves to remember:*
1. ~ctx.run(step, input)~ — do a unit of work (recorded, replay-safe, exactly-once). In 2.0 this is a thin alias for ~ctx.execute(task)~, the generalized primitive.
2. ~ctx.suspend({ on })~ — pause durably for a human or an external signal.
3. ~runtime.fork(id, sequence)~ — branch from any point to explore alternatives.

*One more, for intelligence:* ~ctx.decide(id, optimizer)~ — record an advisory/optimizer choice (a model route, a recall, a ranking) as a durable fact. On replay the recorded choice is served and the optimizer is never re-run — so outcomes improve run-to-run while any single run stays reproducible (P9).

*Pause for a human, then resume* — even across a process restart:

#+begin_src ts
const decision = (await ctx.suspend({ on: "ApprovalGranted", correlationKey: input.target }))
  as { approved: boolean };
// …later, possibly in a new process:
await app.runtime.resume(executionId, { eventType: "ApprovalGranted", payload: { approved: true } });
#+end_src

* Core ideas

- *Event sourcing* — execution state is never stored directly; it's derived by folding an append-only log of ~EventEnvelope~ s. State ~= fold(events)~.
- *Deterministic replay* — the fold is a pure function, and side effects are quarantined behind the ~EffectRuntime~, so a resume, a fork, and a debug-replay all reconstruct identical state.
- *Suspension is first-class* — pausing for a human is a normal outcome, not an error. ~ctx.suspend()~ writes a durable checkpoint; ~resume()~ continues from it.
- *Plain code, not a DSL* — a flow's orchestration is an ordinary ~async~ function using ~ctx.run~ / ~ctx.suspend~ / ~ctx.parallel~. Loom adds durability around your code; it doesn't replace it.
- *Static, replay-safe wiring* — flows and effects are registered statically (the folder convention is honored by build-time codegen, not runtime globbing), so a remote worker or a replay reconstructs an identical graph.
- *Isomorphic core, pluggable edges* — storage, compute placement, LLM providers, and renderers are all interfaces. The same flow runs in a test, a browser tab, a Node server, or on Cloud Run.
- *Non-determinism only when logged* (P9, 2.0) — a runtime may route models, elevate, learn, or optimize, but every such choice becomes a durable ~DECISION_RECORDED~ event. Replay stays a pure fold; outcomes improve run-to-run.
- *Minimal kernel, advisory plane* (P10, 2.0) — the durable core stays small; all "intelligence" is an optional module that shapes latency (off-log) or outcomes (logged), never a hidden input to the fold. You never pay for a runtime you didn't opt into.

** How it works

Every execution is an ordered list of events; the current state is a pure fold of them. Side effects run once and are memoized; a resume replays the log (serving completed steps from it) until it reaches the suspend point, then continues.

#+begin_example
  defineConfig(config)                     ← one static composition root
       │  { runtime, effectRuntime, projectionRuntime, bus, stores, close }
       ▼
  runtime.start(flow, input)
       │  ctx.run(step)  →  EffectRuntime (tool / llm / human / a2a)  +  middleware
       ▼
  ExecutionJournal ──► ReplayVM (fold, in-memory)      state = fold(events)
       │  (sole sequencer + writer)
       └──────────────► EventStore  (memory · SQLite · your own backend)
                              │
                        ProjectionRuntime ──► React / Angular / Web Components / terminal
                              │
                    loom logs · debug · inspect · eval · deploy check
#+end_example

*Bring your own everything.* Storage (~storage: { kind: "custom", eventStore, snapshotStore }~ — Postgres/Redis/DynamoDB), renderer (React/Angular/WC/terminal/DOM), and components (custom widgets in the renderer registry) are all swappable — the durable log never depends on them.

* Loom 2.0 — the execution kernel

Loom 2.0 generalizes the durable workflow runtime into an *execution kernel for intelligent software*: the layer that is to AI applications what an OS kernel is to programs. It is delivered as *additive, opt-in* modules over the same deterministic core — existing apps compile and replay unchanged.

*Two new seams* everything hangs off:

- *Execution seam* — ~ctx.run(step)~ generalizes to ~ctx.execute(task)~ (a step is one *task kind*; others: ~llm~ / ~agent~ / ~tool~ / ~ui~ / ~memory~ / ~human~ / ~plan~). A minimal ~Execution~ process-control-block carries identity/status/frames/lineage; scheduling, compute, and memory concerns live in an out-of-core ~ExecutionPolicy~ sidecar.
- *Decision seam* — ~ctx.decide(id, optimizer)~ + the ~DECISION_RECORDED~ event: the substrate for reasoning routing, memory recall, and self-optimization, all replay-safe by construction (P9).

*The runtimes* (each opt-in):

| Runtime | What it adds |
|---------+--------------|
| *Reasoning* (~@loom/reasoning~) | Cheap-first model routing + confidence-based elevation (Gemma → Flash → Pro → Opus); routes logged via the decision seam |
| *Memory* (~@loom/memory~) | First-class tiers (working / episodic / semantic / procedural) with eviction/summarization/promotion + replay-safe *logged recall* |
| *Compute placement* (~@loom/dispatcher~) | ~PlacementDispatcher~ routes each execution to a named target (local / remote-HTTP / Cloud Run) by policy |
| *Scheduler* (~@loom/scheduler~ in the effect path) | Bounded concurrency + priority admission control; zero-overhead when unconfigured |
| *Scale-out storage* (~@loom/store-postgres~) | Postgres event/snapshot/branch stores + cross-node live subscribe (~LISTEN/NOTIFY~) |
| *Intelligence* (~@loom/analytics~) | Read-only analytics over the log + an opt-in, *logged* self-optimizing router + an advisory runtime-intelligence report |

*The kernel-hardening rings* — what makes it genuinely a kernel:

- *K1 — Syscall ABI.* ~ctx.*~ is a versioned, conformance-pinned surface (~execute~ / ~run~ / ~decide~ / ~parallel~ / ~suspend~ / ~emit~ / ~stream~ / ~ui~).
- *K2 — Protection ring.* The ~EffectRuntime~ authorizes every effect against a least-privilege ~GrantTable~; ungranted effects are *denied* and the denial is logged.
- *K3 — Resource accounting.* ~meteringMiddleware~ meters tokens/$/latency onto the log and enforces *budgets* by admission control.
- *K4 — Fault supervision.* ~SupervisingDispatcher~ adds restart/backoff + a *circuit breaker* for flaky models/tools.
- *K5 — Event-schema ABI.* The on-disk event set is versioned and pinned; ~deploy-sim~ is the CI gate.

*AI-native DX* — ~@loom/appgen~ turns a natural-language intent into a structured spec, then emits *plain, static, inspectable TypeScript you own* (no runtime NL interpretation).

*Core runtime*

| ~@loom/core~               | Authoring builders (~flow$~, ~step$~, ~handler$~, ~tool$~, ~agent$~, ~projection$~, …) + shared types |

*Agentic*

| ~@loom/llm~                | Provider-agnostic LLM abstraction (Anthropic, OpenAI, custom) |

*Compute & distribution*

# Headless (prints to the console)
pnpm --filter @loom/agent-network start

pnpm --filter @loom/cloud-command-center dev

Inspect any run's durable log with the CLI (for apps using SQLite storage):

#+begin_src sh
loom logs    --db .loom/events.db <executionId>        # tail the event timeline
loom debug   --db .loom/events.db <executionId> --at 5 # time-travel: state at sequence 5
loom inspect --db .loom/events.db <executionId>        # web timeline + slider
#+end_src
