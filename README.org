#+title: Loom
#+author: Sushil Chhetri

*The framework for durable, event-sourced agentic applications.*

Loom treats an intelligent workflow as a *process that unfolds over time*, not a request that returns once. Every decision it makes is appended to an immutable event log — so any execution can *pause for a human, resume on another machine, replay bit-for-bit for debugging, fork to explore alternatives,* and be *evaluated against its own history*. You write the intelligence in plain TypeScript; Loom provides the durable spine that makes it trustworthy in production.

#+begin_quote
*The durable event log is the moat.* Durability, resumability, deterministic replay, branching, evals, and time-travel debugging are all just different lenses on one append-only log.
#+end_quote

- ⏸️  *Durable suspend / resume* — a flow can wait days for a human, survive a restart, and continue from exactly where it left off. Completed steps are never re-run.
- 🔁  *Deterministic replay* — state is a pure fold of the event log; the same events always reconstruct the same state.
- 🌱  *Git-style branching* — fork an in-flight execution, simulate alternatives concurrently, and promote a winner. Branch-only, no merge.
- 🤖  *Agentic, end to end* — LLMs, ReAct agents, MCP tools, and agent-to-agent calls are all durable, replayable *effects*.
- 🎨  *Bring your own renderer* — the same backend renders in React, Angular, Web Components, or the terminal.
- 🧩  *One composition root* — ~defineConfig~ wires an app from a static config; the ~loom~ CLI, testing kit, evals, deploy-simulation, and a pluggable-compute seam surround it.

* Quick start

#+begin_src sh
npm create loom-app@latest my-app && cd my-app && pnpm install
#+end_src

Define a flow — schema-checked steps plus an ordinary ~async~ runner:

#+begin_src ts
import { z } from "zod";
import { step$, handler$, flow$ } from "@loom/core";
import type { FlowRunner, RegisteredFlow } from "@loom/workflow-runtime";

const greet = step$({
  id: "greet",
  inputSchema: z.object({ name: z.string() }),
  outputSchema: z.object({ message: z.string() }),
  handler: handler$(async (input) => ({ message: `Hello, ${input.name}!` })),
});

const runner: FlowRunner<{ name: string }, { message: string }> = (ctx, input) =>
  ctx.run(greet, input);

export const helloFlow = {
  definition: flow$({
    id: "hello", name: "Hello", version: "1.0.0",
    inputSchema: z.object({ name: z.string() }),
    outputSchema: z.object({ message: z.string() }),
    steps: [greet],
  }),
  runner,
} as RegisteredFlow;
#+end_src

Wire it with ~defineConfig~ and run it:

#+begin_src ts
import { defineConfig } from "@loom/app";
import { helloFlow } from "./hello";

const app = defineConfig({ storage: { kind: "memory" }, flows: [helloFlow] });
const state = await (await app.runtime.start(helloFlow, { name: "Ada" })).waitForCompletion();
console.log(state.variables._output); // { message: "Hello, Ada!" }
await app.close();
#+end_src

*The three moves to remember:*
1. ~ctx.run(step, input)~ — do a unit of work (recorded, replay-safe, exactly-once).
2. ~ctx.suspend({ on })~ — pause durably for a human or an external signal.
3. ~runtime.fork(id, sequence)~ — branch from any point to explore alternatives.

*Pause for a human, then resume* — even across a process restart:

#+begin_src ts
const decision = (await ctx.suspend({ on: "ApprovalGranted", correlationKey: input.target }))
  as { approved: boolean };
// …later, possibly in a new process:
await app.runtime.resume(executionId, { eventType: "ApprovalGranted", payload: { approved: true } });
#+end_src

* Core ideas

- *Event sourcing* — execution state is never stored directly; it's derived by folding an append-only log of ~EventEnvelope~ s. State ~= fold(events)~.
- *Deterministic replay* — the fold is a pure function, and side effects are quarantined behind the ~EffectRuntime~, so a resume, a fork, and a debug-replay all reconstruct identical state.
- *Suspension is first-class* — pausing for a human is a normal outcome, not an error. ~ctx.suspend()~ writes a durable checkpoint; ~resume()~ continues from it.
- *Plain code, not a DSL* — a flow's orchestration is an ordinary ~async~ function using ~ctx.run~ / ~ctx.suspend~ / ~ctx.parallel~. Loom adds durability around your code; it doesn't replace it.
- *Static, replay-safe wiring* — flows and effects are registered statically (the folder convention is honored by build-time codegen, not runtime globbing), so a remote worker or a replay reconstructs an identical graph.
- *Isomorphic core, pluggable edges* — storage, compute placement, LLM providers, and renderers are all interfaces. The same flow runs in a test, a browser tab, a Node server, or on Cloud Run.

** How it works

Every execution is an ordered list of events; the current state is a pure fold of them. Side effects run once and are memoized; a resume replays the log (serving completed steps from it) until it reaches the suspend point, then continues.

#+begin_example
  defineConfig(config)                     ← one static composition root
       │  { runtime, effectRuntime, projectionRuntime, bus, stores, close }
       ▼
  runtime.start(flow, input)
       │  ctx.run(step)  →  EffectRuntime (tool / llm / human / a2a)  +  middleware
       ▼
  ExecutionJournal ──► ReplayVM (fold, in-memory)      state = fold(events)
       │  (sole sequencer + writer)
       └──────────────► EventStore  (memory · SQLite · your own backend)
                              │
                        ProjectionRuntime ──► React / Angular / Web Components / terminal
                              │
                    loom logs · debug · inspect · eval · deploy check
#+end_example

*Bring your own everything.* Storage (~storage: { kind: "custom", eventStore, snapshotStore }~ — Postgres/Redis/DynamoDB), renderer (React/Angular/WC/terminal/DOM), and components (custom widgets in the renderer registry) are all swappable — the durable log never depends on them.

* Packages

*Core runtime*

| Package                    | Description |
|----------------------------+-------------|
| ~@loom/core~               | Authoring builders (~flow$~, ~step$~, ~handler$~, ~tool$~, ~agent$~, ~projection$~, …) + shared types |
| ~@loom/workflow-runtime~   | Durable execution — ~start~ / ~resume~ / ~fork~ / ~loadState~, the ~ExecutionJournal~, ~WorkflowContext~ |
| ~@loom/replay-vm~          | Deterministic replay — ~foldEvents~ / ~ReplayVM~ (pure state reconstruction) |
| ~@loom/event-runtime~      | Append-only ~EventStore~ (memory / SQLite) + git-style ~BranchRegistry~ |
| ~@loom/snapshot-runtime~   | ~SnapshotStore~ — bounded-tail replay |
| ~@loom/effect-runtime~     | Effect isolation for tool / LLM / human / A2A effects |
| ~@loom/sdk~                | Public re-export surface |

*Composition & effects*

| ~@loom/app~                | *Composition root* — ~defineConfig~ assembles the runtime, stores, middleware, projections, and A2A bus from one static config |
| ~@loom/middleware~         | Effect middleware — ~retryMiddleware~ (deterministic backoff); the ~(ctx, input, next)~ chain |
| ~@loom/registry~           | Workflow / agent registry |

*Projection & UI*

| ~@loom/projection-runtime~ | Event → projection folding with live subscriptions |
| ~@loom/a2ui~               | Agent-to-UI protocol — durable patch/event UI updates (~ctx.ui.set/merge/append~) |
| ~@loom/blueprint-runtime~  | Schema-driven, JSON-serializable UI blueprints |
| ~@loom/renderer-react~     | React renderer (with opt-in render-side fiber) |
| ~@loom/renderer-terminal~  | Terminal renderer — same blueprint, non-React surface |

*Agentic*

| ~@loom/llm~                | Provider-agnostic LLM abstraction (Anthropic, OpenAI, custom) |
| ~@loom/agent~              | ReAct-style agent loop over your tools |
| ~@loom/mcp~                | Model Context Protocol client + tool discovery |
| ~@loom/a2a~                | Agent-to-Agent protocol client + server |
| ~@loom/capability~         | Flows as intent-addressable capabilities (~capability$~ + ~CapabilityCatalog~) |
| ~@loom/intent~             | Routes natural-language intent to a capability |
| ~@loom/planner~            | Composes an ordered, multi-step plan from a goal |
| ~@loom/memory~             | Scoped, TTL/size-bounded agent memory |
| ~@loom/orchestrator~       | Composable approval (~decideApproval~) + plan-dispatch primitives |

*Compute & distribution*

| ~@loom/dispatcher~         | Execution placement — decides *where* a flow runs; owns worker allocation + retries |
| ~@loom/worker-runtime~ (~-local~ / ~-remote~) | Worker SPI + ~ExecutionPackage~ (resume coordinates, never code); in-process + HTTP impls |
| ~@loom/worker-server~      | Stateless worker HTTP endpoint — ~POST /execute~ |
| ~@loom/platform-cloudrun~  | Cloud Run adapter — ~CloudRunWorkerRuntime~ + sizing policy |
| ~@loom/graph-executor~     | Distributed fan-out — per-node executions (one writer each), joined via lineage |
| ~@loom/scheduler~          | Ephemeral cooperative scheduler — priority lanes, ~parallelLimit~, cancellation (opt-in) |

*DX & tooling*

| ~@loom/cli~                | The ~loom~ CLI — ~logs~ / ~debug~ / ~inspect~ / ~eval~ / ~deploy check~ / ~gen~ / ~new~ / ~check~ |
| ~@loom/testing~            | Testing kit — ~createTestApp~, ~waitForPhase~, ~captureGolden~, VCR LLM provider |
| ~@loom/eval~               | Log-as-fixture evals — replay recorded logs, diff/score runs |
| ~@loom/deploy-sim~         | Deploy simulation — replay history vs new flow defs to catch resume-breaking changes |
| ~@loom/scaffold~           | Code templates + registration codegen (~loom gen~ / ~new~) |
| ~@loom/compiler~           | Vite plugin + CLI — ~handler$~ extraction, flow-graph validation, resumability metadata |
| ~@loom/telemetry~          | Zero-overhead telemetry adapters + hooks |

** Running them

#+begin_src sh
# Headless (prints to the console)
pnpm --filter @loom/agent-network start
pnpm --filter @loom/a2a-mesh start

# Browser UIs (open the printed http://localhost:5173)
pnpm --filter @loom/cloud-command-center dev
pnpm --filter @loom/db-command-center dev        # or -wc for Web Components

# Server + client topologies (client :5173 + durable server :8787)
pnpm --filter @loom/db-command-center-server dev
pnpm --filter @loom/incident-war-room dev
pnpm --filter @loom/incident-war-room demo:fork  # narrated headless fork → simulate → promote
pnpm --filter @loom/schema-migration-planner dev
#+end_src

Inspect any run's durable log with the CLI (for apps using SQLite storage):

#+begin_src sh
loom logs    --db .loom/events.db <executionId>        # tail the event timeline
loom debug   --db .loom/events.db <executionId> --at 5 # time-travel: state at sequence 5
loom inspect --db .loom/events.db <executionId>        # web timeline + slider
#+end_src
