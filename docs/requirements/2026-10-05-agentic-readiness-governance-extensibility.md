# Loom audit D: governance & safety for autonomy + extensibility (main 3d2056e)

Method: code only (non-test source). Docs/ADRs/memory ignored except where a doc claim was checked against code.
Paths are relative to the repo root. "G2" = the code's own "unwired == permissive" convention.

## Headline

Loom's governance is a set of well-built, individually sound, OPT-IN primitives. Nothing is on by default, and the
identity that the primitives key on (`PrincipalChain`) is lost at almost every boundary an autonomous system
crosses (dispatcher, A2A, recovery, timers, child spawn). The kernel gives strong DETECTION/AUDIT (journal,
EFFECT_DENIED, QUOTA_EXCEEDED, SAFETY_BLOCKED, EXECUTION_DENIED, DECISION_RECORDED) and weak PREVENTION
defaults. Extensibility is good for storage/dispatch/LLM/auth SPIs (versioned + conformance kits + scaffold),
but the packaging story is not consumable outside the monorepo today.

### Axis 1 verdict

* Preventive controls that are genuinely strong: tool-id-level K2 + deny-wins policy, delegation intersection + holder binding + exp clamp, QuickJS sandbox, taint refusal at prompt positions, audit chain with Ed25519, typed resume gates, in-doubt parking for non-idempotent effects (K9.3).
* Default posture: fail-open at every layer (no authorizer, no executionAuthorizer, no resumeAuthenticator, no metering/safety, no verify, no deadline, taint producers off, A2A/MCP servers unauthenticated, A2A bus auto-approves).
* The identity chain breaks at: dispatcher, A2A server and client, recovery, timers, child spawn, and the event log.
* Biggest structural gap: no "autonomy envelope" concept (agent-scoped budget + spawn cap + deadline + tool allowlist + approval class) that composes these.

### Composition (`@loom/app` defineConfig, `app/src/defineConfig.ts`)

* Swappable by key: storage (custom), memoryStore, timers(store/leases/dispatcher), dispatcher, effectMiddleware, registerEffects, telemetry, authorizer, executionAuthorizer, resumeAuthenticator, secrets, compliance, retention, verify, projectionRuntime, validate.
* Not a key (hand-wire or impossible): LLM provider / reasoning, Scheduler (exists in `EffectRuntimeOptions` but not exposed), ContentStore/claim-check, metering/safety/budget (middleware you assemble yourself), A2A bus transport (hardwired `InProcessA2ABus`), safety validators, audit-chain / crypto wrapping (wrap the store yourself), servers (A2A/MCP) created outside.
* Flat spelling of grouped options THROWS (`defineConfig.ts:~745-760`): explicit break policy.
* `registerEffects` is the universal escape hatch, so a 3P can add anything - but then governance (authz/metering) must be hand-assembled and nothing verifies it was.

Imports used (`flow$,handler$,step$,tool$,agent$,instructions$,skill$,schedule$,memory$,projection$` from `@loom/core`; `defineConfig` from `@loom/app`; `retryMiddleware`, `isClaimCheck`, `sentinelPreset`) all exist as exports in the current sources (checked `core/src/builders/*`, `middleware/src/index.ts`, `plugins/sentinel/src/index.ts`).
* **The generated app's package.json hard-codes `"@loom/app": "workspace:*"` etc.** (`templates.ts:240-250`): it installs only inside this pnpm workspace. A fresh 3P outside the monorepo cannot `pnpm install` it (no registry versions). Template comment "@loom/* publish require-only exports" is aspirational: nothing publishes.
* Generated `app/config.ts` is memory storage, no authorizer, no verify, no deadline (`templates.ts:282-290`): the scaffold teaches the fail-open posture.
* Plugin scaffold: 19 seams (`tools/scaffold/src/plugin.ts`: store, dispatcher, telemetry, middleware, timer, lease, content, durable-state, read-model, keystore, memory, projection, worker, llm, authorizer, execution-authorizer, resume-authenticator, timer-dispatcher, policy), type-checked against real `.d.ts` by `tools/scaffold/src/templateTypes.test.ts` (good fitness test). Missing seams: tool/effect, protocol bridge, renderer, safety validator, secret resolver, reasoning/learning policy, scheduler. First-party templates emit `workspace:*`; 3P use `"*"` (`plugin.ts:1381`) - which cannot resolve until packages are published.
* Plugin scaffold emits tsconfig refs `../../packages/<dep>` (`plugin.ts:1443`) for in-tree plugins - monorepo layout assumption (only for the first-party path).

### Packaging (all `package.json` under packages/ plugins/ tools/)

* Every package: version `0.0.1`, `private` absent (so publishable by accident), no `files`, no `publishConfig`, no `license`, no `sideEffects`, internal deps as `workspace:*` (67 of 72 packages). No `.changeset`, no publish workflow (only `ci.yml`). `@loom/bench-throughput` is the only `private`.
* Format: CJS `require`-only `exports` (e.g. `packages/core/package.json`), except `@loom/conformance` which declares `"type":"module"` ESM-only - so a CJS app (the scaffolded shape) cannot `require` the conformance kit directly, and the scaffold comment "require-only exports" is wrong for that package.
* `isolate` resolves its runner via `__dirname` / `../dist/runner.js` (`IsolatedToolEffect.ts:240-247`): works installed, falls back to dist in dev. No other runtime monorepo assumptions found in `packages/*/src` or `plugins/*/src` (grep for `../../packages|findWorkspaceRoot` = only scaffold/doc comments).
* Net: a third party cannot consume Loom outside the monorepo today; examples use pnpm `link:`/overrides to a sibling checkout (AGENTS.md).

### Plugin authoring (`@loom/plugin-kit`)

`packages/plugin-kit/src/index.ts` is 61 lines: `CustomStorage`, `StoragePreset`, `defineStoragePreset`. That is all. It does NOT provide: a plugin manifest, contribution registry (effects/middleware/authorizers/bridges), lifecycle (start/stop/health), SPI-compat declaration, or anything beyond storage presets. Other plugins compose by ad-hoc functions (`registerMcpInvoke(effectRuntime, ...)`, `createA2AServer(...)`, `sentinelPreset`). Verdict by use case:

| 3P goal | Enough today? |
|---|---|
| New vector/memory store | Yes (MemoryStore SPI v2.1 + kit; precedent loom-plugin-vector) |
| New event/snapshot store | Yes (kits) |
| New LLM vendor | Yes via `LlmProvider` + kit; wire by hand through `registerEffects` |
| New compute backend | Yes (Dispatcher/WorkerRuntime SPIs + kits) |
| New protocol bridge | Only by copying A2A/MCP patterns; no SPI, no identity contract |
| New learning policy | Via `ctx.decide` policy option; no kit/SPI version |
| New authz scheme | Yes (3 SPIs + kits) but identity transport (principal) is not guaranteed across boundaries |
| New safety classifier | `SafetyValidator` interface only; sync; no kit |

### Stability signals

* Versioned ABI/SPIs: `KERNEL_ABI_VERSION`, `EVENT_SCHEMA_VERSION`, 7 SPI constants listed above; `packages/spec/src/manifest.ts` + `capabilities.ts` registry with fitness tests (`packages/spec`) catching ADR/doc drift.
* Self-admitted weakness (`capabilities.ts:535`): "nothing forces the constant to be bumped when the shape changes - the version is a declaration, the kit is the check."
* Lockstep monorepo, all `0.0.1` (`spec/src/manifest.ts:104`, `render.ts:43`): no semver contract for consumers; no deprecation windows (flat config spellings throw).
* Scaffold templates are type-checked against built `.d.ts` (good); app template is not (only seams).

## Top gaps (ranked; safety-critical first)

1. Principal is not durable and not carried across dispatcher/A2A/recovery/timers/children => authz, policies, delegation attenuation silently degrade to "no principal" (kernel: persist principal ref; dispatcher SPI + wire-abi: carry it).
2. Execution-lifecycle authz is fail-open for principal-less calls, and no 1P ExecutionAuthorizer/ResumeAuthenticator exists (kernel option for strict mode + 1P reference impls).
3. Agent loop executes any model-named effect and does not validate tool input (1P `@loom/agent`: membership + schema check).
4. Default posture permissive everywhere; scaffold teaches it; verify off by default and lacks rules for authorizer-absent / no deadline / unbounded spawn / ungated destructive (app default `strict` + 1P verify rules).
5. A2A server unauthenticated by default, bool `authorize` discards identity, client picks executionId, no task ownership, binds all interfaces; MCP server likewise; `InProcessA2ABus` auto-approves HITL gates (1P plugins).
6. Approval is not bound to what the approver saw (no action hash), authenticator absent by default (kernel/1P).
7. No unbounded-autonomy envelope: no default deadline, unlimited child depth/breadth, no global/tenant live-execution cap, no rate limiting, metering not in defineConfig, budget overshoot on first call/parallel steps, no per-agent budget (1P middleware + app config).
8. Kill switch is a per-process sync predicate; no tenant/system cancel-all, no cascade to children, ReasoningRuntime path bypasses authz/metering/safety/kill (1P admin plane + kernel cascade).
9. Taint defence depends on opt-in producers and covers prompt positions only (flip MCP/A2A defaults; add taint->approval rule) (1P).
10. Packaging: nothing consumable outside the monorepo (workspace:* in scaffold, 0.0.1, no files/license/publish, plugin-kit is storage-only, many SPIs unversioned, no Effect/bridge kit) (tooling/release).

Also noted: isolate is not an adversarial boundary (fs/child_process unblocked); audit chain lacks cross-execution anchoring; MCP authz coarse (single `mcp-invoke` id).
