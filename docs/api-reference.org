* Authoring builders — ~@loom/core~
:PROPERTIES:
:CUSTOM_ID: authoring

Declarative ~$~ builders produce plain, serializable definition objects (each tagged with a ~_tag~). They have no runtime behavior on their own — the runtime interprets them.

#+begin_src typescript

}
interface ToolDefinition<TIn, TOut> {
  readonly _tag: "ToolDefinition"; id: string; name: string; description: string;
  kind: EffectKind; inputSchema: ZodSchema<TIn>; outputSchema: ZodSchema<TOut>;
  jsonInputSchema?: Record<string, unknown>; // R4b — JSON Schema input (MCP); bounded + sanitised before a prompt
  trustJsonSchemaText?: boolean;     // R4b — operator vouches for its description/title text
  idempotent?: boolean;              // K9 delivery semantic
  errors?: Record<string, ZodSchema>;// ADR 0060 declared failure channels
  mode?: EffectMode;                 // ADR 0073 — which invocation seam (below)
}
// ADR 0073 — which side of the determinism boundary a tool may be invoked from.
//   "journaled" — runs inside an execution; result recorded and replay-substituted.
//   "ambient"   — an enrichment read (pagination, drill-down, a surface refetch) that
//                 must NEVER append to the log; runs only via invokeTransient.
// `execute` refuses an ambient effect; `invokeTransient` refuses a journaled one
// (EffectModeViolationError). Undeclared = today's behaviour on both seams (G2).
// A boundary CHECK, not a journaling mode: an ambient tool is not "an effect that
// skips its journal" — it may not enter an execution at all, so there remains
// exactly one replay model. Declaration lives here; the enforced copy is on the
// registered effect (`new ToolEffect(fn, { mode })`).
type EffectMode = "journaled" | "ambient";
interface AgentDefinition {
  readonly _tag: "AgentDefinition"; id: string; name: string; description?: string;
  tools: ToolDefinition[]; policies?: PolicyDefinition[]; memoryId?: string;
  version?: string; capabilities?: { streaming?: boolean }; skills?: AgentSkillDef[];
}
// Also: SkillDefinition, ProjectionDefinition, MemoryDefinition, PolicyDefinition, InstructionsRef/Spec/Loader.

*Reserved ~variables~ keys (2.0):* ~_decisions~ (logged ~ctx.decide~ choices, P9), ~_denials~ (capability ~EFFECT_DENIED~ audit, K2), ~_resources~ (metered totals ~{ tokens, costUsd, ms, count, exceeded? }~, K3), ~_blocked~ (behavioral-safety ~SAFETY_BLOCKED~ audit, K6), ~_indoubt~ (parked ~EFFECT_INDOUBT~ deliveries, K9), and ~_shredded~ (crypto-shred ~PAYLOAD_SHREDDED~ tombstones, K10). The full 13-key table is in the [[file:loom-2.0/10-event-schema-reference.md][event-schema reference]].

*Tasks & the process-control-block (2.0).* A step generalizes to a *task*; the minimal ~Execution~ PCB and its out-of-core ~ExecutionPolicy~ sidecar carry scheduling/compute/memory intent without bloating the core.

*Flow-code versioning for in-flight executions (2.0, K11).* Each flow carries a ~flowContentHash~ (structural fingerprint over step bindings + durable policies, emitted by ~@loom/compiler~ and pinned into ~EXECUTION_STARTED~). A resume whose flow code no longer matches the pinned hash throws ~FlowCodeMismatchError~ rather than replaying against drifted code; ~resumeAs~ deliberately migrates such a run — ~"replay-check"~ verifies every recorded step still exists in the new flow (refuses with ~FlowMigrationCheckError~ otherwise), ~"operator-ack"~ vouches without the check. Either way it records a durable, replay-deterministic ~EXECUTION_MIGRATED~ verdict.

~WorkflowRuntime~ is also exported as *~ExecutionRuntime~ (2.0)* — the same class, renamed for the execution-kernel framing.

** ~ExecutionContext~ — the flow API *(2.0; ~WorkflowContext~ is an alias)*

The ~ctx~ handed to every runner. Every call is durable, ordered, and replayable — and is the kernel's *versioned syscall surface* (K1).

*Durable timers (2.0, T1).* ~ctx.sleep~/~ctx.sleepUntil~ suspend the execution with the absolute wake time recorded in the log; a wired ~TimerService~ fires a durable ~TIMER_FIRED~ resume, so a sleep survives restarts and replays deterministically (the scheduled time is in the log — wall-clock drift never enters the fold). Without a timer service the suspension is still durable and resumable by any node. Declare cron-driven starts with ~schedule$~ (see [[#authoring][~@loom/core~ builders]]) and wire both via ~defineConfig({ timers })~.

*Recovering an abandoned execution ([[file:adr/0004-failure-recovery.md][ADR 0004]]).* A dead or wedged *worker* is redispatched by the dispatcher (~executeTimeoutMs~) and resumes idempotently. A dead *supervisor* is not covered — detection lives in its process — so ~recoverAbandoned(runtime, { source, isAbandoned })~ (~@loom/workflow-runtime~) enumerates ~running~/~pending~ executions and resumes the ones your predicate claims, via the same ~EXECUTION_RECOVERED~ resume the worker uses. A re-drive answers no gate ([[file:adr/0104-recovery-never-answers-a-gate.md][ADR 0104]]): the recovered flow parks at the next ~ctx.suspend~ it reaches until a resume names that gate. ~isAbandoned~ is REQUIRED: a running execution on a healthy node is byte-identical in the log to an orphaned one, so only the deployment can decide. Run it from a cron or Job, not as a service. A step failure the flow caught leaves the execution ~running~, so it is recovered too ([[file:adr/0105-a-caught-step-failure-is-not-the-executions.md][ADR 0105]]); ~maxRecoveries~ skips a claimed execution whose last N re-drives made no progress (consecutive ~EXECUTION_RECOVERED~ events since the last ~STEP_COMPLETED~ / ~EXECUTION_SUSPENDED~ / ~EXECUTION_RESUMED~; ≥ 1, default unbounded) and reports it in ~summary.exhausted~ / ~onExhausted~, so a poison execution stops costing every pass. ~reconcileTimers(runtime, { source, timers })~ re-arms the timer row of every execution suspended on a ~wakeAt~ (idempotent — ~schedule~ dedupes); run it once after upgrading to EVENT_SCHEMA 1.21.0, whose predecessor let ~TimerService~ retire the row of a timed park a parallel sibling's failure had folded to ~failed~.

*Start-once for a caller-chosen id ([[file:adr/0103-durable-bootstrap-for-caller-chosen-ids.md][ADR 0103]]).* ~start(flow, input, { executionId })~ makes the execution's ~EXECUTION_STARTED~ durable BEFORE the flow body runs, so a duplicate start (a redelivered trigger, two nodes firing the same schedule occurrence) rejects with ~ExecutionAlreadyExistsError~ and nothing runs — no effect, no fold, no ~onEvent~. Catch it to treat the duplicate as "already started"; there is no separate ~startOnce~. Any other failure of that write rejects with ~StorageWriteError~ — including a start refused on the fence twice with sequence 0 still absent, whose cause is ~StartFencedOutError~ (a newer token's holder wrote nothing and may be dead, so the start stays retryable; L20). A minted ULID cannot collide, so ~start~ without an ~executionId~ pays no extra write and is byte-identical to before. ~onEvent~ otherwise stays pre-durability for every later event: a consumer that must act only on durable facts reads them back (the ADR 0058 catch-up shape).

*Durable placement (#392).* ~start(flow, input, { computeTarget })~ records the compute lane on the execution's ~EXECUTION_STARTED~ anchor (envelope metadata — descriptive, never folded, so replay is untouched), and ~placementOf(eventStore, executionId)~ (~@loom/workflow-runtime~) reads it back in one point-read. ~TimerService~ and ~recoverAbandoned~ accept a ~dispatcher~ and re-drive to that lane instead of resuming in-process; a fork inherits its parent's lane and ~fork(…, { computeTarget })~ overrides it. A HINT, not a pin: ~PlacementDispatcher~ falls back for an unregistered target (and warns once), because a retired lane must not strand the executions that named it.

*What is stuck, and is anything watching it.* ~orphanCensus(runtime, { source, leases?, buckets? })~ (~@loom/workflow-runtime~) is the READ-ONLY pass beside the acting ones: no predicate, no writes, no policy — a predicate is what a census must not need, since the question it answers is whether YOURS is right. It bands ~running~/~pending~ executions by age (cumulative, with a sample of ids) and, given a lease store, classifies each as ~held~ / ~expired~ / ~none~. `none` is the one to watch: a stuck execution nothing ever leased cannot be recovered from evidence at all. Clocks: lease expiry is judged on ~options.now ?? leases.storeNow?.() ?? Date.now()~ (the store's own clock when it has one), while execution ages use the wall clock or ~now~. ~LeaseStore.storeNow?()~ is optional since SPI 2.1.0 and implemented by ~PostgresLeaseStore~ (DB time), so a census run from a skewed host still judges leases on the clock that stamped them.

*Retiring an abandoned branch.* Retention never reclaims an execution while a live descendant branch still has events (R5.3) — and a branch nobody answered is suspended forever, so a forked parent returns ~blocked-by-branch~ on every sweep, permanently. ~retireAbandonedBranches(runtime, registry, parentId, { isAbandoned })~ (~@loom/workflow-runtime~) walks that parent's direct children, offers the non-terminal ones to your predicate, and ~cancel()~s the ones it claims — a durable ~EXECUTION_CANCELLED~, not a deletion, so *why* the branch ended survives. Ordinary retention then collects the branch on its own TTL and the parent behind it. ~isAbandoned~ is REQUIRED, for the same reason ~recoverAbandoned~'s is: a branch parked on a human gate is someone's open question, not garbage. The summary reports what it left alone.

*Fail-closed execution authorization (R3, 1P half).* ~executionAuthorizer~ gates ~start~/~resume~/~cancel~/~loadState~, but only for a call that carries a ~principal~: a call with none skipped it, so an edge that forgot to attach one was wide open. ~WorkflowRuntimeDeps.executionAuthz: { requirePrincipal: true }~ (set by ~security.strict~; ~strict: { requirePrincipal: false }~ opts out) makes the authorizer see the principal-less request (~principal: undefined~) so the policy decides. Off (default) is byte-identical. The kernel's own principal-less machinery — ~TimerService~ (wakes, schedule starts), ~recoverAbandoned~, ~retireAbandonedBranches~, the ~superviseChildren~ child start and parent resume — presents ~runtime.systemOptions()~ (~{ system }~, or ~{}~ when the mode is off): an identity-compared per-instance grant, not a principal, never recorded and never reaching an effect's authorization. A clone, JSON copy or another runtime's grant is refused. It is an in-process capability: never hand it to request-derived code. Observers that read state (~orphanCensus~, ~reconcileTimers~, ~liveQuery~) take ~runtime.systemStateReader()~. ~executionAccessPolicy(options)~ (~@loom/workflow-runtime~) is the reference ~ExecutionAuthorizer~: per-op ~rules~ (~"owner" | "tenant" | "any" | "deny"~; defaults ~start: "any"~, the rest ~"tenant"~), ~allowWorkflows~, ~requireTenant~, ~allowAnonymous~ (default false), ~resolveOwner~, ~unknownOwner~, ~maxTracked~; it exposes ~ownerOf~ / ~adopt~. INTERIM: the kernel does not yet record who started an execution (R3 kernel half, ADR 0111), so the policy remembers owners in a bounded in-process map, which does not survive a restart (unknown owner is refused unless ~resolveOwner~ answers), and the internal paths use the blanket system grant rather than the starting principal. Ownership is recorded in ~ExecutionAuthorizer.committed~ (called once a start is durable; never in ~authorize~), inherited from ~RunOptions.parentExecutionId~ for a principal-less child, and never evicted (~maxTracked~ refuses further starts). ~fork~ (~query~ parent + ~start~ child), ~restoreFromState~ (~resume~) and ~acquireFence~ (~cancel~ / ~start~) take ~{ principal, system }~ and are gated. ~LocalWorkerRuntime~ holds NO system grant by default: a dispatched package acts as ~ExecutionPackage.principal~ (Dispatcher SPI 1.2.0); ~new LocalWorkerRuntime(runtime, { system })~ is the explicit opt-in for kernel re-drive targets (~runsAsSystem~; ~createWorkerServer~ then requires ~authorize~). ~InProcessA2ABus~ (~options.principal~ / ~DispatchOptions.principal~), ~executeGraph~ (~options.principal~), ~createLoomCarrier~/~handleRpc~ (~resolvePrincipal~ on every ~execution.*~ method) and ~createA2AServer~ (~resolvePrincipal~) attach the caller; without one the call is anonymous and refused under strict.

*Retention and compaction of an encrypted log (ADR 0022 Amendment).* ~LogLifecycle.compact~ throws ~UnsafeCompactionError~ when the event store encrypts at rest (exposes ~keys~) and the snapshot store does not share that same KeyStore — the checkpoint is the DECRYPTED fold, so a plaintext one would survive a key shred. ~applyRetention~ / ~evaluate~ return ~"unsafe-archive"~ (a ~RetentionOutcome~) when a configured archive does not share the source's keys. Both refuse before anything is read, copied or truncated. A compacted execution is judged on its snapshot plus the surviving suffix, so it is reclaimable.

*Compaction integrity (ADR 0106).* The checkpoint is named for its execution (a blank one used to send every event a later resume appended to execution ~""~), a log compacted before is folded ON its checkpoint (~CompactionCheckpointMissingError~ when that checkpoint is gone, nothing touched), and ~new LogLifecycle(events, snapshots, { pinnedEventTypes })~ keeps the app's pinned-kind events in place through compaction (~EventStore.truncatePrefixKeeping~, SPI 1.5.0). A store without that method can never compact past the first kept event, and ~onWarn~ says so. Compaction never removes the tip when it keeps events, so a checkpoint is always the log's highest missing sequence (the tip rule). Every kernel-written kind and every non-string is refused in ~pinnedEventTypes~. ~compact~ consults the ~pinned~ predicate only when ~pinnedEventTypes~ is empty (then a pinned execution is left uncompacted); with kinds declared, a pinned execution compacts around them. ~compactionExempt~ (consulted always) keeps a whole log uncompacted. ~compact~ refuses reserved control streams. ~shredSubject~ places its tombstone after the folded tip (pass a ~snapshotStore~, raw or the app's encrypting one, tenant-scoped or not; required on a compactable store) and is retry-safe, and ~EraseCoordinator~ takes a ~snapshotStore~ so a compacted terminal execution is not read as live. A snapshot whose non-blank identity names another execution is refused (~SnapshotIdentityMismatchError~); a blank one is filled. ~reconstructAt~ refuses a position inside compacted history (~CompactedHistoryError~). ~fork~ of a compacted parent is served exactly — every event between the nearest snapshot and the fork point survives, or a snapshot sits exactly at it (a ~[0]~ log's checkpoint is forkable: the range is the folded tip) — or refused with ~CompactedForkPointError~ (~reason~, ~forkableFrom~..~forkableThrough~) and nothing written ([[file:adr/0107-compacted-fork-points-and-the-blank-stream.md][ADR 0107]]). ~LogLifecycle.blankStreamCensus()~ / ~rehomeBlankStream({ apply, assign })~ (~loom repair blank-stream~) re-home the events the pre-0106 bug wrote to execution ~""~ where a snapshot proves their owner (one batch per execution, under a new fence when the execution is fenced; ~failed~ lists what moved since the census), journal ~EVENTS_REHOMED~, and list the rest with candidates rather than guess; ~""~ is reserved (~isReservedStream("")~).

*Collecting the registry.* After retention reclaims a branch, two rows outlive it. ~LogLifecycle~ forgets the fork edge as it deletes the execution (optional ~removeLineage~ — dead edges otherwise make every future sweep walk them). ~pruneBranchRefs(eventStore, registry, { pageSize?, limit?, protect? })~ (~@loom/workflow-runtime~) pages over ~listRefs~ and deletes refs whose execution has no events — a dangling ref is not merely untidy, since promoting one leaves ~main~ naming an execution nobody can read. It takes NO predicate: unlike "is this branch abandoned", "the execution is gone" is a fact. ~main~ is protected by default and reported as dangling instead.

*Cancellation, deadlines & bounded effects (2.0, K8).* A step's ~timeoutMs~ bounds a single effect; a flow's ~deadlineMs~ (see ~FlowDefinition~) bounds the whole run against the logged ~EXECUTION_STARTED~ timestamp (never reset by recovery). Breach — or ~handle.cancel()~ / ~ExecutionRuntime.cancel()~ — aborts in-flight effects via ~EffectContext.signal~ and records a kernel-driven ~EXECUTION_CANCELLED~.

** ~@loom/plugin-audit-chain~ — a tamper-evident, third-party verifiable log

Hash-chains every event into its ~metadata~, which the fold ignores — so replay is byte-identical whether or not it is wired, and any later edit, insert, reorder or drop is detectable out of band.

*Who can check it (#382).* An ~hmacSecret~ makes the log tamper-EVIDENT: verification needs the same secret, so anyone able to check it could also re-chain and re-sign it. A ~signer~ makes it third-party VERIFIABLE — an auditor holds only ~verifier~ and cannot author an entry. The two are mutually exclusive (different promises), ~keyId~ keeps history verifiable across rotation, an unknown key is rejected rather than skipped, and ~signaturesChecked~ says whether authorship was checked at all so a hash-only pass cannot be over-read.

*Identity, tenancy & delegated authority (2.0, K12).* A ~CapabilityRequest~ can carry a ~PrincipalChain~ (tenant / actor / on-behalf-of / a verifiable delegation). ~DelegationAuthorizer~ honors a *signed, attenuated* delegation only after verifying its HMAC and intersecting its grants with the callee's own authority (~base~, required) — a delegate can never invoke an effect the delegator lacked, nor one the callee lacks (no ambient escalation). Attenuation only narrows. The HMAC secret is *symmetric*, so the signature stops a third party forging a grant set in transit but cannot stop the verifier minting its own; the intersection is what bounds the callee. Cross-organisation delegation is out of scope — see [[file:adr/0024-k12-identity-tenancy-delegated-authority.md][ADR 0024]].

** ~@loom/plugin-crypto~ — encryption-at-rest & crypto-shredding (K10)

Wraps any ~EventStore~/~SnapshotStore~ to encrypt *marked* payload fields (dot-paths per event type) under a per-subject key on append and decrypt on read (AES-256-GCM; unmarked events stored verbatim — zero overhead). Erasure is by key destruction: ~shredSubject~ destroys the key (irreversible for everything encrypted under it, in events *and* snapshots) and appends a durable ~PAYLOAD_SHREDDED~ tombstone. A later decrypting read of a shredded execution throws ~PayloadShreddedError~ — replay fails *loudly*, never silently diverges. Optional store capabilities (fencing, ~readRange~, ~copyPrefix~) are forwarded, so it composes with K9.4 and ~fork()~.

** ~@loom/plugin-a2ui~ — A2UI (Agent-to-UI) adapter

Projects a Loom agent surface onto the *real* Google [[https://a2ui.org][A2UI]] wire
protocol v1.0, so any A2UI-compliant client can render a Loom-driven UI. A **1P plugin**,
kernel untouched (ADR 0069, ADR 0070). Covers **egress**, the inbound ~action~ leg, and
the **~callFunction~ bidirectional RPC** (the agent invokes a named client function and
receives a ~functionResponse~). Only continuous two-way *binding sync* remains out of
scope.

The bridge folds ~SURFACE_PATCH~ events locally and translates Loom's *delta* ops into
A2UI's *absolute* ~updateDataModel~ value-replacement (A2UI has no patch framework);
~remove~ → ~contents: null~. K10-R6 egress redaction is applied on the way out.

~callFunction~ is reconciled with Loom's append-only replay grain **not** as a blocking
sync RPC in the log, but by the client's *result* re-entering as an ordinary recorded fact
— a resume event (grain A) or a ~STEP_COMPLETED~ output (grain B). No client-side effect
runtime is needed; determinism rests on **result-as-recorded-fact + a deterministic
~callId~**. No new event types; ~EVENT_SCHEMA~/~KERNEL_ABI~ unchanged (ADR 0070).

The catalogue named by ~catalogId~ is an enforced claim, not a label
([[file:adr/0088-blueprint-conformance.md][ADR 0088]] D5, amended): the constructor and
~recompose~ both throw for a component tree the supplied ~catalog~ does not cover (structural
checks below), and ~callFunction~ throws for a name the catalogue does not declare under
~functions~ — a catalogue declaring none refuses every call rather than allowing one
unverifiably. Naming ~catalogId~ without supplying ~catalog~ is refused outright (unless it is
the default, which ~defaultCatalog~ backs) — the bridge would otherwise stamp an id it cannot
check a single component against.

** ~@loom/plugin-mcp-app~ — MCP Apps (SEP-1865) egress

Projects a Loom agent surface onto the MCP Apps extension so any MCP host renders a Loom-driven
UI ([[file:adr/0072-mcp-apps-ui-extension-placement.md][ADR 0072]]). Egress only — the host role is out of scope (D2).

*** Pin the template

~surfaceHostPin()~ delegates to ~@loom/plugin-mcp~'s ~hashResourceBody~ — the *same* function the
ingress side applies to a fetched resource, so a pin captured at plan time equals what a reader
recomputes. Two hashing implementations that mostly agree is how a pin stops detecting the drift
it exists to detect ([[file:adr/0063-mcp-dynamic-dispatch.md][ADR 0063]] D1).

*** Redaction is required, not defaulted

~redact~ has no default. The payload crosses the trust boundary into a rendered iframe, and a
list that quietly defaults to empty is a silent leak — "we forgot to configure it" would look
identical to "there is nothing to mask". Pass ~[]~ to assert explicitly that nothing needs it.
Masking happens on egress only; the fold keeps true values so ~increment~/~append~/~merge~ stay
correct.

*** No server push — the View polls its own cursor

The extension has no server→View channel after ~ui/notifications/tool-result~. The only seam it
offers is repeatable view-initiated ~tools/call~, so the template polls ~loom.surface.since~.
This is polling and it is worse than SSE — the extension's limitation, contained behind one
tool. A cursor read returns either ~{ changed: false }~ or a *complete* model, never a delta: a
tail fold is a partial state that only looks like one (a nested patch yields ~{a:{b:1}}~, which a
shallow merge splices over all of ~a~, and a ~remove~ is indistinguishable from untouched). The
cheap tail read is kept purely for change detection.

*** Staleness across a long suspension

~resume()~ already refuses stale *code* (K11), stale *input* (K11.5), forged *approvals* (K12.2)
and post-cancel resume (K8.2). What it cannot know is which version of the data a human was
looking at: the execution knows when *it* suspended, not what the user saw. So the View echoes
~seenSequence~ on every action and ~isStale~ is the predicate — *evidence, not policy*. Whether
a lag invalidates a decision is domain-specific; express it as an [[file:adr/0060-typed-failure-channels.md][ADR 0060]] ~staleDecision~
channel so it is recorded, replay-substituted, and branchable into re-confirmation.

Absent provenance counts as **stale**: an action with no ~seenSequence~ is indistinguishable
from one made against arbitrarily old data.

untrusted client, and the head sequence it must be judged against is a property of the LOG — which
the tool handler owns and `ctx` does not expose. So the handler decides *stale or not* and the flow
decides *what that means*:

if (signal.stale) {

  ctx.ui.set("status", "re-review");

Emits ~SKILLS_SELECTED~ / ~AGENT_TOOL_CALL~ / ~AGENT_COMPLETED~ events via ~ctx.emit~.

*Tool menu (every loop: ~AgentRunner~, ~agentStep$~, ~agentLoop$~).* The model sees each tool's real argument structure: ~LlmToolSpec.inputSchema~ is the JSON Schema of the tool's Zod ~inputSchema~ (~toolInputJsonSchema~; a hand-written converter that degrades to ={}= for what it cannot express). A tool call the model returns is executed only if its name is on the agent's menu (the definition's tools plus the selected skills' tools) AND its input passes the tool's ~inputSchema~. Otherwise nothing runs and the model receives a structured result =\{ error: { code: "tool_not_on_menu" | "invalid_tool_input", message, issues? } }= (issues capped at 5, 200 chars each) so it can recover; the refusal is a pure function of the model output and the static menu and nothing is appended. *Replay:* an in-flight ~agentLoop$~ execution whose log (written before R4) recorded an off-menu or invalid-input call replays a refusal in its place, so its ~toolCallLog~ and later transcript diverge; drain in-flight ~agentLoop$~ executions before upgrading (~agentStep$~ / ~AgentRunner~ are single-step and unaffected). The gate sits after the ~requireApproval~ gate (moving it would break resume ordering); the policy receives ~onMenu~ as a third argument so a host can return =true= to skip prompting a human for a call that will be refused anyway. A tool with no ~inputSchema~ (untyped callers) is not input-validated. Validation is a SHAPE check, not sanitisation: unknown keys pass unless the schema is ~.strict()~, and transformed / coerced / preprocessed values are checked but the RAW input is what runs. Schemas used as tool inputs must be pure: an impure refinement makes refusals nondeterministic on replay. A schema fault (async or throwing refinement) or an input deeper than 64 levels / 100k nodes is a refusal (~invalid_tool_input~, fixed message), never a throw; echoed tool names and paths are capped at 200 chars. The converter omits what it cannot state without being tighter than the validator: ~default~ values, ~pattern~ for regexes with flags, a non-coercing ~z.date()~, bigint literals, recursive lazies past their first expansion; a non-object root is sent as a bare ={type: object}= (non-object tool inputs are validated but not described). *Third-party JSON Schema (R4b).* ~ToolDefinition.jsonInputSchema~ (set by ~@loom/plugin-mcp~ from the server's ~inputSchema~) is sent in place of the Zod-derived schema, after ~sanitizeJsonSchema~: keyword allowlist, depth 16 / 1000 nodes / 64KB, strings capped at 200, remote ~$ref~ dropped, cyclic or oversized refused (a bare ={type: object}= and a one-time ~LOOM_AGENT_TOOL_SCHEMA~ warning; the run continues). Its ~description~/~title~ text, and the tool's own description, are stripped (the description becomes the tool id) unless the operator opts in (~registerInto({ trustDescriptions: true })~ / ~trustJsonSchemaText~): they are instructions to a model and a plain string carries no taint for ~guardRequest~ to refuse (ADR 0085). Property names and ~enum~/~const~ strings remain. A call is shape-checked (~checkJsonSchemaShape~: object, ~required~, top-level property types); deeper validation is the server's. Exported: ~buildToolMenu~, ~toolInputJsonSchema~, ~toolSpecFor~, ~sanitizeJsonSchema~, ~checkJsonSchemaShape~, ~validateToolInput~.

The declaration is read from the result's ~_meta.ui~, then an inlined ~ui://~ content block, then
the tool's static ~tools/list~ declaration — decreasing authority. An *inlined* resource is
pinned for free; a declared-but-absent one costs an extra ~resources/read~ and is therefore
fetched only under ~registerMcpInvoke(..., { resolveUi: true })~. The four ~pin~ states exist

fails the dispatch — the tool call already succeeded and its side effect already happened.

Note the emit is a SEPARATE event rather than a field on ~MCP_DISPATCHED~: that one is emitted
*before* the call so a failed attempt stays indexed for proactive repair, and UI provenance is
only knowable *after* it.

**** Both meta forms, on both sides

The spec's form is the nested ~_meta.ui.resourceUri~ block, but the reference SDK's
~registerAppTool~ still emits the *deprecated flat* ~_meta["ui/resourceUri"]~ alongside it, so
hosts that never migrated keep working. A host reading only the flat key therefore sees *no UI
declaration at all* on a server that sends only the nested one, and silently falls back to
rendering text — spec-correct and invisible at the same time. So Loom **writes both on egress**
(~describeTool~) and **accepts either on ingress** (~uiMetaOf~): the nested block wins when the
two disagree, and the flat key is held to the same ~ui://~ scheme rule. Both forms go away when
the flat one is dropped before GA.

Two boundaries the server owns:

- *Audience.* The extension puts visibility enforcement on the *host* — the only party that
  knows whether a ~tools/call~ came from the model or a rendered View — so a server cannot
  derive it from the request. ~audienceOf~ is deployment-supplied (a distinct path, port, or
  credential) and defaults to ~"model"~: absent an explicit boundary, app-only tools stay
  unreachable rather than silently open. An audience-invisible tool is reported as *unknown*,
  not forbidden — a "you may not call that" reply confirms the tool exists.
- *Seam.* A View can call any tool the host proxies for it. Enrichment reads are harmless; a
  call that appends to the log is a state transition requested by the user's UI, so an
  app-originated call to a ~journaled~ tool is *denied by default*.

**** Reachability as a REMOTE connector

Two things a *hosted* client settles before it will talk to a server at all, both handled by the
transport:

- *OAuth discovery.* A remote host probes ~/.well-known/oauth-protected-resource~ (RFC 9728) and
  friends to learn whether it must authenticate. A server without OAuth answers *404* for the
  whole ~/.well-known/~ namespace, and answers it *above* the ~authorize~ gate — behind it, a
  401 would be equally undecidable ("authenticate, somehow", with no way to learn how) and the
  client gives up rather than falling back to connecting unauthenticated. ~GET~ on the MCP
  endpoint itself still returns 405, which is correct for a server offering no SSE stream.
- *Version negotiation.* ~initialize~ *negotiates* rather than asserting: a client that names a
  dated revision gets that same revision back, because this surface — initialize / tools /
  resources over JSON-RPC — is unchanged across every dated revision, so any well-formed version
  a client names is one the transport genuinely speaks. A client told a version it did not ask
  for is entitled to hang up. ~protocolVersion~ (the configured default) is the fallback only
  when the request names nothing usable — absent, ~"latest"~, or older than ~2024-11-05~.

Both are transport behaviour, not configuration: there is nothing to opt into. Neither is
theoretical — with them a tunnelled server completes the handshake from a hosted client; without
them it is unreachable no matter what it serves.

*Superseded is not failed (L20, ADR 0004 amendment).* ~isSupersededRefusal~ is true for an ~ExecutionAlreadyExistsError~, a ~StaleFenceError~ (bare or as a ~StorageWriteError~'s cause) or an ~ExecutionSupersededError~ — each only when it names THIS execution. A dispatcher MUST NOT retry it: every attempt fences, so the retry would fence the winner out and the two would ping-pong. It transfers ownership to the newer fence holder without checking that holder is alive, so a deployment MUST run ~recoverAbandoned~ to re-drive dead holders; a caller that needs the outcome awaits the execution by id. A start refused on the fence with sequence 0 still absent is ~StartFencedOutError~ (~@loom/workflow-runtime~) instead — its holder wrote nothing and may be dead, so it stays retryable.

Implementations: ~new LocalWorkerRuntime(runtime: WorkflowRuntime, { system? })~ (in-process; no system grant unless ~system~ is passed), ~new RemoteWorkerRuntime(baseUrl: string, { fetchImpl? })~ (HTTP → ~POST {baseUrl}/execute~).

*Fencing (2.0, K9.4).* On a fencing-capable store, every event a run appends carries its ~lease.fence~; once a re-dispatch acquires a newer token, the older lease's holder can no longer write — a partitioned "zombie" worker is fenced out at the store rather than double-writing. Absent on single-node SQLite (correlation only).
