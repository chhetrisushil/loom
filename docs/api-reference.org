* Authoring builders — ~@loom/core~
:PROPERTIES:
:CUSTOM_ID: authoring
:END:

Declarative ~$~ builders produce plain, serializable definition objects (each tagged with a ~_tag~). They have no runtime behavior on their own — the runtime interprets them.

** Definition & handler types

#+begin_src typescript
type EffectKind = "tool" | "llm" | "human" | "a2a" | (string & {});   // open (ADR 0115): any /^[a-z][a-z0-9._-]{0,63}$/; only "human" has kernel semantics (parks)

interface StepHandlerContext {
  executionId: string; stepId: string; workflowId: string; attempt: number;
  emit(eventType: string, payload: unknown): void;
}

type HandlerSpec<TIn, TOut> = HandlerRef<TIn, TOut> | HandlerLoader<TIn, TOut>;

interface RetryPolicy { maxAttempts: number; backoffMs?: number; backoffMultiplier?: number; }

interface StepDefinition<TIn, TOut> {
  readonly _tag: "StepDefinition"; id: string; name: string;
  toolId?: string; handler?: HandlerSpec<TIn, TOut>;
  inputSchema: ZodSchema<TIn>; outputSchema: ZodSchema<TOut>; retry?: RetryPolicy;
  timeoutMs?: number;    // (2.0, K8) bounds a single effect
  // K9 delivery semantics (`idempotent`) live on ToolDefinition / the registered Effect, not on the step
}
interface FlowDefinition<TIn, TOut> {
  readonly _tag: "FlowDefinition"; id: string; name: string; version: string; description?: string;
  inputSchema: ZodSchema<TIn>; outputSchema: ZodSchema<TOut>;
  steps: StepDefinition<any, any>[]; policies?: PolicyDefinition[];
  deadlineMs?: number;   // (2.0, K8.3) wall-clock deadline for a live run ⇒ kernel EXECUTION_CANCELLED
}
interface ToolDefinition<TIn, TOut> {
  readonly _tag: "ToolDefinition"; id: string; name: string; description: string;
  kind: EffectKind; inputSchema: ZodSchema<TIn>; outputSchema: ZodSchema<TOut>;
  jsonInputSchema?: Record<string, unknown>; // R4b — JSON Schema input (MCP); bounded + sanitised before a prompt
  trustJsonSchemaText?: boolean;     // R4b — operator vouches for its description/title text
  idempotent?: boolean;              // K9 delivery semantic
  errors?: Record<string, ZodSchema>;// ADR 0060 declared failure channels
  mode?: EffectMode;                 // ADR 0073 — which invocation seam (below)
}
// ADR 0073 — which side of the determinism boundary a tool may be invoked from.
//   "journaled" — runs inside an execution; result recorded and replay-substituted.
//   "ambient"   — an enrichment read (pagination, drill-down, a surface refetch) that
//                 must NEVER append to the log; runs only via invokeTransient.
// `execute` refuses an ambient effect; `invokeTransient` refuses a journaled one
// (EffectModeViolationError). Undeclared = today's behaviour on both seams (G2).
// A boundary CHECK, not a journaling mode: an ambient tool is not "an effect that
// skips its journal" — it may not enter an execution at all, so there remains
// exactly one replay model. Declaration lives here; the enforced copy is on the
// registered effect (`new ToolEffect(fn, { mode })`).
type EffectMode = "journaled" | "ambient";
interface AgentDefinition {
  readonly _tag: "AgentDefinition"; id: string; name: string; description?: string;
  tools: ToolDefinition[]; policies?: PolicyDefinition[]; memoryId?: string;
  version?: string; capabilities?: { streaming?: boolean }; skills?: AgentSkillDef[];
}
// Also: SkillDefinition, ProjectionDefinition, MemoryDefinition, PolicyDefinition, InstructionsRef/Spec/Loader.
#+end_src

*Reserved ~variables~ keys (2.0):* ~_decisions~ (logged ~ctx.decide~ choices, P9), ~_denials~
(capability ~EFFECT_DENIED~ audit, K2), ~_resources~ (metered totals
~{ tokens, costUsd, ms, count, exceeded? }~, K3), ~_blocked~ (behavioral-safety ~SAFETY_BLOCKED~
audit, K6), ~_indoubt~ (parked ~EFFECT_INDOUBT~ deliveries, K9), and ~_shredded~ (crypto-shred
~PAYLOAD_SHREDDED~ tombstones, K10). The full 13-key table is in the
[[file:loom-2.0/10-event-schema-reference.md][event-schema reference]].

** ~runAgentOnce~ (@loom/app)

Scripts and tests only; production runs ~agentLoop$~ in a registered flow on durable storage. Builds
a throwaway in-memory ~defineConfig~ app plus a one-off flow, runs ~agentLoop$~ to completion (or to
a park) and returns the result and the events. It goes through ~defineConfig~ (so ~config.security~
applies), registers the model as a ring effect, and rejects with ~agentLoop$~'s own error for a
config it refuses.

*Flow-code versioning for in-flight executions (2.0, K11).* Each flow carries a ~flowContentHash~
(structural fingerprint over step bindings + durable policies, emitted by ~@loom/compiler~ and
pinned into ~EXECUTION_STARTED~). A resume whose flow code no longer matches the pinned hash throws
~FlowCodeMismatchError~ rather than replaying against drifted code; ~resumeAs~ deliberately migrates
such a run — ~"replay-check"~ verifies every recorded step still exists in the new flow (refuses
with ~FlowMigrationCheckError~ otherwise), ~"operator-ack"~ vouches without the check. Either way it
records a durable, replay-deterministic ~EXECUTION_MIGRATED~ verdict.

*Body-aware fingerprint and divergence detection (ADR 0113, R7).* ~flowContentHash~ is SHA-256
(~sha256:~; a recorded legacy ~fnv1a:~ value is still accepted via ~flowHashMatches~).
~FlowDefinition.codeFingerprint~ (toolchain-supplied, optional) is recorded as
~EXECUTION_STARTED.codeHash~ and compared on resume: a different value throws
~FlowCodeMismatchError~ (~kind: "code"~) unless ~compatibleWith~ lists the recorded one.
~WorkflowRuntimeDeps.divergence~ / ~kernel.divergence~ (~"off" | "warn" | "fail"~, default ~warn~,
~fail~ under ~security.strict~) controls the replay-divergence detector, which raises
~FlowReplayDivergenceError~ (a ~FlowDivergenceError~) before a step's effect, a park, a continuation
or completion when a recorded completed step was never asked for; in ~fail~ mode the execution parks
on the reserved gate ~__loom_diverged__~ and ~retryDiverged(id)~ re-runs it.
~kernel.features.sha256FlowHash~ (default off) makes new starts record ~sha256:~ instead of
~fnv1a:~. ~"replay-check"~ treats ~base#…~ ids as family ~base~ and honours
~FlowDefinition.stepFamilies~.

*Durable timers (2.0, T1).* ~ctx.sleep~/~ctx.sleepUntil~ suspend the execution with the absolute
wake time recorded in the log; a wired ~TimerService~ fires a durable ~TIMER_FIRED~ resume, so a
sleep survives restarts and replays deterministically (the scheduled time is in the log — wall-clock
drift never enters the fold). Without a timer service the suspension is still durable and resumable
by any node. Declare cron-driven starts with ~schedule$~ (see [[#authoring][~@loom/core~ builders]])
and wire both via ~defineConfig({ timers })~.

*Recovering an abandoned execution ([[file:adr/0004-failure-recovery.md][ADR 0004]]).* A dead or
wedged *worker* is redispatched by the dispatcher (~executeTimeoutMs~) and resumes idempotently. A
dead *supervisor* is not covered — detection lives in its process — so
~recoverAbandoned(runtime, { source, isAbandoned })~ (~@loom/workflow-runtime~) enumerates
~running~/~pending~ executions and resumes the ones your predicate claims, via the same
~EXECUTION_RECOVERED~ resume the worker uses. A re-drive answers no gate
([[file:adr/0104-recovery-never-answers-a-gate.md][ADR 0104]]): the recovered flow parks at the next
~ctx.suspend~ it reaches until a resume names that gate. ~isAbandoned~ is REQUIRED: a running
execution on a healthy node is byte-identical in the log to an orphaned one, so only the deployment
can decide. Run it from a cron or Job, not as a service. A step failure the flow caught leaves the
execution ~running~, so it is recovered too
([[file:adr/0105-a-caught-step-failure-is-not-the-executions.md][ADR 0105]]); ~maxRecoveries~ skips
a claimed execution whose last N re-drives made no progress (consecutive ~EXECUTION_RECOVERED~
events since the last ~STEP_COMPLETED~ / ~EXECUTION_SUSPENDED~ / ~EXECUTION_RESUMED~; ≥ 1, default
unbounded) and reports it in ~summary.exhausted~ / ~onExhausted~, so a poison execution stops
costing every pass. ~reconcileTimers(runtime, { source, timers })~ re-arms the timer row of every
execution suspended on a ~wakeAt~ (idempotent — ~schedule~ dedupes); run it once after upgrading to
EVENT_SCHEMA 1.21.0, whose predecessor let ~TimerService~ retire the row of a timed park a parallel
sibling's failure had folded to ~failed~. A sealed-payload replay refusal
([[file:adr/0130-sealed-payload-delivery-guard.md][ADR 0130]] D10) leaves a refusal row (a
timer-store row carrying ~TimerRecord.refused: { head }~, no log append); a ~TimerService~ re-drives
that ~running~ execution on a node that can open it, but only on the sweep's own evidence (its
~isAbandoned~ option, or with ~leases~ an existing expired lease) and only while the log has not
moved since the refusal, through the same internal re-drive routine as ~recoverAbandoned~ and one
shared sealed back-off. ~isAbandoned~ on the poll carries the sweep's contract (a sweep-grade
predicate). With neither ~isAbandoned~ nor ~leases~ the poll cannot prove abandonment and fetches no
refusal rows (~due({ refused: false })~), and the sweep recovers.

*Start-once for a caller-chosen id
([[file:adr/0103-durable-bootstrap-for-caller-chosen-ids.md][ADR 0103]]).*
~start(flow, input, { executionId })~ makes the execution's ~EXECUTION_STARTED~ durable BEFORE the
flow body runs, so a duplicate start (a redelivered trigger, two nodes firing the same schedule
occurrence) rejects with ~ExecutionAlreadyExistsError~ and nothing runs — no effect, no fold, no
~onEvent~. Catch it to treat the duplicate as "already started"; there is no separate ~startOnce~.
Any other failure of that write rejects with ~StorageWriteError~ — including a start refused on the
fence twice with sequence 0 still absent, whose cause is ~StartFencedOutError~ (a newer token's
holder wrote nothing and may be dead, so the start stays retryable; L20). A minted ULID cannot
collide, so ~start~ without an ~executionId~ pays no extra write and is byte-identical to before.
~onEvent~ otherwise stays pre-durability for every later event: a consumer that must act only on
durable facts reads them back (the ADR 0058 catch-up shape).

*Durable placement (#392).* ~start(flow, input, { computeTarget })~ records the compute lane on the
execution's ~EXECUTION_STARTED~ anchor (envelope metadata — descriptive, never folded, so replay is
untouched), and ~placementOf(eventStore, executionId)~ (~@loom/workflow-runtime~) reads it back in
one point-read. ~TimerService~ and ~recoverAbandoned~ accept a ~dispatcher~ and re-drive to that
lane instead of resuming in-process; a fork inherits its parent's lane and
~fork(…, { computeTarget })~ overrides it. A HINT, not a pin: ~PlacementDispatcher~ falls back for
an unregistered target (and warns once), because a retired lane must not strand the executions that
named it.

*What is stuck, and is anything watching it.* ~orphanCensus(runtime, { source, leases?, buckets? })~
(~@loom/workflow-runtime~) is the READ-ONLY pass beside the acting ones: no predicate, no writes, no
policy — a predicate is what a census must not need, since the question it answers is whether YOURS
is right. It bands ~running~/~pending~ executions by age (cumulative, with a sample of ids) and,
given a lease store, classifies each as ~held~ / ~expired~ / ~none~. `none` is the one to watch: a
stuck execution nothing ever leased cannot be recovered from evidence at all. Clocks: lease expiry
is judged on ~options.now ?? leases.storeNow?.() ?? Date.now()~ (the store's own clock when it has
one), while execution ages use the wall clock or ~now~. ~LeaseStore.storeNow?()~ is optional since
SPI 2.1.0 and implemented by ~PostgresLeaseStore~ (DB time), so a census run from a skewed host
still judges leases on the clock that stamped them.

*Batch and steal (LeaseStore SPI 2.2.0, ADR 0130 D11).* ~LeaseStore~ gains the OPTIONAL
~acquireMany(ids, owner, ttlMs, now?, options?)~ (the leases granted; an id another owner holds is
absent), ~renewMany(ids, owner, ttlMs, now?)~ (returns the HELD set, the ids still owned after the
call, never its input, and never resurrects a released or taken lease) and
~releaseMany(ids, owner)~, and ~acquire~ (single id ONLY: ~acquireMany~ rejects ~steal~ with
~TypeError~, a fence belongs to one execution) takes ~{ steal: { fence } }~ (a positive integer; the
proof is shape-only, so pass a fence actually won, never an explicit ~now~ in production): a lease
another owner holds UNEXPIRED may be taken only with a conditional-fence proof (the fence won by
~acquireFenceIf~); any other ~steal~ value throws ~TypeError~ and changes nothing, and the displaced
owner's next renew reports it lost. ~InMemoryLeaseStore~, ~SqliteLeaseStore~ and
~PostgresLeaseStore~ implement all of it (Postgres: one multi-row statement per call, ~ANY($ids)~,
database clock, and ~fillfactor~ / autovacuum options on the ~leases~ table); the kit runs the batch
cases for a store that implements any batch method (then all three are required) and forces them
with ~spiVersion: "2.2.0"~, so a 2.1.0-shaped store passes with no options. ~sqliteStorage()~ and
~postgresStorage()~ return a co-located ~leaseStore~ next to ~eventStore~ (accessor only, lazy and
closed with the event store on SQLite; ~defineConfig~ does not read it yet).

*Heartbeat lease keeper (ADR 0130 D11 S7b/S7c; wired into every driver through
~WorkflowRuntimeDeps.heartbeat~ ={ leaseStore, ttlMs?, renewEveryMs?, onStoreError?, nodeId? }=
(~HeartbeatOptions~, with ~acquire?: "eager" | "lazy"~ (default lazy) and ~lazyGraceMs?~): ~start~,
~resume~, ~resumeAs~, ~restoreFromState~, the ~send~/notify winner, a continue-as-new successor and
~LocalWorkerRuntime~ take a lease BEFORE the fence (eagerly, except that a fresh ~start~ is lazy by
default) and release it awaited at the suspend/terminal commit; another live owner =
~LeaseHeldError~ (stand down, no fence); a lost lease aborts the run with ~LeaseLostError~, appends
nothing and gates every dispatch and append; ~runtime.leaseKeeper~,
~runtime.acquireDriverLease(id)~, ~runtime.closeHeartbeat()~).*
~new LeaseKeeper({ store, nodeId, ttlMs?, renewEveryMs?, onLost, ... })~ (~@loom/workflow-runtime~)
is the one-per-node form of ~renewWhileHeld~: ~acquire(id)~ / ~release(id)~ are group-committed, one
batched renew runs per tick (~renewMany~ when the store has it, single-id calls otherwise),
~validNow(id)~ is the no-I/O gate (a local monotonic deadline of ~lastRenewSent + ttl - ttl/6~), and
~onLost(id, LeaseLostError)~ fires on a renew that no longer holds the id or when the deadline
passes with no confirmed renewal. A store error opens a one-TTL quiet period
(~LeaseStoreQuietError~); every acquire/release store call is bounded by ~storeTimeoutMs~ (default
~min(ttl/6, 1000)~ ms, ~LeaseStoreTimeoutError~). A caller-chosen ~start~ that finds a lease but no
sequence 0 (a ghost) rejects with the retryable ~StartLeaseHeldError~. ~onStoreError: "continue"~
(S7d) lets drivers run through a lease-store outage (no deadline abort; a taken-over lease still
stops them; a new driver whose acquire hits the outage runs unleased) and marks the keeper's owner
with ~HEURISTIC_OWNER_SUFFIX~ (~isHeuristicOwner(owner)~), so its expired leases are never evidence
on any node. *Lease consumers (S7d):* an unexpired lease vetoes ~isAbandoned~ on the poll and on
~recoverAbandoned~; with heartbeat on in stop mode over a cluster-visible store the ~TimerService~
refusal re-drive runs by default on an expired lease (an absent lease is never evidence);
the internal ~redriveAbandoned~ (not exported) takes ~{ conditional: true }~ (the runtime's internal ~claimRecovery~ appends the
~EXECUTION_RECOVERED~ marker with ~appendIfUnchanged~ before the fence; ~RunOptions.recoveryClaimed~
stops the resume from writing a second); ~collectGhostLeases(runtime, { limit? })~ deletes expired
leases that have no stream (the poll runs it, bounded, once per TTL); a lease-store read error fails
closed as ~LeaseEvidenceError~ (a one-TTL quiet period follows recovery).

*Retiring an abandoned branch.* Retention never reclaims an execution while a live descendant branch
still has events (R5.3) — and a branch nobody answered is suspended forever, so a forked parent
returns ~blocked-by-branch~ on every sweep, permanently.
~retireAbandonedBranches(runtime, registry, parentId, { isAbandoned })~ (~@loom/workflow-runtime~)
walks that parent's direct children, offers the non-terminal ones to your predicate, and calls ~cancel()~ on
the ones it claims — a durable ~EXECUTION_CANCELLED~, not a deletion, so *why* the branch ended
survives. Ordinary retention then collects the branch on its own TTL and the parent behind it.
~isAbandoned~ is REQUIRED, for the same reason ~recoverAbandoned~'s is: a branch parked on a human
gate is someone's open question, not garbage. The summary reports what it left alone.

*Fail-closed execution authorization (R3, 1P half).* ~executionAuthorizer~ gates
~start~/~resume~/~cancel~/~loadState~, but only for a call that carries a ~principal~: a call with
none skipped it, so an edge that forgot to attach one was wide open.
~WorkflowRuntimeDeps.executionAuthz: { requirePrincipal: true }~ (set by ~security.strict~;
~strict: { requirePrincipal: false }~ opts out) makes the authorizer see the principal-less request
(~principal: undefined~) so the policy decides. Off (default) is byte-identical. The kernel's own
principal-less machinery — ~TimerService~ (wakes, schedule starts), ~recoverAbandoned~,
~retireAbandonedBranches~, the ~superviseChildren~ child start and parent resume — presents
~runtime.systemOptions()~ (~{ system }~, or ~{}~ when the mode is off): an identity-compared
per-instance grant, not a principal, never recorded and never reaching an effect's authorization. A
clone, JSON copy or another runtime's grant is refused. It is an in-process capability: never hand
it to request-derived code. Observers that read state (~orphanCensus~, ~reconcileTimers~,
~liveQuery~) take ~runtime.systemStateReader()~. ~executionAccessPolicy(options)~

(~"owner" | "tenant" | "any" | "deny"~; defaults ~start: "any"~, the rest ~"tenant"~),
~allowWorkflows~, ~requireTenant~, ~allowAnonymous~ (default false), ~resolveOwner~ (legacy logs
only), ~unknownOwner~, the op ~actAsOwner~ (default deny) and the op ~send~ (default ~"tenant"~:

~EXECUTION_STARTED~ and hands the owner to the policy as ~ExecutionAuthzRequest.owner~ (read from
sequence 0), so there is no in-process owner table (~ownerOf~ / ~adopt~ / ~maxTracked~ are gone) and

*Retention and compaction of an encrypted log (ADR 0022 Amendment).* ~LogLifecycle.compact~ throws
~UnsafeCompactionError~ when the event store encrypts at rest (exposes ~keys~) and the snapshot
store does not share that same KeyStore — the checkpoint is the DECRYPTED fold, so a plaintext one
would survive a key shred. ~applyRetention~ / ~evaluate~ return ~"unsafe-archive"~ (a
~RetentionOutcome~) when a configured archive does not share the source's keys. Both refuse before
anything is read, copied or truncated. A compacted execution is judged on its snapshot plus the
surviving suffix, so it is reclaimable.

*Snapshot pruning (ADR 0134, off by default).* ~LogLifecycle.pruneSnapshots(executionId, { keepLatest?, keepSequences? })~
deletes superseded snapshots in one statement (~SnapshotStore.pruneSnapshots~, SPI 1.2.0) and resolves with the
count. It never prunes the latest ~keepLatest~ (default 1), a compacted log's checkpoint and everything at or
below it, a log compacted through its tip (~[0]~), a ~compactionExempt~ execution, or ~keepSequences~; so every
fork point and every fold is unchanged (a fork may fold more events). The runtime never calls it on its own.
~{ dryRun: true }~ resolves with the count a real call would delete and deletes nothing, through the same
selection code; it needs the optional ~SnapshotStore.listSequences~ (SPI 1.3.0, the ADR 0134 amendment) and
over a store without it refuses with ~SnapshotListingUnsupportedError~ (an exact count or none). ~{ policy }~
(ADR 0145, a ~retentionPolicy()~ value) supplies ~keepLatest~ from ~policy.snapshots~; an explicit ~keepLatest~ wins.

*Compaction archives what it removes (ADR 0138, ~ARCHIVE_STORE_SPI_VERSION~ 1.1.0).* ~LogLifecycle.compact~ appends the exact
envelopes it removes to an ~ArchiveStore~, THEN saves the checkpoint, THEN truncates (a crash leaves a duplicate, never a gap), and
REFUSES with ~CompactionArchiveRequiredError~ when none is configured (~PlaintextArchiveError~ when the log seals and the archive
does not seal under the SAME KeyStore). ~defineConfig~ supplies an archive for ~kind: "memory"~, ~sqliteStorage()~ and
~postgresStorage()~; a durable custom storage sets ~storage.archiveStore~ or ~durability.retention.compactionArchive~
(~durability.retention.tenant~ makes ~compact~ refuse unless the event store and the archive are visibly scoped to that tenant).
~readRange~, replay, resume and every sweep never read the archive.

*Compaction integrity (ADR 0106).* The checkpoint is named for its execution (a blank one used to
send every event a later resume appended to execution ~""~), a log compacted before is folded ON its
checkpoint (~CompactionCheckpointMissingError~ when that checkpoint is gone, nothing touched), and
~new LogLifecycle(events, snapshots, { pinnedEventTypes })~ keeps the app's pinned-kind events in
place through compaction (~EventStore.truncatePrefixKeeping~, SPI 1.5.0). A store without that
method can never compact past the first kept event, and ~onWarn~ says so. Compaction never removes
the tip when it keeps events, so a checkpoint is always the log's highest missing sequence (the tip
rule). Every kernel-written kind and every non-string is refused in ~pinnedEventTypes~. ~compact~
consults the ~pinned~ predicate only when ~pinnedEventTypes~ is empty (then a pinned execution is
left uncompacted); with kinds declared, a pinned execution compacts around them. ~compactionExempt~
(consulted always) keeps a whole log uncompacted. ~pinByEventTypes: true~ (also ~durability.retention.pinByEventTypes~)
makes ~evaluate~ / ~applyRetention~ pin an execution whose log holds one of ~pinnedEventTypes~, so the kinds are declared
once instead of again in a ~pinByEventKinds~ predicate (ORed with ~pinned~; off by default; ~true~ with no kinds throws);
~lifecycle.pinnedEventTypes~ is the read-only getter for the configured kinds. ~compact~ refuses reserved control streams.
~shredSubject~ places its tombstone after the folded tip (pass a ~snapshotStore~, raw or the app's
encrypting one, tenant-scoped or not; required on a compactable store) and is retry-safe, and
~EraseCoordinator~ takes a ~snapshotStore~ so a compacted terminal execution is not read as live. A
snapshot whose non-blank identity names another execution is refused
(~SnapshotIdentityMismatchError~); a blank one is filled. ~reconstructAt~ refuses a position inside
compacted history (~CompactedHistoryError~). ~fork~ of a compacted parent is served exactly — every
event between the nearest snapshot and the fork point survives, or a snapshot sits exactly at it (a
~[0]~ log's checkpoint is forkable: the range is the folded tip) — or refused with
~CompactedForkPointError~ (~reason~, ~forkableFrom~..~forkableThrough~) and nothing written
([[file:adr/0107-compacted-fork-points-and-the-blank-stream.md][ADR 0107]]).
~LogLifecycle.blankStreamCensus()~ / ~rehomeBlankStream({ apply, assign })~
(~loom repair blank-stream~) re-home the events the pre-0106 bug wrote to execution ~""~ where a
snapshot proves their owner (one batch per execution, under a new fence when the execution is
fenced; ~failed~ lists what moved since the census), journal ~EVENTS_REHOMED~, and list the rest
with candidates rather than guess; ~""~ is reserved (~isReservedStream("")~).

*Holding a topic whose head is sealed ([[file:adr/0130-sealed-payload-delivery-guard.md][ADR 0130]]
residuals D9).* ~runtime.quarantineInbox(executionId, { topic, reason? }, { principal })~ (op
~quarantine~) and ~runtime.releaseInbox(executionId, { topic, messageId, sender?, disposition? }, {
principal })~ (op ~release~, or ~discard~ for ~disposition: "discard"~) are the operator verbs of
the per-topic hold. Both default to ~"deny"~ in ~executionAccessPolicy~ like ~discard~, REQUIRE a
~principal~ (refused with ~ExecutionDeniedError~ before anything is read), and refuse with
~InboxQuarantineRefusedError~ (~reason~: ~not-parked~ | ~contended~ | ~invalid~ | ~not-sealed~ |
~checkpoint-unreadable-log-compacted~, ~verb~: ~quarantineInbox~ | ~releaseInbox~ | ~fork~) with
nothing appended. ~quarantineInbox~ copies the topic's sealed head into the reserved
~__loom_quarantine__:<chainId>~ stream FIRST (deterministic id
~quarantine:<chainId>:<key>:<inboxSeq>~; sequence 0 of that stream is a payload-free anchor), then
journals ~INBOX_QUARANTINED~ under the park's conditional fence; the topic is then held for every
node, in original order, and a node that can open the copy releases it by itself
(~INBOX_RELEASED { auto: true }~ + ~MESSAGE_CONSUMED~ at the original ~inboxSeq~ in ONE batch;
~WorkflowRuntimeDeps.inboxAutoRelease~ / ~kernel.inbox.autoRelease~, default ~true~).
~WorkflowRuntimeDeps.inboxQuarantineMax~ / ~kernel.inbox.quarantineMax~ (default 256, ceiling 1024)
bounds the held copies per chain; ~runtime.inboxAutoReleaseOn~ / ~runtime.inboxQuarantineLimit~
report the node's settings. On a node that cannot open the owner's SEALED checkpoint the two verbs
(only they) fold the owner from the complete log; a compacted log is
~checkpoint-unreadable-log-compacted~ (run the verb on a capable node). That log is read PAST a seal
whose ~covers~ lists only ~MESSAGE_CONSUMED.payload[.…]~ (an opaque ciphertext value the fold copies
and never interprets; never decrypted, no key asked); any other covered field is still the ordinary
denial. The state so folded is transient: used to decide the verb, never journaled, returned, cached
or snapshotted. A held topic no node here can open is reported as ~QuarantineHeldError~ (a
~SealedPayloadUnreadableError~). Types: ~QuarantineInboxInput/Options/Result~,
~ReleaseInboxInput/Options/Result~.

*Collecting the registry.* After retention reclaims a branch, two rows outlive it. ~LogLifecycle~
forgets the fork edge as it deletes the execution (optional ~removeLineage~ — dead edges otherwise
make every future sweep walk them).
~pruneBranchRefs(eventStore, registry, { pageSize?, limit?, protect? })~ (~@loom/workflow-runtime~)

by default and reported as dangling instead.

*~onDurableEvent~ (ADR 0147).* ~WorkflowRuntimeDeps.onDurableEvent~ is called with an event after its durable write has resolved, so it NEVER reports an event the log does not hold
(a lost, rejected or fenced write is not delivered). At most once: a process that dies after a write, or a lost acknowledgement, never delivers it, so read the log when you need every event.
In order per writer, not per execution: under a delayed acknowledgement a later sequence can arrive first, so order by ~sequence~. Asynchronous: it lags the fold and a slow store builds a backlog;
an async consumer is not awaited. Only this runtime's writes: another process, ~LogLifecycle~ and crypto-shredding are not reported. A throw or rejection goes to ~onWarn~ (at most once a minute) and
never reaches the run. Unset, the write path does no extra work. ~onEvent~, by contrast, fires BEFORE the durable write.

*Writing a store decorator (ADR 0074 Amendment).* A decorator must decide EVERY optional SPI method:
forward it, override it, or refuse it with a reason. One that silently drops a method takes the
capability away from everything above it — four in-repo decorators dropped ~appendBatch~, so
~Coalescing(TenantScoped(backend))~ never batched. ~installOptional~ installs a plan whose type maps
the whole optional union to REQUIRED keys, so a plan that omits a method (including a future one)
does not compile — the kit catches a decorator that uses no plan at all; each method is installed
only when the inner store has it (capability probes unchanged), refusals are recorded, and the
structural encryption marker (~keys~) is carried up so ~LogLifecycle~'s key rule and ~loom doctor~
still see an encrypting store below. ~runEventStoreDecoratorConformance~ (~@loom/conformance~) is
the check.

** ~@loom/plugin-audit-chain~ — a tamper-evident, third-party verifiable log

Hash-chains every event into its ~metadata~, which the fold ignores — so replay is byte-identical whether or not it is wired, and any later edit, insert, reorder or drop is detectable out of band.

*Who can check it (#382).* An ~hmacSecret~ makes the log tamper-EVIDENT: verification needs the same
secret, so anyone able to check it could also re-chain and re-sign it. A ~signer~ makes it
third-party VERIFIABLE — an auditor holds only ~verifier~ and cannot author an entry. The two are
mutually exclusive (different promises), ~keyId~ keeps history verifiable across rotation, an
unknown key is rejected rather than skipped, and ~signaturesChecked~ says whether authorship was
checked at all so a hash-only pass cannot be over-read.

*Identity, tenancy & delegated authority (2.0, K12).* A ~CapabilityRequest~ can carry a
~PrincipalChain~ (tenant / actor / on-behalf-of / a verifiable delegation). ~DelegationAuthorizer~
honors a *signed, attenuated* delegation only after verifying its HMAC and intersecting its grants
with the callee's own authority (~base~, required) — a delegate can never invoke an effect the
delegator lacked, nor one the callee lacks (no ambient escalation). Attenuation only narrows. The
HMAC secret is *symmetric*, so the signature stops a third party forging a grant set in transit but
cannot stop the verifier minting its own; the intersection is what bounds the callee.
Cross-organisation delegation is out of scope — see
[[file:adr/0024-k12-identity-tenancy-delegated-authority.md][ADR 0024]].

** ~@loom/plugin-crypto~ — encryption-at-rest & crypto-shredding (K10)

Wraps any ~EventStore~/~SnapshotStore~ to encrypt *marked* payload fields (dot-paths per event type)
under a per-subject key on append and decrypt on read (AES-256-GCM; unmarked events stored verbatim
— zero overhead). Erasure is by key destruction: ~shredSubject~ destroys the key (irreversible for
everything encrypted under it, in events *and* snapshots) and appends a durable ~PAYLOAD_SHREDDED~
tombstone. A later decrypting read of a shredded execution throws ~PayloadShreddedError~ — replay
fails *loudly*, never silently diverges. Optional store capabilities (fencing, ~readRange~,
~copyPrefix~) are forwarded, so it composes with K9.4 and ~fork()~.

** ~@loom/plugin-a2ui~ — A2UI (Agent-to-UI) adapter

Projects a Loom agent surface onto the *real* Google [[https://a2ui.org][A2UI]] wire
protocol v1.0, so any A2UI-compliant client can render a Loom-driven UI. A **1P plugin**,
kernel untouched (ADR 0069, ADR 0070). Covers **egress**, the inbound ~action~ leg, and
the **~callFunction~ bidirectional RPC** (the agent invokes a named client function and
receives a ~functionResponse~). Only continuous two-way *binding sync* remains out of
scope.

The bridge folds ~SURFACE_PATCH~ events locally and translates Loom's *delta* ops into
A2UI's *absolute* ~updateDataModel~ value-replacement (A2UI has no patch framework);
~remove~ → ~contents: null~. K10-R6 egress redaction is applied on the way out.

~callFunction~ is reconciled with Loom's append-only replay grain **not** as a blocking
sync RPC in the log, but by the client's *result* re-entering as an ordinary recorded fact
— a resume event (grain A) or a ~STEP_COMPLETED~ output (grain B). No client-side effect
runtime is needed; determinism rests on **result-as-recorded-fact + a deterministic
~callId~**. No new event types; ~EVENT_SCHEMA~/~KERNEL_ABI~ unchanged (ADR 0070).

The catalogue named by ~catalogId~ is an enforced claim, not a label
([[file:adr/0088-blueprint-conformance.md][ADR 0088]] D5, amended): the constructor and
~recompose~ both throw for a component tree the supplied ~catalog~ does not cover (structural
checks below), and ~callFunction~ throws for a name the catalogue does not declare under
~functions~ — a catalogue declaring none refuses every call rather than allowing one
unverifiably. Naming ~catalogId~ without supplying ~catalog~ is refused outright (unless it is
the default, which ~defaultCatalog~ backs) — the bridge would otherwise stamp an id it cannot
check a single component against.

*** Pin the template

~surfaceHostPin()~ delegates to ~@loom/plugin-mcp~'s ~hashResourceBody~ — the *same* function the
ingress side applies to a fetched resource, so a pin captured at plan time equals what a reader
recomputes. Two hashing implementations that mostly agree is how a pin stops detecting the drift
it exists to detect ([[file:adr/0063-mcp-dynamic-dispatch.md][ADR 0063]] D1).

*** Redaction is required, not defaulted

~redact~ has no default. The payload crosses the trust boundary into a rendered iframe, and a
list that quietly defaults to empty is a silent leak — "we forgot to configure it" would look
identical to "there is nothing to mask". Pass ~[]~ to assert explicitly that nothing needs it.
Masking happens on egress only; the fold keeps true values so ~increment~/~append~/~merge~ stay
correct.

*** No server push — the View polls its own cursor

The extension has no server→View channel after ~ui/notifications/tool-result~. The only seam it
offers is repeatable view-initiated ~tools/call~, so the template polls ~loom_surface_since~.
This is polling and it is worse than SSE — the extension's limitation, contained behind one
tool. A cursor read returns either ~{ changed: false }~ or a *complete* model, never a delta: a
tail fold is a partial state that only looks like one (a nested patch yields ~{a:{b:1}}~, which a
shallow merge splices over all of ~a~, and a ~remove~ is indistinguishable from untouched). The
cheap tail read is kept purely for change detection.

*** Staleness across a long suspension

~resume()~ already refuses stale *code* (K11), stale *input* (K11.5), forged *approvals* (K12.2)
and post-cancel resume (K8.2). What it cannot know is which version of the data a human was
looking at: the execution knows when *it* suspended, not what the user saw. So the View echoes
~seenSequence~ on every action and ~isStale~ is the predicate — *evidence, not policy*. Whether
a lag invalidates a decision is domain-specific; express it as an [[file:adr/0060-typed-failure-channels.md][ADR 0060]] ~staleDecision~
channel so it is recorded, replay-substituted, and branchable into re-confirmation.

Absent provenance counts as **stale**: an action with no ~seenSequence~ is indistinguishable
from one made against arbitrarily old data.

The verdict is computed at the *trust boundary*, not in the flow. `seenSequence` is a claim by an
untrusted client, and the head sequence it must be judged against is a property of the LOG — which
the tool handler owns and `ctx` does not expose. So the handler decides *stale or not* and the flow
decides *what that means*:

#+begin_src typescript
// In the approve tool's handler — evidence:

  eventType: "TaskApproved",

});

// In the flow, at the gate — policy:

if (signal.stale) {
  // This gate refuses; another flow could legitimately accept. Declare
  // `staleDecision` on the step to make it a recorded, branchable outcome.
  surface(ctx).set("status", "re-review");
}

*Tool menu (every loop: ~AgentRunner~, ~agentStep$~, ~agentLoop$~).* The model sees each tool's real
argument structure: ~LlmToolSpec.inputSchema~ is the JSON Schema of the tool's Zod ~inputSchema~
(~toolInputJsonSchema~; a hand-written converter that degrades to ={}= for what it cannot express).
A tool call the model returns is executed only if its name is on the agent's menu (the definition's
tools plus the selected skills' tools) AND its input passes the tool's ~inputSchema~. Otherwise
nothing runs and the model receives a structured result
=\{ error: { code: "tool_not_on_menu" | "invalid_tool_input", message, issues? } }= (issues capped
at 5, 200 chars each) so it can recover; the refusal is a pure function of the model output and the
static menu and nothing is appended. *Replay:* an in-flight ~agentLoop$~ execution whose log
(written before R4) recorded an off-menu or invalid-input call replays a refusal in its place, so
its ~toolCallLog~ and later transcript diverge; drain in-flight ~agentLoop$~ executions before
upgrading (~agentStep$~ / ~AgentRunner~ are single-step and unaffected). The gate sits after the
~needsApproval~ gate (moving it would break resume ordering); the policy receives ~onMenu~ as a
third argument so a host can return =false= (or, on the deprecated ~requireApproval~, =true=) to
skip prompting a human for a call that will be refused anyway. A tool with no ~inputSchema~ (untyped
callers) is not input-validated. Validation is a SHAPE check, not sanitisation: unknown keys pass
unless the schema is ~.strict()~, and transformed / coerced / preprocessed values are checked but
the RAW input is what runs. Schemas used as tool inputs must be pure: an impure refinement makes
refusals nondeterministic on replay. A schema fault (async or throwing refinement) or an input
deeper than 64 levels / 100k nodes is a refusal (~invalid_tool_input~, fixed message), never a
throw; echoed tool names and paths are capped at 200 chars. The converter omits what it cannot state
without being tighter than the validator: ~default~ values, ~pattern~ for regexes with flags, a
non-coercing ~z.date()~, bigint literals, recursive lazies past their first expansion; a non-object
root is sent as a bare ={type: object}= (non-object tool inputs are validated but not described).
*Third-party JSON Schema (R4b).* ~ToolDefinition.jsonInputSchema~ (set by ~@loom/plugin-mcp~ from
the server's ~inputSchema~) is sent in place of the Zod-derived schema, after ~sanitizeJsonSchema~:
keyword allowlist, depth 16 / 1000 nodes / 64KB, remote ~$ref~ dropped, cyclic or oversized refused
(a bare ={type: object}= and a ~LOOM_AGENT_TOOL_SCHEMA~ warning per tool; the run continues). The
text that remains is constrained, not just capped: property and ~$defs~ keys must match
~^[A-Za-z0-9_.-]{1,64}$~ (else the entry is dropped), ~enum~/~const~ strings are at most 64 chars
without control/zero-width/bidi characters, ~format~ is from the standard list, ~pattern~ must
compile, a ~$ref~ must name a kept ~$defs~ entry, and a 4096-character total budget refuses the
whole schema. ~description~/~title~ text, and the tool's own description (replaced by a fixed
"Third-party tool; description withheld"), are stripped unless the operator opts in
(~registerInto({ trustDescriptions: true })~ / ~trustJsonSchemaText~, capped at 1000 chars, warns
once per tool): they are instructions to a model and a plain string carries no taint for
~guardRequest~ to refuse (ADR 0085). ~@loom/plugin-mcp~ skips tools whose name is not
~^[A-Za-z0-9_-]{1,64}$~. An MCP tool shape-checks its own call (object, ~required~, top-level
property types) INSIDE its effect and returns the refusal as the recorded result, so replay never
re-evaluates a live schema; deeper validation is the server's. Exported: ~buildToolMenu~,
~toolInputJsonSchema~, ~toolSpecFor~, ~sanitizeJsonSchema~, ~validateToolInput~.

**** Observable from the log, not just from the client

A dispatch whose result declares a UI emits ~MCP_UI_OBSERVED~ — a userspace domain event the
fold skips, like ~MCP_DISPATCHED~ — so the declaration reaches the *log* rather than only the
client API:

The declaration is read from the result's ~_meta.ui~, then an inlined ~ui://~ content block, then
the tool's static ~tools/list~ declaration — decreasing authority. An *inlined* resource is
pinned for free; a declared-but-absent one costs an extra ~resources/read~ and is therefore
fetched only under ~registerMcpInvoke(..., { resolveUi: true })~. The four ~pin~ states exist
because "no ~contentHash~" would otherwise be ambiguous between *not asked for* and *asked for
and unavailable*, and a pin is a correctness device. A resource that cannot be fetched never
fails the dispatch — the tool call already succeeded and its side effect already happened.

Note the emit is a SEPARATE event rather than a field on ~MCP_DISPATCHED~: that one is emitted
*before* the call so a failed attempt stays indexed for proactive repair, and UI provenance is
only knowable *after* it.

**** Both meta forms, on both sides

The spec's form is the nested ~_meta.ui.resourceUri~ block, but the reference SDK's
~registerAppTool~ still emits the *deprecated flat* ~_meta["ui/resourceUri"]~ alongside it, so
hosts that never migrated keep working. A host reading only the flat key therefore sees *no UI
declaration at all* on a server that sends only the nested one, and silently falls back to
rendering text — spec-correct and invisible at the same time. So Loom **writes both on egress**
(~describeTool~) and **accepts either on ingress** (~uiMetaOf~): the nested block wins when the
two disagree, and the flat key is held to the same ~ui://~ scheme rule. Both forms go away when
the flat one is dropped before GA.

Two boundaries the server owns:

- *Audience.* The extension puts visibility enforcement on the *host* — the only party that
  knows whether a ~tools/call~ came from the model or a rendered View — so a server cannot
  derive it from the request. ~audienceOf~ is deployment-supplied (a distinct path, port, or
  credential) and defaults to ~"model"~: absent an explicit boundary, app-only tools stay
  unreachable rather than silently open. An audience-invisible tool is reported as *unknown*,
  not forbidden — a "you may not call that" reply confirms the tool exists.
- *Seam.* A View can call any tool the host proxies for it. Enrichment reads are harmless; a
  call that appends to the log is a state transition requested by the user's UI, so an
  app-originated call to a ~journaled~ tool is *denied by default*.

**** Reachability as a REMOTE connector

Two things a *hosted* client settles before it will talk to a server at all, both handled by the
transport:

- *OAuth discovery.* A remote host probes ~/.well-known/oauth-protected-resource~ (RFC 9728) and
  friends to learn whether it must authenticate. A server without OAuth answers *404* for the
  whole ~/.well-known/~ namespace, and answers it *above* the ~authorize~ gate — behind it, a
  401 would be equally undecidable ("authenticate, somehow", with no way to learn how) and the
  client gives up rather than falling back to connecting unauthenticated. ~GET~ on the MCP
  endpoint itself still returns 405, which is correct for a server offering no SSE stream.
- *Version negotiation.* ~initialize~ *negotiates* rather than asserting: a client that names a
  dated revision gets that same revision back, because this surface — initialize / tools /
  resources over JSON-RPC — is unchanged across every dated revision, so any well-formed version
  a client names is one the transport genuinely speaks. A client told a version it did not ask
  for is entitled to hang up. ~protocolVersion~ (the configured default) is the fallback only
  when the request names nothing usable — absent, ~"latest"~, or older than ~2024-11-05~.

Both are transport behaviour, not configuration: there is nothing to opt into. Neither is
theoretical — with them a tunnelled server completes the handshake from a hosted client; without
them it is unreachable no matter what it serves.

*Superseded is not failed (L20, ADR 0004 amendment).* ~isSupersededRefusal~ is true for an
~ExecutionAlreadyExistsError~, a ~StaleFenceError~ (bare or as a ~StorageWriteError~'s cause) or an
~ExecutionSupersededError~ — each only when it names THIS execution. A dispatcher MUST NOT retry it:
every attempt fences, so the retry would fence the winner out and the two would ping-pong. It
transfers ownership to the newer fence holder without checking that holder is alive, so a deployment
MUST run ~recoverAbandoned~ to re-drive dead holders; a caller that needs the outcome awaits the
execution by id. A start refused on the fence with sequence 0 still absent is ~StartFencedOutError~
(~@loom/workflow-runtime~) instead — its holder wrote nothing and may be dead, so it stays
retryable.

Implementations: ~new LocalWorkerRuntime(runtime: WorkflowRuntime, { system? })~ (in-process; no system grant unless ~system~ is passed), ~new RemoteWorkerRuntime(baseUrl: string, { fetchImpl? })~ (HTTP → ~POST {baseUrl}/execute~).

*Fencing (2.0, K9.4).* On a fencing-capable store, every event a run appends carries its ~lease.fence~; once a re-dispatch acquires a newer token, the older lease's holder can no longer write — a partitioned "zombie" worker is fenced out at the store rather than double-writing. Absent on single-node SQLite (correlation only).

copy of the command table is a second thing to forget. Broad strokes:

| Group                    | Commands                                                        |
|--------------------------+-----------------------------------------------------------------|
| scaffold & wire          | ~gen~, ~new~, ~appgen~                                           |
| validate before you run  | ~doctor~, ~check~, ~verify~, ~lint claim-check~                  |
| observe / analyze a run  | ~logs~, ~debug~, ~inspect~, ~profile~, ~introspect~, ~optimize~  |
| learn from the log       | ~learn report~, ~learn eval~                                     |
| ship safely              | ~eval~, ~deploy check~, ~compat~, ~kernel-manifest~              |
| data protection          | ~retention run~, ~sweep content~, ~compliance report~            |
| author a plugin          | ~plugin seams~ / ~new~ / ~check~ / ~try~ / ~search~              |
| list / triage executions | ~ls~ (~--waiting-on <event>~ filters suspended runs by the gate they wait on), ~census~ (what is stuck, and is anything watching it), ~snapshot show~ (a stored snapshot, decoded) |
| act through your runtime (dry run unless ~--apply~) | ~start~, ~resume~, ~cancel~, ~recover~, ~branches retire~ / ~branches prune~, ~repair blank-stream~ / ~repair terminal-event~ |
| knowledge corpus         | ~knowledge sync~ / ~list~ / ~search~                            |
| dev loop & config        | ~dev~ (gen --watch + run the app + the inspector), ~migrate-config~ (flat ~defineConfig~ options into their groups) |

Every command has a pure, testable core exported from ~@loom/cli~: ~foldAt(events, sequence?)~, ~formatLog(events, redact?)~, ~describeState(state, redact?)~, ~evaluateGoldens(goldens)~, ~buildTrace(events)~, ~checkManifest(manifest)~, ~discoverFlows(dir, skipped?)~ / ~cmdGen(dir, root?)~ / ~cmdNew(kind, name, dir, template?, root?)~, ~loadLogs(dir)~ / ~runDeployCheck(logs, resolver)~, ~serveInspector(eventStore, { port?, host? })~, ~parseArgs(argv)~.
