#+title: Loom Framework — Architecture
#+author: Sushil Chhetri

* Overview

Loom is a TypeScript framework for durable, event-sourced AI workflows. Its central design goal is that a workflow function can be interrupted at any point (to wait for a tool call, an LLM response, or a human decision), survive a process restart, and resume from exactly where it left off — without the application code knowing the difference between a fresh run and a replay.

Four ideas underpin the whole system:

1. *Event sourcing* — every state change is an immutable ~EventEnvelope~ appended to an ordered log. State is always derived by replaying that log, never mutated in place.
2. *Deterministic replay* — on resume, the ~ReplayVM~ fast-forwards through historical events so that previously-completed steps return their cached outputs instead of re-executing.
3. *Blueprint-driven UI* — the running workflow emits domain events; ~ProjectionRuntime~ folds those events into view models; the React renderer turns a JSON-serializable ~Blueprint~ into live UI widgets bound to those view models.
4. *Build-time optimization* — ~@loom/compiler~ extracts co-located handler functions into lazy chunks at build time, statically validates flow graphs, and generates resumability metadata that eliminates round-trips to the server on client restore.

* Deployment & Execution Model

Loom is *isomorphic*: it is neither a client-only nor a server-only framework. The execution core is environment-agnostic and runs unchanged in Node or the browser; the *edges* (durable storage, the A2A HTTP server, terminal rendering, the build-time compiler) are the only environment-specific parts, and storage/transports are injected. In production the durable, agentic core is typically *server-side*, while rendering is *client-side and multi-surface* — bridged by an explicit server→client resumability seam.

Think of it as three layers:

#+begin_example
  ISOMORPHIC CORE  (runs in Node or the browser — no Node/DOM imports; stores & effects injected)
    core · workflow-runtime · effect-runtime · replay-vm · projection-runtime · blueprint-runtime
    capability · intent · planner · agent · memory · scheduler · registry · sdk
    fetch-based I/O: @loom/llm (Anthropic/OpenAI) · @loom/mcp client · @loom/a2a CLIENT

  SERVER-ONLY (Node)                          CLIENT-ONLY (browser)
    SqliteEventStore     (better-sqlite3)       @loom/renderer-react
    SqliteSnapshotStore  (better-sqlite3)       (or any BYOR layer: DOM / Web Components)
    createA2AServer      (node:http)
    @loom/renderer-terminal (Node TUI)
    @loom/compiler          (build-time: node:fs / node:path)
#+end_example

*Isomorphic core.* ~@loom/core~, ~workflow-runtime~, ~effect-runtime~, ~replay-vm~, ~projection-runtime~, ~blueprint-runtime~, and the intelligence packages (~capability~, ~intent~, ~planner~, ~agent~, ~memory~) carry no Node or DOM imports. They receive their ~EventStore~, ~SnapshotStore~, and effects by dependency injection, so *what you inject decides where they run*. Network I/O is ~fetch~-based (the ~@loom/llm~ providers, the ~@loom/mcp~ client, and the ~@loom/a2a~ *client*), which works in both Node ≥ 18 and modern browsers.

*Environment-specific edges (pluggable).* The store interfaces have two shipped implementations each — pick per environment:

| Concern            | Browser / tests            | Server / production                          |
|--------------------+----------------------------+----------------------------------------------|
| ~EventStore~       | ~InMemoryEventStore~       | ~SqliteEventStore~ (WAL mode, durable)       |
| ~SnapshotStore~    | ~InMemorySnapshotStore~    | ~SqliteSnapshotStore~                        |
| Agent transport    | ~createA2AClientEffect~ (~fetch~) | ~createA2AServer~ (~node:http~)       |
| Rendering surface  | ~@loom/renderer-react~ / BYOR DOM | ~@loom/renderer-terminal~ (Node TUI)  |

The only runtime Node-only dependencies are therefore the SQLite stores (~better-sqlite3~) and the A2A *server* (~node:http~); ~@loom/compiler~ is Node-only but runs at *build time*, not at runtime.

*Server→client handoff — "continuation, not hydration."* Because storage is injected, an execution can start (and durably suspend) on a server and then continue and render on a client without re-running completed work:

1. Server runs a flow to a checkpoint, then ~serializeExecution(state)~ and ~serializeProjections(...)~ (~@loom/workflow-runtime/resumability~) to plain JSON.
2. Client ~<LoomProvider serializedExecutionState serializedProjectionState>~ seeds projections synchronously via ~seedState(...)~ (no re-fold, no empty-state flash) and holds the preloaded ~ExecutionState~.
3. On the next input (e.g. a human approval) ~WorkflowRuntime.restoreFromState(preloaded, resumeEvent)~ builds ~new ReplayVM([], preloadedState)~ and continues; ~vm.hasCompleted(stepId)~ means completed steps are *never re-run*.
4. ~@loom/compiler~ turns each ~handler$~ (and each skill's ~instructions$~ body) into a lazy ~import()~ chunk (recorded in ~loom-manifest.json~) so the client downloads a step's code — or a skill's instructions — only when it is actually reached or selected.

*Where the examples sit.* The browser reference apps (~cloud-command-center~, ~db-command-center~, ~db-command-center-wc~) inject the in-memory stores and run the *entire* runtime client-side for a self-contained, offline demo. The ~db-command-center-server~ example shows the production topology of the *same* app: the durable runtime runs on a Node server (~SqliteEventStore~/~SqliteSnapshotStore~, orchestrator, agents, durable ~ctx.suspend~/~resume~) and the Web-Components client renders and drives it over HTTP + SSE — the server pushes a ~serializeProjections~ snapshot on connect, then one A2UI patch per update, and the client folds them into its own projection runtime. Only the stores and the client/server boundary change; everything upstream of the pixels is reused byte-for-byte.

Each capability is expressed as an *effect*, so LLM calls, agent runs, MCP tool invocations, and remote-agent delegations are all durable and replayable exactly like ordinary tool steps. The LLM and MCP providers use the global ~fetch~ (Node 18+) and speak their wire protocols directly, so there are no mandatory SDK dependencies. ** ~SuspendError~

~SuspendError~ is the mechanism that interrupts a running workflow. When ~ctx.suspend()~ is called, the ~WorkflowContext~ throws a ~SuspendError~ carrying a ~SuspendCondition~. ~WorkflowRuntime~ catches this, persists a snapshot, and resolves the caller's ~waitForSuspend()~ promise. On resume, the VM's state carries a ~_resumePayload~ variable so that ~ctx.suspend()~ passes through instead of throwing again.

* ~WorkflowRuntime~ — Execution Orchestrator

~WorkflowRuntime~ is the central coordinator. It owns the event store, snapshot store, and effect runtime.

** Auto-Registration of ~LazyEffect~

When ~registerFlow()~ is called, ~WorkflowRuntime~ inspects every step in the flow definition. For each step that carries a ~handler~ field (a ~HandlerSpec~), it automatically registers a ~LazyEffect~ under ~step.toolId ?? step.id~ — as long as that key is not already occupied. This means steps using ~handler$()~ syntax require no manual ~effectRuntime.register()~ calls.

#+begin_example
registerFlow(definition, runner)
  │
  ├─ flows.set(definition.id, { definition, runner })
  │
  └─ for each step in definition.steps:
       if step.handler !== undefined
       and NOT effectRuntime.has(step.toolId ?? step.id):
         effectRuntime.register(
           step.toolId ?? step.id,
           new LazyEffect(step.handler)   ← wraps HandlerRef or HandlerLoader
         )
#+end_example

** ~ExecutionHandle~

~start()~, ~resume()~, and ~restoreFromState()~ all return an ~ExecutionHandle~ synchronously (before the flow completes). This lets callers set up listeners before the async runner fires:

#+begin_src typescript
const handle = await runtime.start(MyFlow, input);

handle.waitForSuspend().then(() => {
  // workflow is paused — show approval UI
});

handle.waitForCompletion().then(() => {
  // workflow finished
});

handle.getState(); // current ExecutionState at any time

handle.cancel(reason?); // abort in-flight effects and stop this live run
#+end_src

*** ~ExecutionHandle.cancel(reason?)~ — live cancellation

~cancel()~ tears down a live run without touching durable state. Each ~start()~ / ~resume()~ / ~restoreFromState()~ creates one ~AbortController~ per run whose ~signal~ is threaded into every ~EffectContext~. Calling ~cancel()~:

- aborts the signal, so in-flight effects (LLM/tool/A2A) that forward it to ~fetch~ reject promptly,
- records a durable ~EXECUTION_CANCELLED~ event (status → ~"cancelled"~),
- rejects ~waitForCompletion()~ with the supplied reason.

It is *idempotent* (the event is recorded once) and *live-only*: it affects nothing about the persisted event log or snapshot, so a later ~resume()~ behaves exactly as before. Effects that never observe their ~signal~ simply run to completion; cancellation is cooperative, not preemptive.

* ~WorkflowContext~ — The Flow API

~WorkflowContextImpl~ is the object passed to every flow runner function. It is the only API a flow author touches.

#+begin_example
WorkflowContext methods
─────────────────────────────────────────────────────────────
ctx.run(step, input)
  ├─ VM: hasCompleted(step.id)?
  │     YES → return cached output (replay path)
  │     NO  → emit STEP_STARTED
  │           effectRuntime.execute(toolId, input, ctx)
  │           emit STEP_COMPLETED  (or STEP_FAILED)
  │           return output

ctx.parallel(pairs, { limit? })
  └─ order-preserving fan-out over pairs.map(ctx.run)
       no limit  → all steps race concurrently (Promise.all semantics)
       limit: n  → bounded to n at a time (via @loom/scheduler parallelLimit)

ctx.emit(eventType, payload)
  └─ append to EventStore, applyEvent to ReplayVM, notify onEvent

ctx.suspend(config)
  ├─ Resume path: _resumePayload in variables?
  │     YES → consume it, return resolved (pass-through)
  └─ Fresh path: throw SuspendError(config)
#+end_example

~ctx.parallel(pairs, { limit })~ now accepts an optional bounded concurrency cap (default unbounded). Regardless of the cap, results are returned in *input order* — this determinism is load-bearing for replay: a run and its replay reduce fan-out results identically even though execution interleaves. Under the hood it delegates to ~parallelLimit~ from ~@loom/scheduler~.

The idempotency of ~ctx.run()~ is critical. If the process crashes after a step completes but before the workflow finishes, resuming replays all historical events through the VM. ~hasCompleted(stepId)~ returns ~true~ for already-done steps, so their effect is never re-executed — they just return the cached ~output~ from the ~ExecutionFrame~.

* ~ReplayVM~ — Deterministic State Machine

~ReplayVM~ holds an ~ExecutionState~ that is built by folding the event log through a set of pure event handlers (~foldEvents~).

#+begin_example
Event log (ordered by sequence)
  [EXECUTION_STARTED]
  [STEP_STARTED: fetch-metrics]
  [STEP_COMPLETED: fetch-metrics]  ← output cached in frame
  [STEP_STARTED: fetch-logs]
  [STEP_COMPLETED: fetch-logs]
  [EXECUTION_SUSPENDED]
  [ApprovalGranted]
  [EXECUTION_RESUMED]
          │
          ▼
     foldEvents()
          │
          ▼
   ExecutionState {
     status: "running",
     frames: {
       "fetch-metrics": { status: "completed", output: {...} },
       "fetch-logs":    { status: "completed", output: {...} },
     },
     variables: { _resumePayload: { approved: true } },
     sequence: 7
   }
#+end_example

On resume, the VM is seeded with either the full event log or a snapshot + tail events. When the flow runner calls ~ctx.run(FetchMetricsStep, ...)~, the VM already has ~frames["fetch-metrics"].status === "completed"~, so it skips re-execution and returns the cached output instantly.

~restoreFromState()~ takes this further: it accepts a pre-serialized ~ExecutionState~ (produced server-side via ~serializeExecution~) and seeds the VM directly — no EventStore read at all. This is the client-side resumption path.

** Event Handlers (~foldEvents~)

| Event type             | Effect on ~ExecutionState~                                    |
|------------------------+---------------------------------------------------------------|
| ~EXECUTION_STARTED~    | status → "running", startedAt set                            |
| ~STEP_STARTED~         | frame[stepId].status → "running"                             |
| ~STEP_COMPLETED~       | frame[stepId].status → "completed", output stored            |
| ~STEP_FAILED~          | frame[stepId].status → "failed", error stored                |
| ~EXECUTION_SUSPENDED~  | status → "suspended", suspendedOn set                        |
| ~EXECUTION_RESUMED~    | status → "running", payload stored in ~variables._resumePayload~ |
| ~EXECUTION_COMPLETED~  | status → "completed"                                         |
| ~EXECUTION_FAILED~     | status → "failed"                                            |
| ~STEP_CANCELLED~       | frame[stepId].status → "cancelled"; execution status *unchanged* |
| ~EXECUTION_CANCELLED~  | status → "cancelled", cancel reason stored in ~variables._cancelReason~ |

~"cancelled"~ is a value of both ~ExecutionStatus~ and ~FrameStatus~. ~STEP_CANCELLED~ marks the in-flight frame only and deliberately does *not* touch the execution status — ~EXECUTION_CANCELLED~ owns that. ~ctx.run()~ emits ~STEP_CANCELLED~ (instead of ~STEP_FAILED~) when an effect rejects while the run's ~signal~ is aborted, so a cancelled step reads as cancelled rather than failed in the log and replayed state.

* ~EffectRuntime~ — Side-Effect Sandbox

~EffectRuntime~ is a registry of named effects. Every side effect in a flow must be registered here before it can be executed. This makes effects swappable — use ~ToolEffect~ in production, a mock in tests.

#+begin_example
EffectRuntime
  registry: Map<toolId → Effect>

  execute(toolId, input, ctx)
    └─ registry.get(toolId).execute(input, ctx)
#+end_example

** Effect Types

| Class          | Kind     | Behaviour                                                      |
|----------------+----------+----------------------------------------------------------------|
| ~ToolEffect~   | ~tool~   | Wraps an async function — HTTP call, DB query, anything async  |
| ~LlmEffect~    | ~llm~    | Wraps an LLM call; produced by ~createLlmEffect~ / ~AgentRunner.asEffect()~ |
| ~HumanEffect~  | ~human~  | Throws ~SuspendError~ immediately — no async work              |
| ~A2AEffect~    | ~a2a~    | Agent-to-agent delegation; produced by ~createA2AClientEffect~ |
| ~LazyEffect~   | ~tool~   | Resolves and caches a ~HandlerSpec~ on first ~execute()~ call  |

~LlmEffect~ and ~A2AEffect~ have the same wrapper shape as ~ToolEffect~, but the agentic layer packages (~@loom/llm~, ~@loom/a2a~) provide factories that fill them with real protocol behaviour — see [[*Agentic Capabilities][Agentic Capabilities]].

*** ~EffectContext.signal~ — cancellation seam

~EffectContext~ carries an optional ~signal?: AbortSignal~. It is threaded from the owning execution's cancellation controller (see [[*~ExecutionHandle.cancel(reason?)~ — live cancellation][~ExecutionHandle.cancel~]]) and aborts when that run is cancelled. Long-running I/O effects forward it to ~fetch~ (and providers check it at await points), so ~handle.cancel()~ propagates promptly. It is ~undefined~ by default, so non-cancellable effects pay nothing.

** ~LazyEffect~ — Handler Co-location Bridge

~LazyEffect~ is the runtime counterpart to the ~handler$()~ compiler primitive. It accepts either a ~HandlerRef~ (runtime direct path) or a ~HandlerLoader~ (compiled dynamic-import path) and resolves the underlying function on first call.

#+begin_example
LazyEffect(spec)
  execute(input, ctx)
    │
    ├─ already resolved? → call cached fn
    │
    ├─ spec is HandlerRef (runtime path)?
    │     YES → cache spec.fn directly
    │
    └─ spec is HandlerLoader (compiled path)?
          YES → await spec()   ← dynamic import()
                cache mod.default
#+end_example

At runtime (without the compiler), ~handler$(fn)~ returns a ~HandlerRef~, so ~LazyEffect~ calls ~fn~ directly — zero overhead, full test compatibility. At build time, the compiler rewrites ~handler$(fn)~ to ~() => import("\0loom:chunk:stepId_hash")~ (a ~HandlerLoader~), so the function is loaded lazily from a separate chunk on first execution.

~HumanEffect~ is the bridge between the effect system and the suspend mechanism. When a flow reaches a step backed by a ~HumanEffect~, execution suspends until an external ~resume()~ call delivers the human's decision.

#+begin_example
Flow runner                    WorkflowRuntime
  │                                  │
  ctx.run(ApprovalStep, input)       │
  │                                  │
  EffectRuntime.execute()            │
  │  HumanEffect.execute()           │
  │  └─ throw SuspendError ─────────►│
  │                                  │ catch SuspendError
  │                                  │ append EXECUTION_SUSPENDED
  │                                  │ save Snapshot
  │                                  │ resolve suspendPromise
  │                                  │
                   (time passes — operator approves)
                                     │
  runtime.resume(executionId, {      │
    eventType: "ApprovalGranted",    │
    payload: { approved: true }      │
  }) ─────────────────────────────► │
                                     │ append ApprovalGranted
                                     │ append EXECUTION_RESUMED
                                     │ build ReplayVM from snapshot
                                     │ re-run flow runner
                                     │  ctx.suspend() sees _resumePayload
                                     │  → passes through, no re-throw
                                     │  ctx.run(ApplyRemediationStep)
                                     │  → step not yet completed
                                     │  → executes normally
                                     │ resolve completionPromise
#+end_example

* ~EventStore~ — Append-Only Event Log

Two implementations ship with the framework:

| Implementation          | Use case                                     |
|-------------------------+----------------------------------------------|
| ~InMemoryEventStore~    | Browser, tests, short-lived processes        |
| ~SqliteEventStore~      | Server / production (WAL mode, durable)      |

~SqliteEventStore~ enforces a ~UNIQUE(execution_id, sequence)~ constraint — duplicate appends throw, making the log conflict-free by construction. WAL mode keeps writes fast without sacrificing durability.

#+begin_example
EventStore interface
──────────────────────────────────────────────
append(envelope)          → void
read(executionId)         → EventEnvelope[]     (ordered ASC)
readFrom(executionId, seq)→ EventEnvelope[]     (seq inclusive)
subscribe(executionId, fn)→ unsubscribe()
nextSequence(executionId) → number
#+end_example

* ~SnapshotStore~ — Resume Acceleration

Reading and folding thousands of events on every resume is expensive. ~SnapshotStore~ solves this by capturing a full ~ExecutionState~ at the moment of suspension.

#+begin_example
On suspend:
  snap = {
    executionId,
    sequence: vm.getState().sequence,   ← last applied sequence
    state: vm.getState(),               ← full ExecutionState
  }
  snapshotStore.save(snap)

On resume:
  snapshot = snapshotStore.loadLatest(executionId)
  if (snapshot):
    tailEvents = eventStore.readFrom(executionId, snapshot.sequence + 1)
    vm = new ReplayVM(tailEvents, snapshot.state)
  else:
    allEvents = eventStore.read(executionId)
    vm = new ReplayVM(allEvents)
#+end_example

In the steady state — one suspend, one resume — the replay cost on resume is proportional to the number of events *after* the snapshot (typically 2–3), not the total event count.

* ~ProjectionRuntime~ — Live View Models

~ProjectionRuntime~ subscribes to workflow events and maintains per-execution view state for each registered ~Projection~. The UI subscribes to projection state changes and re-renders on every update.

#+begin_example
WorkflowRuntime                ProjectionRuntime
       │                              │
       │  onEvent(envelope) ─────────►│
       │                              │ for each registered projection:
       │                              │   handler = projection.handlers[eventType]
       │                              │   if handler:
       │                              │     nextState = handler(currentState, event)
       │                              │     states.set(key, nextState)
       │                              │     notify subscribers
       │                              │
                    React UI
                        │
              subscribe(projectionId, executionId, setState)
                        │
              ◄──────── state updates arrive live
#+end_example

** Coalesced notifications (opt-in)

By default every ~handleEvent~ notifies subscribers synchronously — one subscriber call per event, preserving strict synchronous semantics. For high-frequency bursts (e.g. LLM token streaming, where one event arrives per token) this is O(events) subscriber calls. ~InMemoryProjectionRuntime~ accepts an opt-in config to collapse them:

#+begin_src typescript
const projectionRuntime = new InMemoryProjectionRuntime({
  coalesceNotifications: true,
});
#+end_src

With coalescing on, ~handleEvent~ still folds each event immediately (state stays correct) but marks the affected ~projectionId::executionId~ key dirty and schedules a single ~queueMicrotask~ flush. The flush notifies each dirty key's subscribers *once* with the *latest* state, so a synchronous burst of N events yields O(microtask flushes) subscriber calls instead of O(N). Off by default; when off the runtime takes the exact synchronous path it always has.

** Projection State Key

State is keyed by ~projectionId::executionId~, so multiple concurrent executions of the same flow each maintain independent projection state.

** ~seedState(projectionId, executionId, state)~

~seedState~ populates projection state synchronously without processing events. It is called by ~LoomProvider~ on mount to restore projection state from a serialized snapshot, preventing an empty-state flash on first render. State seeded this way is immediately visible to all subscribers.

* @loom/compiler — Build-Time Optimizer

The compiler is a Vite plugin and standalone CLI that applies three optimizations at build time, inspired by the QwikJS optimizer.

** Feature 1: ~handler$()~ Lazy Chunk Extraction

~handler$()~ is an identity function at runtime — it wraps a handler function in a ~HandlerRef~ with no overhead. The compiler replaces it at build time:

#+begin_example
Source (authored):
  const FetchMetricsStep = step$({
    id: "fetch-metrics",
    handler: handler$(async (input, ctx) => {
      const data = await fetchFromApi(input.incidentId);
      return data;
    }),
    inputSchema: ..., outputSchema: ...,
  });

After compiler transform:
  const FetchMetricsStep = step$({
    id: "fetch-metrics",
    handler: () => import("\0loom:chunk:fetch-metrics_2f936a0b"),
    inputSchema: ..., outputSchema: ...,
  });

Generated chunk (\0loom:chunk:fetch-metrics_2f936a0b):
  // re-emits all top-level imports from the source file
  import { fetchFromApi } from "...";
  export default async function(input, ctx) {
    const data = await fetchFromApi(input.incidentId);
    return data;
  };
#+end_example

The dynamic import is only resolved on the first ~ctx.run(FetchMetricsStep, ...)~ call. Steps that are never reached in an execution never load their chunk.

** Feature 2: Static Flow Graph Analysis + ~loom-manifest.json~

The compiler walks every ~step$()~ and ~flow$()~ call in the codebase, resolves variable names to step ids, and emits a ~loom-manifest.json~ build asset:

#+begin_example
loom-manifest.json
{
  "version": "1",
  "flows": {
    "investigate-incident": {
      "version": "1.0.0",
      "steps": ["fetch-metrics", "fetch-logs", "apply-remediation"],
      "chunkMap": {
        "fetch-metrics": "dist/chunks/fetch-metrics_2f936a0b.js",
        "fetch-logs":    "dist/chunks/fetch-logs_4a1b3c2d.js"
      },
      "suspendPoints": ["apply-remediation"],
      "warnings": [
        "Step \"apply-remediation\" has neither a handler$ nor a toolId"
      ]
    }
  },
  "skills": {
    "diagnose-cpu": { "chunk": "dist/chunks/diagnose-cpu_9c1f0a7e.js" }
  }
}
#+end_example

The ~skills~ map records each ~skill$~'s lazy instruction chunk — the progressive-disclosure analog of a flow's ~chunkMap~ (empty ~chunk~ when the skill was authored with inline instructions and no ~instructions$~ marker to extract). Warnings are printed to the terminal at build time for steps that lack both a ~handler$~ and a ~toolId~.

** Feature 3: Resumability Primitives

The compiler package exports serialization utilities that implement the server → client state transfer contract:

#+begin_example
SERVER SIDE (e.g. API route)
─────────────────────────────────────────────────────────────
const state = handle.getState();
const projStates = {
  metrics:  projectionRuntime.getState("metrics", executionId),
  incident: projectionRuntime.getState("incident", executionId),
};

const serializedExec = serializeExecution(state);
const serializedProj = serializeProjections(projStates, executionId);

// Embed in SSR HTML or API response:
window.__LOOM_EXEC__ = JSON.parse(serializedExec);
window.__LOOM_PROJ__ = JSON.parse(serializedProj);

CLIENT SIDE (React mount)
─────────────────────────────────────────────────────────────
<LoomProvider
  workflowRuntime={workflowRuntime}
  projectionRuntime={projectionRuntime}
  serializedExecutionState={window.__LOOM_EXEC__}
  serializedProjectionState={window.__LOOM_PROJ__}
>
  <App />
</LoomProvider>
#+end_example

~LoomProvider~ calls ~projectionRuntime.seedState()~ synchronously on mount, so child components never see an empty-state flash on first render.

** Vite Plugin Hook Sequence

#+begin_example
configResolved   → store resolved Vite config (for outDir)
     │

* @loom/telemetry — Structured Observability

~@loom/telemetry~ is a zero-dependency observability layer that sits between the ~WorkflowRuntime~ and any telemetry backend. It has no peer dependency on ~@loom/workflow-runtime~ — it only requires ~@loom/core~ for ~EventEnvelope~ types. The canonical usage is:

#+begin_src typescript
import { createTelemetryHook, ConsoleTelemetryAdapter, composeAdapters } from "@loom/telemetry";

const telemetryHook = createTelemetryHook(ConsoleTelemetryAdapter);

const runtime = new WorkflowRuntime({
  // ...
  onEvent: (e) => {
    projectionRuntime.handleEvent(e);  // existing handler
    telemetryHook(e);                  // compose in telemetry
  },
});
#+end_src

** ~TelemetryAdapter~ interface

All nine methods are optional; implement only the events you care about:

| Method             | Fires on                   | Payload                      |
|--------------------+----------------------------+------------------------------|
| ~onFlowStart~      | ~EXECUTION_STARTED~        | ~FlowTelemetryInfo~          |
| ~onFlowComplete~   | ~EXECUTION_COMPLETED~      | ~FlowTelemetryInfo~          |
| ~onFlowFail~       | ~EXECUTION_FAILED~         | ~FlowTelemetryInfo~          |
| ~onFlowSuspend~    | ~EXECUTION_SUSPENDED~      | ~FlowTelemetryInfo~          |
| ~onFlowResume~     | ~EXECUTION_RESUMED~        | ~FlowTelemetryInfo~          |
| ~onStepStart~      | ~STEP_STARTED~             | ~StepTelemetryInfo~          |
| ~onStepComplete~   | ~STEP_COMPLETED~           | ~StepTelemetryInfo~          |
| ~onStepFail~       | ~STEP_FAILED~              | ~StepTelemetryInfo~          |
| ~onStepRetry~      | ~STEP_RETRYING~            | ~StepTelemetryInfo~          |

** ~FlowTelemetryInfo~ and ~StepTelemetryInfo~

~createTelemetryHook~ computes ~durationMs~ from ~EventEnvelope.timestamp~ values, so telemetry adapters receive pre-computed timings rather than raw timestamps. ~FlowTelemetryInfo~ accumulates ~stepCount~ and ~suspendCount~ as the execution progresses. On ~EXECUTION_RESUMED~, ~completedAt~ and ~durationMs~ are cleared and ~status~ resets to ~"running"~ so that the reported duration reflects the total wall-clock time across all resume legs.

** ~createTelemetryHook(adapter)~

Returns an ~(event: EventEnvelope) => void~ function ready to compose with any existing ~onEvent~ handler. The returned function is a pure event transformer — it holds no async operations and will not throw. Internal per-execution state (flow info maps, step start times, attempt counters) is closure-local; multiple hooks from different ~createTelemetryHook~ calls do not share state.

** ~ConsoleTelemetryAdapter~

The built-in zero-dependency adapter. Writes structured, column-aligned lines to ~console.log~:

#+begin_example
[loom] FLOW_START      exec=01JNXXX  workflow=investigate-incident
[loom] STEP_START      exec=01JNXXX  step=fetch-metrics   attempt=1
[loom] STEP_DONE       exec=01JNXXX  step=fetch-metrics   duration=687ms  attempt=1
[loom] STEP_DONE       exec=01JNXXX  step=fetch-logs      duration=503ms  attempt=1
[loom] FLOW_SUSPEND    exec=01JNXXX  workflow=investigate-incident  duration=1204ms  suspend#=1
[loom] STEP_DONE       exec=01JNXXX  step=apply-remediation  duration=615ms  attempt=1
[loom] FLOW_DONE       exec=01JNXXX  workflow=investigate-incident  duration=1841ms  steps=3
#+end_example

** ~composeAdapters(...adapters)~

Fans out all nine adapter methods to every adapter in the list. Use this to send telemetry to multiple sinks simultaneously:

#+begin_src typescript
const telemetryHook = createTelemetryHook(
  composeAdapters(ConsoleTelemetryAdapter, otelAdapter)
);
#+end_src

** OTel integration pattern

~@loom/telemetry~ deliberately does not bundle ~@opentelemetry/api~. The adapter interface is shaped so that each flow-level event maps to span lifecycle operations:

#+begin_src typescript
import { trace, context, SpanStatusCode } from "@opentelemetry/api";
import type { TelemetryAdapter, FlowTelemetryInfo, StepTelemetryInfo } from "@loom/telemetry";

const tracer = trace.getTracer("loom");
const flowSpans = new Map<string, Span>();
const stepSpans = new Map<string, Span>();

export const OtelAdapter: TelemetryAdapter = {
  onFlowStart(info) {
    const span = tracer.startSpan(info.workflowId, { startTime: info.startedAt });
    flowSpans.set(info.executionId, span);
  },
  onStepStart(info) {
    const parent = flowSpans.get(info.executionId);
    const ctx = parent ? trace.setSpan(context.active(), parent) : context.active();
    const span = tracer.startSpan(info.stepId, { startTime: info.startedAt }, ctx);
    stepSpans.set(`${info.executionId}:${info.stepId}`, span);
  },
  onStepComplete(info) {
    stepSpans.get(`${info.executionId}:${info.stepId}`)?.end(info.completedAt);
  },
  onFlowComplete(info) {
    flowSpans.get(info.executionId)?.end(info.completedAt);
    flowSpans.delete(info.executionId);
  },
  onFlowFail(info) {
    const span = flowSpans.get(info.executionId);
    span?.setStatus({ code: SpanStatusCode.ERROR });
    span?.end(info.completedAt);
  },
};
#+end_src

* Agentic Capabilities

Loom is an *agentic* application framework: the model provider, the agents, the tools, and inter-agent communication are all pluggable, and every one of them is expressed as a durable *effect*. This means an LLM call or a remote-agent delegation is memoized on its step frame and skipped on replay, exactly like a tool call — durability is free.

** Configurable LLM (~@loom/llm~)

The ~LlmProvider~ interface is the single seam through which a model is chosen. It has one required method, ~complete(request)~, and an optional ~stream(request)~.

#+begin_src ts
interface LlmProvider {
  complete(request: LlmRequest): Promise<LlmResponse>;
  stream?(request: LlmRequest): AsyncIterable<LlmStreamChunk>;
}
#+end_src

~@loom/llm~ ships ~AnthropicProvider~ and ~OpenAiProvider~, both implemented against the global ~fetch~ (Node 18+) so neither vendor SDK is a required dependency. A provider is turned into a step with ~createLlmEffect~:

#+begin_src ts
import { AnthropicProvider, createLlmEffect } from "@loom/llm";

const provider = new AnthropicProvider({ model: "claude-opus-4-8" });
effectRuntime.register("summarize", createLlmEffect({
  provider,
  buildRequest: (text: string) => ({ messages: [{ role: "user", content: text }] }),
}));
#+end_src

Because the provider is just an object, tests use a hand-written stub and the offline examples use a ~MockLlmProvider~ / ~ScriptedLlmProvider~. Switching to a live model is a one-line change.

** Agents (~@loom/agent~)

~AgentRunner~ implements a ReAct loop: it sends the prompt plus the agent's tool specs to the provider, executes any requested tool calls against the ~EffectRuntime~, feeds the results back, and repeats until the model stops or ~maxIterations~ is hit. Each tool call emits an ~AGENT_TOOL_CALL~ event; the run ends with ~AGENT_COMPLETED~.

*Skills.* An optional ~SkillRegistry~ (built from ~skill$~ definitions) adds progressively-disclosed expertise. Before the loop the runner selects the skills relevant to the turn, emits ~SKILLS_SELECTED~, lazy-loads *only* those instruction bodies (the compiler extracts each ~instructions$~ body into its own chunk, so unselected skills never load), appends them to the system prompt, and adds their tools to the model's menu. This is the instruction/know-how axis — separate from tools (functions) and capabilities (flows). Selection is deterministic by default so replay reconstructs the same prompt; an opt-in ~llmSkillSelector~ trades that for model-driven choice, with the recorded ~SKILLS_SELECTED~ event as the audit hook. Distinct from the A2A ~AgentSkillDef~ card metadata described in the A2A section.

#+begin_example
AgentRunner.run(input, ctx)
  loop (≤ maxIterations):
    provider.complete({ messages, tools })
      │
      ├─ stopReason "end_turn" → break, return content
      │
      └─ stopReason "tool_use":
           for each toolCall:
             effectRuntime.execute(toolCall.name, toolCall.input, ctx)
             ctx.emit("AGENT_TOOL_CALL", …)
             append result to messages
  ctx.emit("AGENT_COMPLETED", …)
#+end_example

By default the ReAct loop executes a turn's tool calls sequentially. ~AgentConfig.parallelTools~ (~boolean | number~, default ~false~) opts into concurrent tool execution within a turn: ~true~ runs them all at once, a number bounds the concurrency. It routes through ~parallelLimit~ from ~@loom/scheduler~, so tool *outputs and events are emitted in the model's requested input order* regardless of completion order — a run and its replay produce byte-identical event logs.

~agentStep$({ id, agent, provider, effectRuntime })~ packages a runner as an ordinary ~StepDefinition~ (kind ~llm~), so an agent drops into a flow like any other step and inherits suspend/resume and replay.

** MCP tools (~@loom/mcp~)

~McpClient~ speaks the Model Context Protocol over JSON-RPC. ~connect()~ performs the ~initialize~ handshake; ~registerInto(effectRuntime)~ calls ~tools/list~ and registers each discovered tool as a ~ToolEffect~ whose handler invokes ~tools/call~. MCP tools validate their own inputs, so their ~ToolDefinition~ uses ~z.unknown()~ and the raw JSON Schema is preserved on ~MappedMcpTool.jsonInputSchema~ for building ~LlmToolSpec~s.

#+begin_src ts
const mcp = new McpClient({ transport: "http", url: "http://localhost:9000/mcp" });
await mcp.connect();
const defs = await mcp.registerInto(effectRuntime);   // → ToolDefinition[]
// defs can be handed straight to agent$({ tools: defs })
#+end_src

** Agent-to-Agent (~@loom/a2a~)

A2A gives a Loom service two roles. As a *server*, ~createA2AServer(workflowRuntime, flow, agentCard)~ starts a Node HTTP server exposing three routes:

- ~GET /.well-known/agent.json~ — the agent card (capabilities + skills)
- ~POST /tasks/send~ — starts a flow execution, returns the task id
- ~GET /tasks/:id~ — maps ~ExecutionStatus~ → ~A2ATaskStatus~ and returns artifacts on completion

As a *client*, ~createA2AClientEffect(agentUrl)~ returns an ~A2AEffect~ that POSTs a task, polls for completion, and returns the result — so calling a remote agent is just another step in a flow. Both use built-in ~http~/~fetch~ with no framework HTTP dependency.

The agent card is not hand-authored: an ~agent$~ definition carries optional ~version~, ~capabilities~, and ~skills~ metadata, and ~toAgentCard(agent)~ derives its ~AgentCard~ from that — keeping the card and the agent a single source of truth.

~@loom/registry~ provides ~AgentRegistry~, a store of ~AgentDefinition~ + agent-card pairs that a gateway can use to serve multiple agents.

** A2UI — the Agent-to-UI protocol (~@loom/a2ui~)

A2UI is a first-class, patch/event-based protocol for agents and workflows to drive the UI. Rather than each flow inventing its own event shapes, A2UI standardises UI updates as a stream of typed *patches* carried by a single event type. Because those patches travel through the ordinary Loom event pipeline, UI updates are durable, ordered, and *replayable* — the UI surface is fully reconstructable from the event log, so a refresh or a resume rebuilds the exact same screen.

*** Patches and surfaces

The unit of change is an ~A2UIPatch~ — a declarative mutation addressed by a dot-notation path (~""~ = the root):

#+begin_src ts
type A2UIPatch =
  | { op: "set";       path: string; value: unknown }
  | { op: "merge";     path: string; value: Record<string, unknown> }
  | { op: "append";    path: string; value: unknown }   // arrays: tokens, logs, timelines
  | { op: "remove";    path: string }
  | { op: "increment"; path: string; by?: number };
#+end_src

A *surface* is one addressable UI state tree (~A2UISurfaceState = Record<string, unknown>~). Most apps use one (id ~"ui"~); an agent can drive several (e.g. ~"ui"~, ~"sidebar"~). Every patch batch is emitted as one ~A2UI_PATCH~ event with payload ~{ surface, patches }~.

*** Producing patches

Any context that can emit events can drive the UI. ~WorkflowContext~ exposes ~ctx.ui~ (an ~A2UIEmitter~), and ~createA2UIEmitter(emit, surface?)~ gives the same API to a step's ~EffectContext~ or an agent:

#+begin_src ts
ctx.ui.set("phase", "triaging");           // one A2UI_PATCH event
ctx.ui.merge("stats", { items: 42 });
ctx.ui.append("log", "connection reset");  // grows an array
ctx.ui.increment("stepsCompleted");
#+end_src

*** Consuming patches

There are two consumers, both folding ~A2UI_PATCH~ events with the pure ~applyA2UIPatch~ reducer:

- ~a2uiSurfaceProjection(surfaceId)~ — a ProjectionDefinition whose id is the surface id. Register it in an existing ~ProjectionRuntime~ and widgets bind to A2UI state with the ordinary ~{ projectionId: "ui", path }~ binding — the React ~BlueprintRenderer~ needs no changes.
- ~A2UIRuntime~ — a standalone, framework-agnostic surface store (subscribe / getSurface), for consumers that are not projection-based. The ~useA2UISurface~ hook in ~@loom/renderer-react~ wraps it for React.

#+begin_example
ctx.ui.set("phase", "triaging")
   │  emits
   ▼
A2UI_PATCH event  { surface:"ui", patches:[{op:"set",path:"phase",value:"triaging"}] }
   │  onEvent
   ├────────────► a2uiSurfaceProjection("ui")  ─► ProjectionRuntime ─► BlueprintRenderer
   └────────────► A2UIRuntime.handleEvent()     ─► useA2UISurface()  ─► any React tree
#+end_example

The ~cloud-command-center~ example streams an AI root-cause analysis into the ~"ui"~ surface and drives a phase badge with ~ctx.ui.set~; the playground's *A2UI* tab shows the live surface next to the raw patch stream. Because patches replay deterministically and any producing step is memoized, the surface is consistent across refresh and resume.

The ~StreamingText~ widget (in ~@loom/blueprint-runtime~, rendered by ~StreamingTextRenderer~) is a convenience for binding to a growing string in the surface; ~WorkflowContext.stream()~ remains as low-level sugar over ~emit~ for callers that want raw delta events instead of patches.

* The Intelligence Pipeline (Intent → Planner → Capabilities)

The agentic layer answers "how do I run a model / an agent / a remote agent as a durable effect". The *intelligence pipeline* answers a higher-level question: given a natural-language *intent*, which unit of work should run, and in what order? Five packages fill in the pieces the proposal calls out — Intent Runtime, Planner Runtime, "Capabilities Over APIs", agent memory access, and non-React surface delivery. All are re-exported from ~@loom/sdk~, and the ~examples/agent-network~ showcase demonstrates every one of them.

#+begin_example
intent text
     │
     ▼
IntentRuntime.route(text) ──► LLM routing (provider set)
     │                         or deterministic keyword match (offline)
     ▼
IntentRoute { capability, confidence }
     │
     ▼
capability.flow  ──►  WorkflowRuntime.start(flow, input)  ──►  ExecutionHandle
                                                               (durable, resumable)
#+end_example

A ~PlannerRuntime~ sits alongside the router: instead of picking one capability it composes an ordered *plan* of capability ids from the same catalog. Downstream, everything is ordinary Loom — the chosen capability's ~RegisteredFlow~ runs on ~WorkflowRuntime~, emits events, folds into projections, and renders to a surface.

** Capabilities Over APIs (~@loom/capability~)

A *capability* wraps a runnable flow with intent-facing metadata, so the same unit of work can be exposed as an API, a UI action, an A2A endpoint, or a workflow node without re-authoring it. ~capability$(config)~ produces a ~CapabilityDefinition~ carrying an ~id~, a human ~name~, a natural-language ~intent~, ~tags~, an ~inputSchema~, and the ~flow~ (a ~RegisteredFlow~).

~CapabilityCatalog~ is the registry. Beyond ~register~ / ~get~ / ~all~ / ~ids~, it provides:

- ~find(query)~ — deterministic keyword scoring over each capability's ~id~, ~name~, ~intent~, and ~tags~; returns ~{ capability, score }[]~ ranked high-to-low. No model required, so discovery works offline.
- ~registerInto(workflowRuntime)~ — registers every capability's flow with a ~WorkflowRuntime~ in one call.
- ~invoke(workflowRuntime, capabilityId, input)~ — looks up a capability and starts its flow, returning the ~ExecutionHandle~.

The catalog is the shared vocabulary both the Intent Runtime and the Planner Runtime route over.

** Intent Runtime — Intent Over Routes (~@loom/intent~)

~IntentRuntime~ maps a natural-language intent to a capability, replacing hand-written route tables. It is constructed with a ~catalog~ and, optionally, an ~LlmProvider~ and a ~WorkflowRuntime~.

- ~route(intentText)~ → ~IntentRoute | null~. With a ~provider~, the model is asked to pick a capability id from the catalog (returning ~{ capability, confidence, rationale }~). With *no* provider it falls back to ~catalog.find()~ keyword scoring — so routing works fully offline. Returns ~null~ when nothing matches.
- ~run(intentText, input)~ → routes, then calls ~workflowRuntime.start()~ on the matched capability's flow and returns the ~ExecutionHandle~. Requires ~workflowRuntime~ in the config.

The key property is that the *same* runtime works with or without a model: the deterministic keyword path makes tests and offline demos possible, and adding a provider is a drop-in upgrade to LLM routing.

~IntentRuntime~ also accepts an optional ~scheduler~ (a ~@loom/scheduler~ ~Scheduler~). When supplied, the routing LLM call is submitted at ~Priority.Idle~, so background routing yields the scheduler's slots to foreground agent turns when a shared scheduler runs at a finite concurrency cap.

** Planner Runtime (~@loom/planner~)

~PlannerRuntime~ composes an ordered, multi-step ~Plan~ from the catalog rather than choosing a single capability. It takes a ~catalog~, an optional ~provider~, and ~maxSteps~ (default 5).

- ~plan(goal)~ → ~Plan { goal, steps: PlanStep[] }~, each ~PlanStep~ naming a ~capabilityId~ and an optional ~rationale~. With a ~provider~, the model returns an ordered JSON plan; with none, a heuristic keyword-ranked plan is produced. Either way every emitted ~capabilityId~ is validated against the catalog, so a plan can only reference capabilities that actually exist, and it is truncated to ~maxSteps~.

Like ~IntentRuntime~, ~PlannerRuntime~ takes an optional ~scheduler~ and runs its planning LLM call at ~Priority.Idle~ — planning is background work that should defer to live foreground turns under a shared, capped scheduler.

** Agent Runtime memory (~@loom/memory~)

~MemoryRuntime~ gives an agent durable recall across turns. A ~MemoryStore~ (default ~InMemoryMemoryStore~) holds ~MemoryEntry~ records (~{ role?, content, timestamp }~) under a key. The runtime layers definition-aware semantics on top:

- ~register(definition)~ — takes a ~MemoryDefinition~ (from ~memory$()~) and honors its ~ttlMs~ and ~maxEntries~.
- ~append(memoryId, scope, entry)~ / ~read(memoryId, scope)~ / ~clear(memoryId, scope)~ — reads are pruned by ~ttlMs~ first, then trimmed to ~maxEntries~. The ~scope~ string partitions memory by conversation or user.

Integration with ~@loom/agent~ is opt-in: ~AgentConfig~ gained an optional ~memory?: MemoryRuntime~. When the agent's ~definition.memoryId~ is set and a ~MemoryRuntime~ is provided, ~AgentRunner.run~ recalls prior entries into the prompt before calling the model, and writes the user prompt plus the assistant answer back afterward. ~AgentInput~ gained ~memoryScope?: string~ (defaulting to ~ctx.executionId~) to scope recall per conversation.

#+begin_example
AgentRunner.run(input, ctx)   [memory + memoryId configured]
  │
  ├─ memory.read(memoryId, input.memoryScope ?? ctx.executionId)
  │     └─ prior entries → prepended into the prompt
  │
  ├─ …ReAct loop (provider.complete + tool calls)…
  │
  └─ memory.append(memoryId, scope, { role:"user",      content: input.prompt })
     memory.append(memoryId, scope, { role:"assistant", content: output.content })
#+end_example

** Multi-surface delivery (~@loom/renderer-terminal~)

The proposal's surface layer is deliberately framework-agnostic: ~traverseBlueprint<T>~ walks a ~Blueprint~ producing values of any type ~T~, so a blueprint is not tied to React. ~@loom/renderer-terminal~ proves this by rendering the *same* blueprint + projection state to text instead of DOM:

- ~renderBlueprintToString(blueprint, stateMap)~ — uses ~traverseBlueprint<string>~ to fold a blueprint and a ~Map<string, unknown>~ of projection state into a plain string.
- ~TerminalRenderer~ — constructed with a ~ProjectionRuntime~; its ~render(blueprint, executionId)~ pulls each of the blueprint's projections' state for that execution and renders them to text.

Because ~traverseBlueprint~ is the shared traversal used by both the React ~BlueprintRenderer~ and the terminal renderer, a single blueprint definition renders to the web *or* the terminal with no changes — the multi-surface delivery the proposal calls for.

** Render-side "useFiber" — leveraging React's own fiber

The render side does *not* add a second reconciler. The synchronous ~traverseBlueprint~ (a pull walk that assembles the whole tree) remains the default and is unchanged. On top of it, two opt-in seams apply Fiber principles where they actually pay off:

*** React renderer: ~<BlueprintRenderer fiber={…}>~

The React ~BlueprintRenderer~ accepts an opt-in ~fiber~ prop (~boolean | { granularUpdates, suspense, deferStreaming }~; defaults off, byte-identical output when falsy). Rather than time-slicing itself, it leverages React's *own* fiber scheduler:

- ~granularUpdates~ — each widget subscribes to its own binding path, so only the widget whose slice changed re-renders instead of the whole blueprint.
- ~suspense~ — each widget is wrapped in its own ~<Suspense>~ boundary, so an async BYOC component can suspend without blanking its siblings.
- ~deferStreaming~ — high-frequency (streaming) widgets are fed through ~startTransition~, so their updates never block urgent work.

~fiber={true}~ enables all three; an object opts into individual capabilities (requesting any implies per-widget mounting). A ~LoomProvider~ ~fiber~ prop supplies a default that a per-renderer prop can override.

*** Scheduler-less BYOR renderers: ~traverseBlueprintAsync~

For renderers with no framework scheduler of their own (direct DOM, canvas, native), ~@loom/blueprint-runtime~ exports ~traverseBlueprintAsync~ — an interruptible, incremental-commit *push* traversal. It creates each node top-down, commits children into their container as they resolve (progressive paint), cooperatively yields against a counter-based budget (default every 64 nodes, via ~@loom/scheduler~ ~yieldControl~), and checks an ~AbortSignal~ at every node so a stale render can be dropped. This is the validated BYOR extension point; no production renderer targets it yet (all current renderers use the synchronous pull walk).

The division of labour: React already has fiber, so useFiber *rides* it; the async traversal is the seam reserved for future non-React renderers that would otherwise have nothing.

* ~@loom/scheduler~ — Cooperative Scheduling & Cancellation

~@loom/scheduler~ is an *ephemeral*, dependency-free cooperative scheduler for live, in-flight async work. It applies Fiber *principles* — priority, interruptibility, incremental progress — to the *async agentic layer*, not to UI reconciliation. Concretely it is an async, priority-ordered semaphore plus ~AbortSignal~ cancellation.

It is deliberately *not* a UI reconciler and *not* durable: Loom's ~SuspendError~ + ~ReplayVM~ already own durable pause/resume across the event log, and this package complements them for the live window *between* events (a running LLM call, an in-flight tool fan-out). Scheduler state is never persisted — on a crash/resume it simply doesn't exist, and the durable log rebuilds the world.

Everything is opt-in and latency-safe. The default ~concurrency: Infinity~ disables gating entirely, so ~schedule~ reduces to ~await task(signal)~ with no queue node, no controller, and no bookkeeping — overhead is paid only when a finite cap is explicitly set (see docs/benchmarks.md). Dependents: ~@loom/workflow-runtime~, ~@loom/agent~, ~@loom/planner~, ~@loom/intent~, and ~@loom/blueprint-runtime~.

** Priority lanes

~Priority~ is *ordering only*. The lanes decide which queued task acquires the next free slot under a finite concurrency cap; they do *not* drive a frame-deadline time-slicer (a frame budget is meaningless while awaiting a socket). Lower numeric value == more urgent (dequeued first).

| Lane                        | Use                                                     |
|-----------------------------+---------------------------------------------------------|
| ~Priority.Immediate~ (0)    | Interactive, must-run-now work (a user cancel/approval) |
| ~Priority.UserBlocking~ (1) | Foreground work a user is waiting on (a live agent turn) |
| ~Priority.Normal~ (2)       | Default — ordinary flow/effect work                     |
| ~Priority.Idle~ (3)         | Background work that yields to everything (planning)    |

** ~createScheduler({ concurrency })~

Builds a scheduler around a priority queue in front of a counting semaphore.

#+begin_src typescript
import { createScheduler, Priority } from "@loom/scheduler";

const scheduler = createScheduler({ concurrency: 4 }); // cap live LLM/tool calls

const result = await scheduler.schedule(
  (signal) => provider.complete(request, { signal }),
  { priority: Priority.UserBlocking, label: "agent-turn" }
);
#+end_src

~schedule(task, opts?)~ always returns a promise (it never throws synchronously — an already-aborted signal yields a rejected promise). ~inFlight~ and ~pending~ expose live counts. With the default ~concurrency: Infinity~, ~createScheduler~ returns a fast-path implementation with no queue at all; a finite cap switches on the semaphore. Tasks queued behind the cap are dequeued by ~(priority asc, enqueue-order asc)~, and a task whose caller ~signal~ aborts *while still queued* is removed before it ever takes a slot — keeping cancellation latency low under load.

** ~parallelLimit~ — order-preserving structured concurrency

~parallelLimit(tasks, { limit?, signal?, failFast? })~ runs an array of ~(signal) => Promise<T>~ tasks with bounded concurrency and *preserves input order in the result array* — ~results[i]~ always corresponds to ~tasks[i]~ regardless of completion order. This ordering guarantee is load-bearing for replay determinism: callers that fan out work (~ctx.parallel~, ~AgentRunner.parallelTools~) reduce results deterministically even though execution interleaves. With ~failFast~ (default) the first rejection aborts still-pending siblings via a linked signal; with ~failFast: false~ every task settles and the first error by input order is thrown afterward. Unbounded (~limit >= tasks.length~) it degenerates to ~Promise.all~ semantics.

** ~yieldControl~ — cooperative yielding

~yieldControl()~ returns a promise that resolves on a *macrotask* boundary (~setTimeout(0)~, ~unref~'d), so the event loop genuinely drains between chunks — used by CPU-bound loops (e.g. ~traverseBlueprintAsync~) that want to stay responsive. It is a macrotask, not a microtask, precisely so paint/input can interleave in a browser.

** AbortSignal utilities

Small, dependency-free helpers; all are optional-signal-safe (passing ~undefined~ allocates nothing):

- ~throwIfAborted(signal?)~ — throw the signal's reason if already aborted; prefers the platform method when present.
- ~linkSignals(...signals)~ — combine several signals into one that aborts when any input does; returns ~undefined~ for no signal, the same signal for one, and prefers native ~AbortSignal.any~ otherwise.
- ~withTimeout(ms, parent?)~ — derive a signal that aborts after ~ms~ (a ~TimeoutError~) or when ~parent~ aborts; call ~dispose()~ when the guarded work settles to release the timer.
- ~NEVER_SIGNAL~ — a single shared never-aborting signal handed to tasks when the caller supplies none, so task callbacks can always rely on receiving an ~AbortSignal~ without a per-call ~AbortController~ allocation.

* Resumability — Client-Side State Restoration

Resumability eliminates the client's need to re-fetch or re-replay events from the server when mounting a React UI that already has a live (or suspended) execution.

#+begin_example
Traditional browser-side execution (current baseline):
  1. Mount React app
  2. Call workflowRuntime.start() or resume()
  3. WorkflowRuntime reads EventStore (SQLite / HTTP)
  4. Rebuilds ExecutionState from event log
  5. Re-runs all steps from replay
  → Round-trip to server / database required on every mount

With Loom resumability:
  1. Server serializes ExecutionState + ProjectionState into strings
  2. Strings embedded in SSR HTML / API response
  3. Mount React app with <LoomProvider serialized…>
     LoomProvider.seedState() seeds projections synchronously
  4. Component renders with correct data immediately (no flash)
  5. If execution is suspended, call restoreFromState(preloadedState)
     → No EventStore round-trip; VM seeded from preloaded state
#+end_example

** ~serializeExecution~ / ~deserializeExecution~

Pure JSON serialization of ~ExecutionState~. The state is self-contained — it includes all step outputs, status, variables, and sequence number. Passing it to ~restoreFromState()~ is sufficient to resume execution without touching the EventStore.

** ~serializeProjections~ / ~deserializeProjections~

Serializes a ~Record<projectionId, state>~ snapshot keyed by ~executionId~. ~LoomProvider~ deserializes this on mount and calls ~projectionRuntime.seedState()~ for each entry.

** ~LoomProvider~ + ~useLoom~

~LoomProvider~ is a React context provider that:
1. Accepts ~workflowRuntime~ and ~projectionRuntime~ as props.
2. Deserializes and seeds projection state synchronously in the render phase (before the first child render).
3. Exposes both runtimes and the deserialized ~ExecutionState~ via ~useLoom()~.

#+begin_example
LoomProvider (React component)
  props: workflowRuntime, projectionRuntime,
         serializedExecutionState?, serializedProjectionState?
  │
  ├─ First render (synchronous):
  │     if serializedProjectionState:
  │       snapshot = deserializeProjections(serializedProjectionState)
  │       for each [projId, state] in snapshot.states:
  │         projectionRuntime.seedState(projId, snapshot.executionId, state)
  │
  └─ Context value: { workflowRuntime, projectionRuntime, preloadedExecutionState }

useLoom()
  └─ returns the LoomContext value; throws if called outside <LoomProvider>
#+end_example

* Suspend / Resume — Detailed Mechanics

#+begin_example
             FIRST RUN                        RESUME
─────────────────────────────   ────────────────────────────────────
runner(ctx, input)               runner(ctx, input)
  ctx.run(step-A)                  ctx.run(step-A)
    executes normally                VM.hasCompleted → true
    emits STEP_COMPLETED             returns cached output ✓
                                   ctx.run(step-B)
  ctx.run(step-B)                    VM.hasCompleted → true
    executes normally                returns cached output ✓
    emits STEP_COMPLETED
                                   ctx.suspend(cfg)
  ctx.suspend(cfg)                   vm.variables._resumePayload exists
    throw SuspendError               suspendPassthroughConsumed? no
    ↓                                consume flag, return payload
  WorkflowRuntime catches            continues past suspend ✓
    saves Snapshot
    resolves waitForSuspend()      ctx.run(step-C)  ← NEW step
                                     VM.hasCompleted → false
                                     executes normally ✓
#+end_example

The ~suspendPassthroughConsumed~ flag on ~WorkflowContextImpl~ ensures that in a flow with multiple suspends, only the *first unresolved* suspend passes through on each resume. Subsequent suspends still throw if they haven't been resumed yet.

* Design Decisions

** Why event sourcing?

Events are the only durable write. State is always derived. This means:
- Debugging: replay any execution to see exactly what happened.
- Auditability: the event log is a complete, immutable audit trail.
- Resume: re-derive state at any point without storing intermediate snapshots.

** Why ~SuspendError~?

Suspend is implemented as a thrown exception rather than a ~return~ value so that the flow runner function's control flow is unchanged. A ~return~ would require every step after the suspend to be nested in a callback. Throwing lets the code read as a simple linear function while the runtime handles the mechanics.

** Why ~handler$()~ is a no-op at runtime?

Making ~handler$(fn)~ return a ~HandlerRef~ (rather than nothing) means code works correctly without the Vite plugin — development, unit tests, and environments without a build step all work out of the box. The compiler rewrite is a pure optimization, not a correctness requirement.

** Why a cooperative scheduler and not a Fiber reconciler?

Fiber solves a specific problem: a synchronous, CPU-bound render blocking a single UI thread, fixed by slicing work against a frame deadline. That problem does not exist here. Loom's render trees are dashboard-sized — the ~traverseBlueprint~ benchmark walks a 10k-node tree in ~0.47ms, well inside a frame budget (see docs/benchmarks.md) — and where React is the surface, React *already* provides fiber. A second reconciler would duplicate that machinery and add latency for no gain.

The Fiber *principles* — priority, interruptibility, incremental progress — do pay off, but in the *async agentic layer*: cancelling an in-flight LLM call, ordering foreground turns ahead of background planning, bounding tool/effect fan-out. So those principles are implemented as an *ephemeral async scheduler* (~@loom/scheduler~) — a priority-ordered semaphore plus ~AbortSignal~ cancellation — which complements (does not replace) the durable pause/resume already owned by ~SuspendError~ + ~ReplayVM~. On the render side, "useFiber" leverages React's fiber directly, and ~traverseBlueprintAsync~ is the async-traversal seam reserved for future non-React renderers. Every piece is opt-in and default-off; the synchronous fast paths (~traverseBlueprint~, ~schedule~ at ~concurrency: Infinity~, synchronous projection notify) are benched with no regression.

** Why JSON-serializable Blueprints?

Blueprints carry no framework imports. A server-side flow step can produce a Blueprint, store it in the event log, and a completely separate renderer picks it up. This makes server-generated UI, persisted layouts, and cross-language rendering all possible without coupling to React.

** Why a widget registry?

The registry keeps ~@loom/blueprint-runtime~ (pure types) independent of ~@loom/renderer-react~. New widget kinds can be added without touching the framework — register a component, use the widget builder, done.

** Why a separate ~@loom/compiler~ package?

The compiler has a fundamentally different dependency profile — it imports TypeScript's compiler API and Vite's plugin types, neither of which belong in a runtime bundle. Keeping it separate ensures zero build-tool code reaches the browser and keeps the peerDependency on Vite optional.

** Why is the framework UI-agnostic?

~WorkflowRuntime~, ~ProjectionRuntime~, ~EffectRuntime~, and ~@loom/telemetry~ carry zero framework imports. The only React-specific code lives in ~@loom/renderer-react~ (~LoomProvider~, ~useLoom~, ~useProjection~, ~BlueprintRenderer~). This means:

- Angular applications use ~WorkflowRuntime~ directly inside an ~@Injectable~ service; Angular signals bridge Loom events to change detection.
- Vue applications wire ~onEvent~ into a ~reactive()~ store.
- Server-side Node.js scripts use the runtimes with no DOM dependency.
- The ~examples/angular-command-center~ app demonstrates this: it imports ~@loom/workflow-runtime~, ~@loom/telemetry~, and ~@loom/projection-runtime~ directly, uses Angular's DI (~@Injectable~) as the equivalent of ~LoomProvider~, and Angular signals (~signal()~, ~computed()~) as the equivalent of React state hooks. The flow definition and runner are identical to the React cloud-command-center example.

The deliberate separation of ~@loom/renderer-react~ from the runtime packages is what makes this possible without any abstraction cost in the common case.
