# ADR 0130 — Refuse to deliver a sealed payload to a flow that cannot open it

- Status: **Accepted** (2026-10-12) — user approved the kernel guard 2026-10-12; implemented.
- Date: 2026-10-12
- Origin: review of loom #575 (the r2-erasure flake).
- Builds on: [ADR 0110](0110-durable-inbox-and-receive-select.md) (the durable inbox, D9 erasure marker), ADR 0085 (bounded untrusted-content walks).
- Placement: **kernel** (`@loom/workflow-runtime`, the inbox delivery path). Not `@loom/plugin-crypto`.
- Version impact: none. No event kind is added or changed, so `EVENT_SCHEMA` stays 1.24.0; no SPI signature or semantics change (`EVENT_STORE_SPI`, `SNAPSHOT_STORE_SPI`), `KERNEL_ABI` and the wire vectors are unchanged. The only public additions are the error class `SealedPayloadUnreadableError` and its classification. (The 2026-10-14 residuals below add one coordinated bump, `EVENT_SCHEMA` 1.25.0 and `EVENT_STORE_SPI` 2.5.0.)

## Context

`@loom/plugin-crypto` seals fields of an inbox message (`INBOX_MESSAGE.payload`, and the copy in `MESSAGE_CONSUMED.payload`) inside `EncryptingEventStore`, at the store boundary: `{ __loomEnc: "loom/aes-256-gcm", ... }` replaces the plaintext on append and is opened again on read. A node whose store is NOT configured to open that path (a different `sensitive` map, or no crypto plugin at all) reads the same stream through its raw store. Before this ADR it then:

1. handed the flow the envelope as if it were the user's payload, and
2. journaled the envelope as the `MESSAGE_CONSUMED` payload,

so the corruption was durable and replayed deterministically. Nothing refused it. (`__loomEnc` appeared in the kernel only in `blankStream.ts`, a diagnostic.)

## Decision

### D1 — Placement: the kernel, not a 1P crypto check

The failing case is a node that does not have the crypto plugin, or has it configured differently. A check shipped in the plugin cannot run on a node that does not load the plugin, so it cannot protect exactly the node that needs protecting. The inbox delivery path is kernel code that every node runs. The guard is fail-closed, adds no dependency (it recognises the envelope by SHAPE, an own `__loomEnc` key, and knows nothing about keys or ciphers), and the kernel already walks untrusted payloads elsewhere. Kernel placement is the one that holds when the plugin is absent.

### D2 — The invariant

> A message whose payload contains a sealed envelope after the store has had its chance to open it is never delivered to a flow and never journaled as `MESSAGE_CONSUMED`.

At delivery time every envelope the node's store recognised has already been opened on read, so an envelope that survives is by construction "sealed and not openable here".

**What "contains" means.** The sealed paths are configuration (`pathsFor` / `mapPaths` in `EncryptingEventStore` accept nested paths such as `payload.secret`, and the default inbox registration is the whole `payload`). The kernel cannot know a given deployment's paths, so the guard looks for a plain object with an OWN `__loomEnc` key whose value is a STRING (the algorithm id) at the top level or at any depth, in objects and arrays. Inherited keys do not count, and neither does a non-string value (`{ __loomEnc: 1 }` is an ordinary payload): the predicate stays algorithm-independent (it never reads WHICH algorithm) and has fewer false positives. A caller that must relay FOREIGN ciphertext (a `__loomEnc` string key it did not produce) wraps it as a string, for example `JSON.stringify(envelope)`.

**Bounded walk.** Iterative and breadth-first (a shallow envelope is found before any budget matters, and depth cannot blow the stack), capped at `SEALED_WALK_BUDGET` = 100 000 visited nodes, the same budget as `blankStream`'s `carriesKey`. Exhausting the budget (a huge, very deep, or cyclic in-process payload) is NOT "clean": the guard fails closed and treats it as unverifiable (`SealedPayloadUnreadableError.unverifiable`).

### D3 — One shared check, every delivery site

`assertDeliverable(executionId, message)` in `inbox.ts` runs BEFORE any `MESSAGE_CONSUMED` is built, at both sites that consume an inbox message into a flow:

- `WorkflowContext.satisfyFromInbox` (the live run; closure 1 of the lost-wakeup protocol), and
- `WorkflowRuntime.notifyAttempt`'s scan (the notify path: the post-park re-read `afterInboxPark`, `TimerService`, `recoverAbandoned`, the send wake).

Every `MESSAGE_CONSUMED` append was audited. The others write no user payload: the operator discard (`discardInbox`, D8) and the TTL expiry (D10a) journal `payload: null`, and a duplicate delivers nothing (its payload is not copied), so they need no check. An operator discard is deliberately still allowed on a sealed message: it is the escape hatch for a message nobody can open.

### D4 — Park, do not fail; refuse the attempt, not the execution

Every site leaves the message (or the execution) as it was and appends nothing. What the flow sees differs by site, and in none of them does the execution fail:

- **Live run:** the flow stays parked on its receive. Failing the execution would make the refusal permanent (`EXECUTION_FAILED` is terminal), destroying exactly the "stay available for a correctly configured node" property. The run parks normally; the post-park notify pass raises the typed error.
- **Notify path:** `SealedPayloadUnreadableError` is thrown to the caller, which already routes errors to `onStorageError` / `TimerService.onError` / `recoverAbandoned`'s `onError`. The park and the inbox are untouched. The notify pass also writes the durable `INBOX_WAKE_AT` row (whichever caller got there: the post-park read, a send's wake, a timer poll), so a node configured to open the payload picks the message up on its next poll without waiting for a new `send`.
- **Replay:** `ctx.select` / `ctx.receive` serves a RECORDED inbox answer from the folded `_waitAnswers`. If that recorded payload is still a sealed envelope on this node (a capable node journaled it sealed in `MESSAGE_CONSUMED`; this node reads the raw log), the flow is NOT handed the ciphertext. The attempt is refused: the context latches the refusal and seals its journal, so even a flow that swallows the rejection cannot append, complete or park on it, and the context is also frozen like a park: no NEW tool call, effect, decision or child start is dispatched after the refusal (a swallowing flow's later `ctx.run` simply never starts); the runtime rejects the handle with the typed error (`recorded: true`) and writes nothing, in particular no `EXECUTION_FAILED`. The execution stays where it was (a resume of an unrelated gate on that node already appended its own `EXECUTION_RESUMED`, so it reads `running`) for a capable node, which sees plaintext after decryption, passes the check and completes it via `recoverAbandoned` or the next resume. Old logs are unaffected: a plaintext answer is `clean`, so replay on any node is identical to before.

**Head-of-line blocking is per EXECUTION, not per topic.** The live `return delivered` and the notify path's throw both abort the whole scan for that execution, not just the sealed message's topic. A sealed head message therefore holds every topic of that execution for this node until a capable node consumes it or an operator discards it. This is deliberate: skipping the sealed topic and delivering another would let two nodes with different crypto configuration pick different `select` branches (and so different journaled histories) for the same execution. Delivery is FIFO per topic and a cursor cannot skip, so skipping would also silently reorder or lose the sealed message.

**Back-off on an incapable node.** `TimerService.fireInbox` catches `SealedPayloadUnreadableError` and applies an exponential back-off (the re-drive schedule, no attempt cap) that NEVER retires the row, because capable nodes still need it. `onError` is reported on the first refusal and then every 16th, not on every poll. The per-execution back-off map is bounded (1024 entries, oldest evicted); beyond that cap it degrades to periodic polling rather than growing. `recoverAbandoned` treats a refused re-drive like a diverged one: it counts it as `failed` (never `recovered`, no `onRecovered`), reports it through `onError` on the first refusal and then every 16th, and skips that execution on this node for an exponential back-off window (same bounded map, same degradation).

### D5 — The error

`SealedPayloadUnreadableError(executionId, messageId, topic, unverifiable = false)`. Ids only; the message text and fields never carry the ciphertext. It is classified **TERMINAL** in `packages/agent/src/toolFailure.ts` (and its fitness test): retrying on the same node cannot help, and a model must not be told to "try again" by an `isError` result.

### D6 — The ingest rule (`send`)

`send` refuses a payload that contains an `__loomEnc` envelope, with `InboxMessageRefusedError`, before anything is appended, like the forged `$shredded` marker. The walk runs over `JSON.parse(json)`, the same JSON the store persists and the `$shredded` check reads (a `toJSON` can mint an envelope the live object does not show), and AFTER the byte-size check so the parse is bounded. Why this layer and why it is unconditional: sealing happens inside the event-store wrapper at append, AFTER `send` has run, so at `send` time a raw user payload carrying `__loomEnc` is always forged (or relayed ciphertext read through a raw store). A genuine seal can only be produced by the configured store, below `send`. Without the rule a sender could plant an envelope that is indistinguishable from a real seal at delivery, and the guard would be a denial-of-service lever (park any execution's topic) instead of a safety net. A payload too large or deep to check inside the budget is refused as well (fail closed); the default `inboxMaxPayloadBytes` (64 KiB) is far below the budget, so this only bites a raised limit.

Residual: a writer that bypasses `send` and appends to the reserved inbox stream directly is below the kernel's authority (the stream is kernel-owned; only `send` writes it).

## Consequences

What is guaranteed, and what is not:

- **Guaranteed.** A node that cannot open a sealed inbox payload never delivers the ciphertext to a flow and never journals it, on any of three paths: a live consume, a notify-path consume, and a replay of an answer a capable node already journaled. In each case it appends nothing, never fails the execution, and leaves it consumable by a capable node (a durable `INBOX_WAKE_AT` row exists for the notify-path and live refusals, written by `notifyPass`/`markContended`; a PURE replay refusal in `run()` writes no row, the execution is `running`, and it relies on `recoverAbandoned` or the next resume on a capable node). A forged envelope cannot be planted through `send`.
- **Mixed fleet.** "A mixed fleet can no longer corrupt a log" holds for the `INBOX_MESSAGE` and `MESSAGE_CONSUMED` payloads this ADR guards. It is NOT a claim about every sealed field.
- Cost: one bounded walk per delivered (non-duplicate) message, per replayed inbox answer, and per `send`.

Residuals, named:

1. **Other sealed event kinds on an incapable node.** Any other kind a deployment seals through `sensitive` (a step input or output, `EXECUTION_STARTED.input`, an effect result, and so on) is read raw by an incapable node and is not checked by this guard; the kernel cannot tell an app's own field from a sealed one except by this shape, and only the inbox delivery path is a choke point. Run such kinds only on capable nodes.
2. **The snapshot store.** A snapshot holds the folded state, including `_waitAnswers`. A capable node checkpoints PLAINTEXT there, so a snapshot store shared with an incapable node hands that node the plaintext (it passes the replay check, correctly, but the plaintext is at rest unencrypted: already documented in `docs/compliance.md`). Conversely a snapshot that holds a SEALED answer is caught by the replay check like any other. Give snapshots the same encryption as the log, or do not share a snapshot store across differently configured nodes.
3. **A pre-existing plaintext payload carrying a string `__loomEnc` key.** `send` now refuses it, but one journaled before this ADR would be refused on replay forever. No such payload is expected (the key is the crypto plugin's envelope marker).
4. **Head-of-line blocking is per execution** (D4), until a capable node consumes the message or an operator discards it.
5. **A writer that bypasses `send`** (D6).

### R-a — Other sealed event kinds on an incapable node

**Confirmed.** `assertDeliverable` is called at exactly two sites, `packages/workflow-runtime/src/WorkflowContext.ts:2114` (live consume) and `packages/workflow-runtime/src/WorkflowRuntime.ts:4933` (notify scan), plus the replay check at `WorkflowContext.ts:1936` (recorded INBOX answers only, `arm.kind === "inbox"`). Nothing else looks for an envelope. `EncryptingEventStore` seals any event type named in its `sensitive` map (`plugins/crypto/src/EncryptingEventStore.ts:86` `pathsFor`, `:162` append, `:385-415` read and subscribe), and the kernel itself registers kernel-authored kinds: `defineConfig` seals `EXECUTION_STARTED.principal.identity.*` and `OUTCOME_RECORDED.recordedBy` (`packages/app/src/principalPolicy.ts:99-101`). The other places a recorded value reaches a flow are therefore unguarded: `STEP_COMPLETED.output` served on replay (`WorkflowContext.ts:859/887/1077` write it, replay serves it), the `EXECUTION_STARTED.input` handed to the flow, effect and decision results, human-step answers.

**Minimal repro (describe only).** Node A: `EncryptingEventStore` with `sensitive: { STEP_COMPLETED: ["output"] }`; run a flow `const s = await ctx.run(tool); await ctx.receive("go"); return s` to the park. Node B: same stream through a RAW store, `resume`/`recoverAbandoned` after `send("go")`. B replays the recorded step, `s` is `{ __loomEnc: "loom/aes-256-gcm", ... }`, the flow completes, and `EXECUTION_COMPLETED.output` journals the envelope (or a downstream step is invoked with ciphertext as input). Variant with the principal: B reads `principal.identity.tenant` as an envelope object; whether authz fails closed depends on the policy comparing a string to an object (not verified here, it needs a test before anyone relies on it).

**Severity.** Correctness plus integrity of the log, not confidentiality (ciphertext is shown, never plaintext). It is the same durable-corruption class D2 closed for the inbox, so the "mixed fleet can no longer corrupt a log" claim is bounded to two event kinds today. Kernel-authored sealed kinds (principal, outcome) are the part that cannot be handled by "run such kinds only on capable nodes", because `defineConfig` opted the app in without the operator choosing the kind.

**Options.**

1. *Document only.* **Rejected: user chose the stronger option.** Keep Consequences residual 1; add the principal and outcome kinds to `docs/compliance.md` as "mixed fleets must be homogeneous in `security.crypto`". Free; leaves a footgun the kernel itself arms.
2. *Generalise the replay and fold guard to every recorded value.* **Rejected: user chose the stronger option** (its shape sniffing is superseded by the marker; the D2 shape guard stays as the fallback for unmarked streams). One check on the fold input: when the kernel hydrates an event for a VM, any envelope in a kind that is not the inbox raises `SealedPayloadUnreadableError` (`recorded: true`) from the fold or the VM seed, refusing the whole attempt like the replay refusal. Kernel, because only the kernel sees every read. Cost: a bounded walk per event folded, which is O(total payload bytes) on every fold and replay (not per delivered message), so it needs a cheap pre-filter (substring test for `__loomEnc` on the already-serialised JSON where the store keeps it) or a per-execution "checked up to seq" watermark. False positives: an app payload with a string `__loomEnc` key (residual 3) would be refused on EVERY kind. No version bump if it only refuses; a new error context field is additive.
3. *Capability handshake instead of shape sniffing.* **Chosen (user, 2026-10-14).** The store declares what it seals; the runtime refuses to start an execution (or resume one) whose stream header says "sealed under config X" unless this node has X. Needs a stream-level sealed-config marker (a new field on `EXECUTION_STARTED` or a metadata record) and a decorator capability bit. Fixes the class properly and also covers (b) partially, but is a durable-format change: `EVENT_SCHEMA` minor bump (and `EVENT_STORE_SPI` minor if the marker lives in store metadata, as the ADR 0129 incarnation anchor did). It is also the largest option and has no consumer asking.

**Placement.** Option 2 is kernel (read-path choke point; same argument as D1). Option 3 is kernel plus 1P (`@loom/plugin-crypto` writes the marker). Option 1 is docs.

**Recommendation (superseded by the user's decision: Option 3).** Option 2, scoped to the kernel-authored sealed kinds first (`EXECUTION_STARTED` principal and `OUTCOME_RECORDED`), because those are sealed without the operator choosing them. Keep the arbitrary-kind case as documented (Option 1) until a deployment names a second kind; revisit Option 3 only if the user wants the marker for (b) too. Bumps: none for the scoped Option 2 (it adds a refusal, no event shape); `EVENT_SCHEMA` 1.25.0 (+ `EVENT_STORE_SPI` minor) only if Option 3 is chosen.

### R-b — An unencrypted shared snapshot store holds plaintext of sealed content

**Confirmed, but narrower than first logged.** An encrypting snapshot decorator already exists (`plugins/crypto/src/EncryptingSnapshotStore.ts`, `sensitive` dot-paths into the folded `ExecutionState`, same subject key as the events, so a shred erases both). The gap is that it is opt-in and the kernel does not check it on the ordinary path:

- `WorkflowRuntime.ts:6519` and `:7009` call `snapshotStore.save(...)` with the decrypted fold (checkpoint on settle, periodic) whatever the snapshot store is.
- The only cross-check is `LogLifecycle.ts:155`, which refuses COMPACTION when the event store encrypts but the snapshot store does not share its `KeyStore`. A plain checkpoint is not checked.
- `docs/compliance.md:203-206` documents that `variables._waitAnswers` is keyed by a dynamic `waitId`, "which a sensitive path cannot name", so even an `EncryptingSnapshotStore` configured with static paths does not seal a recorded inbox answer. The fix named there is "seal the whole state", which `EncryptingSnapshotStore` does not offer (it maps declared paths only).

**Minimal repro (describe only).** Node A: `EncryptingEventStore` with `INBOX_MESSAGE`/`MESSAGE_CONSUMED` payload sealed, plain `InMemorySnapshotStore`. Run a flow that receives a secret and settles. `snapshotStore.loadLatest(id)` returns state with `variables._waitAnswers.<waitId>.payload` in clear. Shred the subject: the event log is unreadable, the snapshot still serves the secret (and node B, incapable, replays from the snapshot, passes the D4 check because it is plaintext, and completes).

**Severity.** Confidentiality, and erasure-theater (K10.2/A1 is the same hole for static paths, closed by `EncryptingSnapshotStore`). Not a liveness or corruption issue. For the guard itself it is benign (an incapable node served plaintext is correct), so it is a compliance gap rather than a hole in D2.

**Options.**

1. *Document and doctor.* **Chosen, together with 2 and 3 (user, 2026-10-14: BOTH 1P and kernel).** Keep the compliance note; add a `loom doctor` finding (structural `keys` property check already exists, `packages/event-runtime/src/installOptional.ts:28`) "event store seals X but snapshot store does not share the KeyStore". Outward, no kernel change, no bump.
2. *Whole-state sealing mode in `EncryptingSnapshotStore`.* **Chosen (user, 2026-10-14).** A `sensitive: "all"` (or `sealState: true`) option that encrypts `variables._waitAnswers` and the other dynamic-key containers wholesale under the subject key. 1P plugin change; the snapshot payload stays an opaque `ExecutionState` to the store contract, so no SPI change if the decorator re-presents the same shape on load. Cost: snapshots lose partial readability (tooling that inspects `variables`), and a load needs the key (already true for static paths).
3. *Kernel refuses the plaintext checkpoint.* **Chosen (user, 2026-10-14); it is a behaviour change.** At `snapshotStore.save` the runtime refuses (or skips the save) when `security.crypto.events` is composed and the snapshot store lacks the shared `KeyStore`, generalising `LogLifecycle.ts:155` to every save. Kernel behaviour change: a deployment that today checkpoints plaintext starts failing or losing checkpoints (a skip is safe for correctness but regresses read cost). No bump; a behaviour change needing a CHANGELOG "Changed" entry.

**Placement.** Option 1 and 2: 1P (`@loom/plugin-crypto`, `loom doctor`). Option 3: kernel, but the kernel only enforces "same KeyStore", never the cipher.

**Recommendation (superseded: the user chose 1, 2 AND 3).** Options 1 and 2 together, no kernel change; defer Option 3 unless the user wants fail-closed by default (it is the only option that makes the unsafe configuration impossible rather than detectable, and it changes behaviour for existing deployments). Bumps: none for 1/2/3 (`SNAPSHOT_STORE_SPI` unchanged because the shape is preserved).

### R-c — Head-of-line blocking is per execution

**Confirmed, and designed.** `WorkflowContext.ts:2116` (`return delivered`) abandons the whole scan, and `WorkflowRuntime.ts:4933` throws out of the whole notify scan; the scan loop covers every topic of the execution (`for (const w of waits)` at `:4925-4932`), so a sealed head on topic A holds topic B's deliverable messages. D4 gives the reason: skipping would let nodes with different configs pick different `select` branches.

**Repro (describe only).** Execution parks on `select([receive("a"), receive("b")])`; `send("a", sealedUnderNodeA)` then `send("b", "plain")`. Capable node A consumes `a` (lowest `inboxSeq`) and completes the select with arm `a`. Incapable node B refuses the scan and never delivers `b`: correct, since delivering `b` on B would diverge from A's branch.

**Severity.** Liveness only, on the incapable node only; capable nodes are unaffected and the log is never corrupted. The harm is a fleet whose only runner of an execution is incapable (a misconfigured deploy): the execution stalls behind a message nobody can open, with an `onError` every 16th poll and an operator escape hatch (`discardInbox`, D3; TTL expiry D10a if configured).

**Why most options are unsound.** Skipping a sealed topic is unsafe for the reason in D4. A weaker rule, "block only messages with a higher `inboxSeq` than the sealed one", is already what FIFO plus a deterministic first-answered-arm gives for a single `select`; it does not unblock any case that is not already blocked by that ordering, so it buys nothing.

**Options.**

1. *Document and accept (WONTFIX in the kernel).* Head-of-line semantics are KEPT (user, 2026-10-14); the document-only stance is **rejected as the whole answer: user chose the stronger option** (keep + quarantine). Name it as designed (already Consequences residual 4); point operators at `discardInbox` and the journaled TTL. Zero change.
2. *Observability, no semantics change.* Kept as a by-product (the quarantine slice emits the blocked-state data); a standalone analytics advisory is not part of this decision. Surface a stuck-behind-sealed state: an `onError` payload carrying the blocked topics and the sealed message's age, and an analytics advisory (`@loom/analytics`, advisory per ADR 0034) "execution X blocked behind sealed message M for > T". 1P, no bump.
3. *Operator quarantine verb.* **Chosen (user, 2026-10-14); the shape below is superseded by D9** (a dedicated event pair that holds the topic and preserves original order on release, not a `MESSAGE_CONSUMED` dead letter). A first-class `quarantineInbox` that journals the sealed message as a dead letter (`MESSAGE_CONSUMED` with `payload: null` plus a reason) so the head clears while preserving the audit trail, an explicit, human-triggered version of the existing discard. Possibly already expressible by `discardInbox` with a reason; if a new reason value is needed it is an additive field. Kernel only if a new journaled reason is required (`EVENT_SCHEMA` minor), otherwise no bump.

**Placement.** 1: docs. 2: 1P analytics. 3: kernel if it adds a journaled reason, else a recipe over `discardInbox`.

**Recommendation (superseded: keep the semantics AND add the quarantine verb).** WONTFIX the semantics (Option 1) and do Option 2 so the state is visible; do Option 3 only if `discardInbox`'s journal does not already record who discarded and why (check before proposing a schema bump). Bumps: none for 1/2; `EVENT_SCHEMA` minor only if 3 needs a new reason value.

### R-d — A replay refusal writes no wake row

**Confirmed.** `markContended` (`WorkflowRuntime.ts:4861`) is reached only from `notifyPass`'s catch (`:4847`), i.e. the notify path. The replay refusal is raised inside `run()` (`WorkflowContext.ts:1936-1945`, handled `WorkflowRuntime.ts:6874-6885`), which warns, rejects the handles and returns: no `timerStore.schedule`, no event. The execution is left `running` (an unrelated resume already appended `EXECUTION_RESUMED`) or whatever it was. The ADR already admits this (Consequences, "a PURE replay refusal in `run()` writes no row").

What recovers it today: `recoverAbandoned` on a capable node (`recoverAbandoned.ts:280`, `status` running or pending), but that needs an app to run the sweep with an `isAbandoned` predicate or a lease store (`recoverAbandoned.ts:60-75`, the predicate is REQUIRED with no default), and the staleness window must elapse. The incapable node's own sweep skips it for a back-off window (`:392`, `:491`).

**Minimal repro (describe only).** Capable node A journals `MESSAGE_CONSUMED` with a sealed `payload`, then crashes before the next step; the execution is `running`. Incapable node B resumes (`resume` of any gate, or a sweep): replay hits `WorkflowContext.ts:1936`, B refuses; no timer row exists. Node A is later redeployed capable but no `send`, no timer, no resume arrives, and the app runs no sweep: the execution sits `running` indefinitely.

**Severity.** Liveness, narrow: needs a mixed fleet AND no sweep on a capable node. Not a confidentiality or correctness issue.

**Options.**

1. *Document that a sweep is the contract.* **Rejected: user chose the stronger option.** State that a deployment with an incapable node must run `recoverAbandoned` on a capable node; no code.
2. *Write the durable wake on a replay refusal too.* **Chosen NOW (user, 2026-10-14).** In the `run()` catch at `WorkflowRuntime.ts:6874`, call `markContended(executionId)` (same best-effort `.catch(onStorageError)`). Then `TimerService`'s inbox poll (`INBOX_WAKE_AT`) re-drives it on any node. But the wake row's job today is to trigger the NOTIFY scan for a PARKED execution; for a `running` execution the notify path may find no unanswered park and retire the row, so the row alone does not re-run the flow. Either the poll must learn to `resume`-redrive a running execution carrying the row, or the row must be paired with a distinct reason. Kernel, small, no event change; needs a decision on what the poll does with a `running` execution (this is why it is not a one-liner).
3. *Park the execution on the refusal.* **Rejected** (breaks "appends nothing"; also user chose Option 2). Instead of leaving it `running`, journal a reserved park (like `FLOW_DIVERGED_GATE`, ADR 0113) so it is `suspended` and every existing wake path (notify, timers, `recoverAbandoned`'s parked-execution notify pass) applies. Strongest liveness, but it appends an event on a refusal, which contradicts D4 "appends nothing" and the property that an incapable node never writes about an execution it cannot read; it also adds a reserved gate name (`EVENT_SCHEMA` minor if the gate is a new journaled condition kind, none if it reuses `SuspendError` with a reserved `on`). Highest risk.

**Placement.** Kernel (1: docs).

**Recommendation (superseded: Option 2 now).** Option 2 only after the poll semantics for `running` executions are decided; until then Option 1 plus a `recoverAbandoned` recipe in `docs/` naming this case. Reject Option 3 (breaks the appends-nothing rule). Bumps: none for 1 and 2; `EVENT_SCHEMA` minor only for 3.

## Accepted design (2026-10-14)

Everything below is design; no code exists yet. One coordinated version bump carries all schema and SPI changes, reserved FIRST (slice S1, the W2-0 pattern: freeze the shapes, ship the constants, the reserved fold handlers and the optional SPI method with no behaviour, then the behaviour slices fill them in). `docs/` registries (compatibility matrix, spec section, cheatsheet, usage strings) are updated in slice S1, not in this ADR PR.

### D7 (R-a) — The capability marker: per-envelope `metadata.seal`, no new event

**Where it lives.** The kernel assigns sequence numbers, so the crypto plugin cannot insert a marker EVENT into a stream, and a store-side side table would not commit atomically with the sealed row (a crash between them leaves sealed data unmarked, the worst failure). The marker therefore rides ON the sealed envelope, in `EventEnvelope.metadata` (an existing open `Record<string, unknown>`), written by `EncryptingEventStore` in the SAME append that seals the fields:

```ts
// EventEnvelope.metadata.seal  (EVENT_SCHEMA 1.25.0, reserved key)
interface SealMarker {
  v: 1;
  cipher: string;            // e.g. "loom/aes-256-gcm" (the algorithm id the envelopes carry)
  covers: readonly string[]; // sorted, deduped "EVENT_TYPE.dot.path" entries actually sealed in THIS envelope
}
```

It is stamped on exactly the envelopes in which at least one field was sealed (not on every envelope of an encrypting node), so `covers` is exact, never stale after a config change, and carries no key material, key id or subject. "Stream-level" is the aggregate: a stream is sealed iff any of its envelopes carries `metadata.seal`. This covers every kind the node seals through `sensitive`, including the ones `defineConfig` registers itself (`EXECUTION_STARTED.principal.identity.*`, `OUTCOME_RECORDED.recordedBy`) and `STEP_COMPLETED.output`, with no per-kind kernel code: the marker is derived from what was actually sealed.

**The SPI (EVENT_STORE_SPI 2.5.0, optional, additive).**

```ts
interface SealingCapability {
  readonly cipher: string;
  /** Every "EVENT_TYPE.path" this node's store seals AND therefore opens. */
  readonly covers: readonly string[];
  /** True iff this node can open an envelope stamped with `marker` (same cipher, every entry of marker.covers is opened here). */
  opens(marker: SealMarker): boolean;
}
interface EventStore {
  /** 2.5.0. Absent, or returning undefined: this store seals nothing and opens nothing. */
  sealingCapability?(): SealingCapability | undefined;
}
```

Listed in `OPTIONAL_EVENT_STORE_METHODS`, so every decorator must forward, override or refuse it (compile error otherwise): plain decorators forward; `EncryptingEventStore` overrides it from its `sensitive` map (live, so `registerSensitive` is reflected); `ShardedEventStore` FAILS CLOSED on disagreement (it defines the method when ANY shard has it, and a shard that lacks the method entirely counts as sealing nothing, i.e. `undefined`, so an encrypting shard beside a plain SQLite/InMemory shard throws; when NO shard has the method it is omitted, as for any all-plain fleet): if every shard reports an identical capability (same `cipher`, same `covers`) it returns that capability; if no shard seals it returns undefined; any other combination (some shards sealing and some not, different `covers`, different `cipher`) throws the exported, typed misconfiguration error `ShardSealingMismatchError` (carries the shard indexes and each shard's cipher/covers, never key material). It is evaluated LIVE on every `sealingCapability()` call, because `registerSensitive` can change one shard's capability at runtime. The reason is that two questions share this one method and must never diverge: D7 asks "what can this node open" and D8 asks "does this store seal at all" (non-empty `covers`); an intersection answers only the first, and would report a store that seals some paths on some shards as sealing nothing, letting D8 allow a plaintext checkpoint. A store that does not claim 2.5.0 simply lacks the method: that IS the fallback, and it means "incapable", which is the correct reading for a store that cannot open sealed data. Conformance: `runEventStoreConformance(..., { eventStoreSpi: "2.4.0" })` skips the new cases (the ADR 0129 option).

**The check (kernel, before fold and replay).** `assertStreamReadable(executionId, events, store)` is called at every funnel through which stored envelopes reach the fold or the VM seed (the implementer enumerates them; a fitness test pins the list, in the style of `testTimeoutGuard`): for each envelope with `metadata.seal`, if `store.sealingCapability?.()?.opens(marker)` is not true it throws `SealedStreamUnreadableError(executionId, sequence, covers)` before anything is folded, handed to a flow, journaled or authorised against. Cost is O(1) per envelope (a property read), not a payload walk, so it also replaces the pre-filter worry of the rejected shape-sniffing option. **The principal is refused BEFORE the policy is consulted (user ruling 2026-10-14, from the S0 probe, PR #579).** S0 found that on a raw node `ownerForAuthz` hands the policy `owner === undefined` for a sealed principal, so a denial rests ENTIRELY on the policy's `unknownOwner: "deny"` default: with `unknownOwner: "allow"` a raw node ALLOWS a stranger to `loadState` (fail-open), and the legitimate owner is locked out too (closed, but not correct, and untyped). That is not acceptable for a kernel invariant. The kernel therefore refuses with `SealedStreamUnreadableError` (the denial-shaped refusal described under "The error", independent of `unknownOwner` and of any policy) at `ownerForAuthz`'s read of `first`, BEFORE `authzDenial` runs: (a) when `first.metadata.seal.covers` names any `EXECUTION_STARTED.principal.*` entry (or `OUTCOME_RECORDED.recordedBy` for the outcome path) and this node cannot open it; and (b) as a structural backstop for an UNMARKED legacy stream, when the principal read for authorization is itself a ciphertext envelope (a plain object with an own string `__loomEnc`, an O(1) check on the small principal object, never a payload walk). (b) is the single place where an unmarked stream is refused on shape, because the alternative is a fail-open authorization decision; a plaintext principal is never refused. A system-granted internal read does not consult the principal and is unaffected. **The refusal LOOKS LIKE A DENIAL to the caller (user ruling 2026-10-14; see "The error" below): it is an `ExecutionDeniedError` whose caller-visible shape is the ordinary unknown-owner denial, so a caller who names an id learns nothing about whether it exists or is sealed.** The owner is not told the fix by the error; the sealed / key-unavailable detail goes to operators only.

**The error: a denial to the caller, detail to the operator (user ruling 2026-10-14; removes the former "existence leak" accepted residual).** A distinct typed refusal would be an existence oracle: a caller naming an id would learn that it exists and is sealed. So the stream-level refusal is not a new caller-visible outcome:

- `SealedStreamUnreadableError extends ExecutionDeniedError` (including the `reason: "key-unavailable"` variant, which stays a distinct internal cause, not a distinct class). Constructed as `new SealedStreamUnreadableError(op, executionId, detail)` it calls `super(op, executionId, UNKNOWN_OWNER_REASON)`, where `UNKNOWN_OWNER_REASON` is the exact string the default `executionAccessPolicy` gives an execution whose owner it cannot establish (`"the execution's owner is unknown to this policy"`, exported from one module so the two cannot drift). Everything a caller can observe equals the ordinary denial of the same call: `name` stays `"ExecutionDeniedError"` (the subclass does NOT override it), `message`, `op`, `executionId`, `reason`, and the call stack's top frame is the same `denyOp` site. The sealed detail (`reason: "marker-unopenable" | "key-unavailable"`, `sequence`, `covers`) is NOT a property of the error: it lives in a module-private `WeakMap<Error, SealedDetail>` and is read only through `sealedDetailOf(err)`, exported from the operator entry (`@loom/workflow-runtime/operator`, not the main index), so JSON-serialising or enumerating the error at an RPC/HTTP edge cannot leak it. Stack frames are not a trust boundary (an in-process caller already shares the process); edges serialise `name`, `message`, `op`, `executionId`, `reason` only.
- **Where it is thrown.** Only where the caller has NOT yet proven anything: the stream-level reads that precede or feed authorization (`ownerForAuthz`'s read of `first`, `loadState`, `send`, `resume`, `cancel`, `discardInbox`, `quarantineInbox`, `releaseInbox`, `recordOutcome`). It goes through the same `denyOp` as any denial, so `onExecutionDenied(request, reason)` fires with the GENERIC reason, identical to the ordinary denial's. The existing delivery-guard refusal `SealedPayloadUnreadableError` (D4/D5) is unchanged and stays a distinct error: it is raised on the node's own notify/replay paths and on `releaseInbox("deliver")` AFTER the caller passed authorization on a plaintext, openable principal, so it tells the caller nothing they have not already proved they may know.
- **What operators see.** Every refusal is also reported through the runtime's operator channel (`onStorageError`, the channel the delivery-guard refusals already use, plus the structured log line) with the real cause: the error object itself (use `sealedDetailOf`), carrying `executionId`, `sequence`, `covers` and `reason`. The first-then-every-16th reporting and the `sealedBackoff` apply to it unchanged. A caller sees "denied"; an operator sees "sealed, cannot open here, fix: run a capable node / supply the key".
- **The `EXECUTION_DENIED` audit fact.** An ordinary denial of `resume`/`cancel` best-effort records `EXECUTION_DENIED { op, reason?, actor? }`. For a sealed refusal the fact, if written, would be byte-identical in shape to the ordinary denial's (`op`, the GENERIC reason, the caller's own `actor`; never `covers`, `sequence`, `reason: "key-unavailable"` or any cipher or key detail), so it could not leak more than today's. **Decision (confirmed by the user 2026-10-14): it is NOT written.** (1) The ADR 0130 invariant is "a refusal appends nothing"; an incapable node appending a plaintext fact into a log it cannot read is exactly what the guard exists to prevent, and the unfenced `afterSequence + 1` append would also let any stranger who can reach an incapable node burn sequence numbers on the owner's stream (a DoS on the capable writer). (2) The audit need is met without it: `onExecutionDenied` fires (generic reason) and the operator channel carries the true cause. S2 asserts the log is untouched. If a deployment later wants the fact, the shape above is the only permitted one.
- **How internal code still tells it apart.** `instanceof SealedStreamUnreadableError` (an `ExecutionDeniedError` subclass check, so it must be tested BEFORE any generic `ExecutionDeniedError` handling), and a brand guard `isSealedUnreadable(e)` (a `Symbol.for("loom.sealedUnreadable")` property, true for BOTH `SealedStreamUnreadableError` and the existing `SealedPayloadUnreadableError`, which cannot share a base class with `ExecutionDeniedError`). `TimerService.fireInbox`, `recoverAbandoned`, the replay refusal, the notify scan and the back-off maps test the brand guard, so the ADR 0130 back-off and "first then every 16th" reporting apply unchanged. `packages/agent/src/toolFailure.ts` (and its fitness test) classifies both TERMINAL, and checks the brand BEFORE the `ExecutionDeniedError` branch; a model sees only the generic denial text. Like the existing refusals it never fails the execution.
- **Indistinguishability, stated exactly.** Under the default deny-unknown-owner policy a missing id and a sealed id both return the same `ExecutionDeniedError` for every gated op. Two configurations keep an oracle, both of which already expose unsealed executions to a stranger: no authorizer at all, and a policy with `unknownOwner: "allow"` (documented UNSAFE), where a missing id is "not found" rather than denied. A custom `ExecutionAuthorizer` whose unknown-owner reason differs from `UNKNOWN_OWNER_REASON` shows a different string: such a deployment should return the exported constant for an unknown owner. These are configuration caveats, not residuals of this design.

**A node whose KeyStore lacks the key (S0 fix-round finding, PR #579; user-directed 2026-10-14).** A `defineConfig` node with crypto but a DIFFERENT or EMPTY `KeyStore` is the same fact as "cannot open", reached through the other door: the marker (`covers`, `cipher`) matches, but the key for the envelope's subject is absent here. Today the encrypting store reads `keys.get(subject) === null` and throws `PayloadShreddedError` from inside the read, before the authorizer, on `loadState`/`send`/`resume`/`discardInbox`/`recordOutcome` (only `cancel` reaches the authorizer, typed-denied): closed, but UNTYPED, and it reports "erased" for what is really "key not here", conflating a misconfigured node with a crypto-shred. The fix has two parts.
1. **Distinguishing the two (the `KeyStore` cannot).** `KeyStore.get` returns `null` for "never existed OR destroyed" by contract (`keystore.ts`), so the key store alone cannot tell them apart and the SPI is not changed. What CAN tell them apart is the log: a real shred (`shredSubject`) writes a durable `PAYLOAD_SHREDDED` tombstone to every affected execution at shred time (and ADR 0106 compaction folds it into the snapshot's state). So, when the key is `null`, `EncryptingEventStore` (and `EncryptingSnapshotStore`, `EncryptingSnapshotStore.ts:92`) decides: a tombstone present for the subject (the raw tip of the stream, or the latest snapshot's folded shred record, reusing the shred-status helper in `shred.ts`) => a real shred, `PayloadShreddedError` exactly as today (erasure semantics, tolerant `onShredded` modes, tombstone-aware cancel all unchanged); NO tombstone => `KeyUnavailableError` (new, plugin-level, carries a stable `code`, the subject id and the stream id, never ciphertext). The residual ambiguity is stated, not hidden: between `keys.destroy(subject)` and the tombstone write of a `shredSubject` that failed part-way (the documented retry window, `ShredIncompleteError`), a read has no tombstone and reports `KeyUnavailableError`, a refusal (denial-shaped to the caller, D7) that clears when the retry completes; it never reports plaintext and never mislabels a shred as available.
2. **Typed, and before the policy.** `KeyUnavailableError.code` lives in `@loom/event-runtime` beside the store error contract (the crypto plugin already depends on it, the kernel does not depend on the plugin). The kernel's read funnels (the same list as `assertStreamReadable`, including `ownerForAuthz`'s read of `first`) translate it into `SealedStreamUnreadableError` with `reason: "key-unavailable"` (versus `"marker-unopenable"` for the capability check), so the caller sees ONE outcome for "this node cannot open this stream" whichever way it cannot (the generic denial above; the cause is operator-only), the `isSealedUnreadable` handlers (back-off, first-then-every-16th) apply, and the authorizer is never invoked. `PayloadShreddedError` stays exclusively the erasure outcome. Inbox streams keep their non-loud read (D9 of ADR 0110) and are unaffected.

**What an unmarked stream means (exactly).** An envelope without `metadata.seal` makes NO claim. It is either truly plaintext, or it was sealed by a writer that did not stamp (a pre-1.25.0 node, a third-party sealing decorator, a store whose decorator stack dropped metadata). The kernel therefore does not read absence as "safe to open": it behaves EXACTLY as it does today on that envelope, with the D2/D4 shape guard still guarding inbox payloads. Nothing is refused because a marker is missing, and nothing existing is bricked: a pre-1.25.0 stream with no markers folds and replays byte-identically on every node. The marker only ADDS refusals, and only where a writer said "sealed" and this node cannot open it. Documented limit: a stream sealed by an unstamping writer keeps the pre-0130 mixed-fleet exposure for its non-inbox kinds; upgrading the writer fixes new envelopes, and old ones are not back-filled (no rewrite of a log).

**Rolling upgrade.** A pre-1.25.0 node ignores unknown `metadata` keys (the fold reads only the keys it knows; to be verified by a test in S1), so it keeps today's behaviour on marked streams; it is a node that does not yet have the protection, not one that corrupts differently. Deploy order: upgrade every node, then rely on the marker. The envelope grows by `~60-200` bytes per sealed envelope (the `covers` list); hash chains (`plugins/audit-chain`) hash the envelope the wrapper appended, so the marker is inside the chain, deterministically.

**Replay byte-identity.** Logs written with no crypto plugin are byte-identical to before. For an encrypting node the envelope already differs run to run (a random IV in every ciphertext), so DST seeds that compare logs run with the **deterministic cipher seam** (user ruling 2026-10-14, slice S2): `EncryptingEventStore` (and `EncryptingSnapshotStore`) take an injectable IV/nonce source, `ivSource?: (ctx: { streamId: string; sequence: number; path: string }) => Uint8Array`, whose production default is `crypto.randomBytes(12)`. The seam exists so a seeded simulation can derive the IV from `(seed, stream, sequence, path)` and compare logs byte for byte. A reused IV under AES-GCM breaks confidentiality, so the seam is exported ONLY from a `@loom/plugin-crypto/testing` subpath (never the main entry), the constructor refuses a custom `ivSource` when `NODE_ENV === "production"`, and a fitness test pins that the default path calls `randomBytes` and that no non-test source passes the seam. The marker (a pure function of the config and the event type) adds no new nondeterminism.

**False positives.** None from content: the marker is written by the sealer, never inferred from a payload, so an app payload with a string `__loomEnc` key (residual 3) is not affected by D7. (An app can still forge a `metadata.seal`? No: `metadata` is set by the runtime and the store; a flow cannot set envelope metadata. The `send` rule D6 is unchanged.)

### D8 (R-b) — Whole-state snapshot sealing (1P) and the kernel refusal of a plaintext checkpoint

**1P.**
- `EncryptingSnapshotStore` gains `sealState: true` (mutually exclusive with `sensitive`, which stays for compatibility): the folded `ExecutionState` is serialised and sealed as ONE envelope under the same subject key as the events (so a shred erases both), and stored as `{ executionId, workflowId, <the snapshot's index fields the store contract needs in the clear>, state: { __loomEnc: ... } }`. The exact plaintext index fields are whatever `SnapshotStore.loadLatest`/`list` must filter or order by (the implementer reads the contract; none of them are payload). This is what covers the dynamic `variables._waitAnswers.<waitId>` keys that no static path can name. A load with a destroyed key throws `PayloadShreddedError`, as today. **Slot binding (AAD).** The whole-state envelope is a new format, so it is bound to its slot: AES-GCM additional authenticated data is `loom-snap-v1|<executionId>|<sequence>`, and the envelope carries `aad: "loom-snap-v1"` so the format is self-describing (the bound context itself is not stored; it is re-derived from the row on load). A sealed row copied into another execution's slot, an older snapshot rolled into a newer sequence, and an envelope without the marker all fail to open with the typed `SnapshotUndecryptableError` (never raw GCM text, and distinct from `PayloadShreddedError` so a defect cannot read as an erasure). `encryptValue`/`decryptValue` take AAD optionally, so field-level (static-path) envelopes are unchanged. **Downgrade.** `legacyPlaintext: "load" | "refuse"` (default `"load"`: old snapshots stay readable, per the migration paragraph below): `"refuse"` throws `PlaintextSnapshotRefusedError` on any state that is not a whole-state envelope, so a plaintext row cannot be substituted for a sealed one once none legitimately remain. **Legacy opening.** A snapshot written by a static-path store has nested envelopes; in `sealState` mode the old paths are unknown, so each envelope-shaped value is tried and left exactly as stored if it does not open (an application's own ciphertext under another key no longer fails the load); the optional `legacySensitive` paths restrict this to the named paths (without it, an application value sealed under the SAME subject key by the same helper is opened). **Census.** `loom doctor` reads the wiring, not the data at rest: `SnapshotStore` has no enumerating method, so counting plaintext snapshots still under a `sealState` store would be a per-backend full scan. That residual is documented, not detected. **Content GC.** A `sealState` snapshot read RAW is one opaque envelope, so `sweepUnpinnedContent` cannot see the refs it cites; an erasing pass throws `SealedSnapshotScanError` ("pass the decrypting snapshot store") and a `dryRun` lists `sealedSnapshots`. The store exposes the structural marker `sealsWholeState: true` (a plain property, like `keys`, so neither `loom doctor` nor the kernel depends on `@loom/plugin-crypto`).
- `loom doctor` finding (`snapshot-plaintext-under-encrypting-events`, severity error): event store seals (`sealingCapability` has covers, or the structural `keys` probe) while the snapshot store neither shares the `KeyStore` nor reports `sealsWholeState`; also warns when `sensitive` (static paths) is used, naming `_waitAnswers`. Names the fix and the `allowPlaintextCheckpoints` escape.
- `docs/compliance.md` is updated in the same slice (the `_waitAnswers` caveat becomes "use `sealState`").

**Kernel (behaviour change).** The kernel knows the event store seals from the D7 capability: `eventStore.sealingCapability?.()` with non-empty `covers`. No new SPI is needed: the snapshot store is judged structurally, as `LogLifecycle` already does for compaction (`keysOf`), extended with `sealsWholeState`.

- **Rule.** When the event store seals, a checkpoint (`snapshotStore.save`, the on-settle and periodic sites in `WorkflowRuntime`, and `LogLifecycle` which already has its own stricter check) is permitted iff the snapshot store `sealsWholeState === true` and shares the event store's `KeyStore`. A static-path `EncryptingSnapshotStore` is NOT sufficient (it leaves `_waitAnswers` plaintext).
- **When it fires.** At runtime CONSTRUCTION (fail fast, the primary form): `new WorkflowRuntime`/`defineConfig` throws `PlaintextCheckpointError` (a config error, listing the two ways out) when both stores are known and the rule fails. Defensively again at each `save` (stores can be swapped or composed late): there it throws the same class, which the existing best-effort checkpoint `try/catch` surfaces through `onStorageError` WITHOUT failing the run (a checkpoint is an optimisation; the log is the source of truth). A runtime with no snapshot store is unaffected.
- **Error type.** `PlaintextCheckpointError extends Error` in `@loom/workflow-runtime` (fields `executionId?`, `reason: "not-sealed" | "keys-not-shared"`), not retryable.
- **Escape hatch (kept, confirmed by the user 2026-10-14).** `security.crypto.allowPlaintextCheckpoints: true` (explicit, off by default; the opt-out for a snapshot store on an encrypted volume and the migration path) skips the rule and makes `loom doctor` downgrade to info. It is the migration path for a deployment that cannot move yet.
- **Migration.** An existing deployment with an encrypting event store and a plaintext snapshot store stops booting with a message naming the fix, which is the intended behaviour change; CHANGELOG "Changed" (breaking-by-design) entry, and the `loom doctor` finding ships in the PREVIOUS slice so it can be run first. Snapshots already written in plaintext are not rewritten or deleted (no pruning, user ruling); they stay readable. A sealed snapshot loaded by a node that cannot open it (top-level `__loomEnc` in the loaded state) raises `SealedStreamUnreadableError` from the load path, never a half-state.

### D9 (R-c) — `quarantineInbox` / `releaseInbox`: a journaled per-TOPIC hold that preserves original order

**User rulings (2026-10-14).** (1) The held bytes live in the reserved stream `__loom_quarantine__:<chainId>`, default cap 256 per chain. (2) A release MUST preserve the message's ORIGINAL order. The first cut of this section (release re-sends the message at the topic's tail) is **rejected**, and the "re-delivered at the tail" residual is gone.

#### What "original order" means, and the three designs

The inbox promises FIFO **per topic** and nothing across topics (D5 of ADR 0110; `select` takes the first arm, in park order, that has a deliverable message). "Original position" therefore means: relative to the other messages of the SAME topic. The folded state is one monotone number per topic, `_inbox.cursors[topic]`: every stream entry at or below it is disposed of (consumed, skipped as a duplicate, discarded), and the next message delivered is the first one above it. Once a later message `m2` of a topic has been delivered, its cursor is above the held `m1`, and any way of delivering `m1` afterwards shows the flow `m2` before `m1`.

| Design | Original order? | Verdict |
|---|---|---|
| (i) The quarantine HOLDS THE TOPIC: no later message of that topic is delivered until the held one is released or discarded; other topics continue | **Yes, by construction.** The flow can never see `m2` before `m1`, because `m2` is never delivered while `m1` is held. | **Chosen** |
| (ii) A cursor with holes (a consumed-set / skip-list): later messages flow, the held one is delivered later under its original `inboxSeq` | **No.** The flow sees `m2` then `m1`: out of order, and `select` can already have chosen a branch from `m2`. Only the label (`inboxSeq`) is original. Rejected. | rejected |
| (iii) A rewindable cursor | Impossible: it would re-deliver consumed messages (their answers are already folded and replay serves them), breaks cursor monotonicity and the dedupe window, and makes replay depend on when the rewind happened. | rejected |

**Plainly: only (i) honours original order, and it changes residual (c) from per-EXECUTION head-of-line (D4) to per-TOPIC head-of-line for a quarantined topic.** The trade-off, stated: a quarantine is a decision that the held topic stops delivering to every node that cannot open the held message, and to capable ones only until the first capable node lifts the hold by itself ("Auto-release" below); it stays held for as long as NO capable node runs, or until an operator releases or discards it. The topic's later messages accumulate behind the hold (they are bounded by the per-topic backlog and cap, `InboxFullError` for THAT topic only on per-topic streams). What the user gains over today: the execution's OTHER topics deliver again (today a sealed head stalls them all), the stall is a journaled fact every node agrees on (deterministic `select`, no per-poll refusal and `onError` storm for the held topic), and the sealed message no longer pins the original stream (see "Cursor and trim"). If a deployment would rather have the topic keep flowing, its answer is `discardInbox` (the message is gone), not a quarantine that reorders.

#### The facts (owner's log, kernel-stamped, folded only from a kernel-stamped envelope like the discard facts; both are `ignorable` for the fence, like `MESSAGE_CONSUMED`)

```ts
// INBOX_QUARANTINED: the topic's head message is held.
{ topic: string; inboxSeq: number; key: string /* dedupeKeyOf(msg), 64 hex */; messageId: string /* raw, <=256 */;
  heldAt: number /* seq in __loom_quarantine__:<chainId> */; operator: Owner; reason?: string /* <=256, event only */ }
// folds: _inbox.cursors[topic] = max(cursor, inboxSeq)          // the original entry is disposed of
//        _quarantined[topic].push({ key, inboxSeq, heldAt, state: "held" })   // FIFO queue per topic
//        NOT added to the dedupe window (the release delivery must not read as a duplicate)
//        ignored when total entries would exceed QUARANTINE_FOLD_CAP (1024, a fold constant)

// INBOX_RELEASED: the topic's OLDEST held entry is released, or dropped.
{ topic: string; key: string; messageId: string; disposition: "deliver" | "discard";
  operator?: Owner;   // present on a MANUAL release (releaseInbox); absent on an automatic one
  auto?: true;        // present, and only with disposition "deliver", on an AUTOMATIC release (below)
  reason?: string }
// exactly one of `operator` / `auto` is present; a fact with both or neither is ignored by the fold
// folds: only for the topic's first entry, and only if its state is "held" (else ignored):
//   "deliver": state = "released" (deliverable, still ahead of everything above the cursor)
//   "discard": entry removed; key added to the dedupe window (a sender's retry of that id is a duplicate)
```

`_quarantined` is `{ [topic]: Array<{ key, inboxSeq, heldAt, state: "held" | "released" }> }` (a topic whose queue becomes empty is deleted from the record, and the `_quarantined` variable itself is deleted when the record becomes empty, in both `MESSAGE_CONSUMED` and the `INBOX_RELEASED` discard branch, so a full hold, release and consume cycle returns to exactly the never-quarantined shape): no reason, no payload, ~100 bytes per entry, hard-capped by the fold at 1024 entries (a fold cannot read a runtime setting, the lesson of ADR 0110 D6; the runtime default `quarantineMax` is **256** and may be raised to the ceiling, never above). The queue shape is always `released? held*` (AT MOST ONE released entry: the fold can only release the oldest held one, and the delivery consumes it before the next release; a carried seed with two `released` entries for a topic is invalid and ignored) because release only ever takes the OLDEST held entry (a release of a younger one is `invalid`: releasing it first would deliver out of order).

**One existing handler changes, gated on `_quarantined`.** `MESSAGE_CONSUMED` additionally removes the topic's first entry when it is `released` and its `key` equals the fact's `messageId` (the dedupe key). A log with no `_quarantined` folds byte-identically to before (golden vectors, S1). The delivery fact is otherwise unchanged: `inboxSeq` is the original sequence, which is at or below the cursor, so the cursor does not move and the dedupe window records the key like any delivery.

#### Delivery rule (the one rule every node, the live run and the notify scan apply, from FOLDED state only)

For a wait on topic T, in park order as today:
1. If `_quarantined[T]` starts with `released` entries, the next message is the FIRST released entry, read from the quarantine stream at `heldAt` (it precedes everything above the cursor, which is its original position). It passes `assertDeliverable` like any message (an incapable node refuses, D4, and the refusal is again the execution-wide head-of-line for that node).
2. Else if `_quarantined[T]` starts with a `held` entry: a node that CAN open the copy AUTO-RELEASES it (below) and delivers it as in step 1, in the same atomic batch; a node that CANNOT open it has NO deliverable message on T and skips T entirely (does not read it, does not refuse, does not report except the one operator signal "held, awaiting a capable node"). Other topics are scanned. Skipping is deterministic because it depends on a journaled fact plus this node's own ability to open the copy, which the batch's fence re-validates; the choice is recorded in the log before it reaches a flow, and replay serves recorded answers.
3. Else T is read past its cursor as today.

`select` across topics therefore stays deterministic across nodes: the set of satisfiable arms is a function of the folded state plus the inbox contents, as before; the hold removes T's arm from the set of every node that cannot open the held copy, and a node that can opens it by journaling an auto-release first, so the branch a flow takes is always the one recorded. A `select` whose only inbox arms are held topics parks until a release (or a timer/gate arm fires).

#### Auto-release (user ruling 2026-10-14): a capable node lifts the hold by itself

**Semantics, plainly.** A quarantine is a CAPABILITY hold: it exists because some node could not open the head message, and the topic is held, in its original order, until a node that can open it exists. As soon as one does, the system releases the message with no operator: the capable node delivers it FIRST, from the quarantine copy, with its original `inboxSeq`, ahead of everything above the cursor, and the topic resumes. The operator verbs remain: `quarantineInbox` (the initial hold), `releaseInbox("deliver")` (force the same thing now, from a capable node), `releaseInbox("discard")` (drop it; the only way out when no node can ever open it).

**Reads of the quarantine stream are non-loud.** `inboxChainOf` gives the quarantine stream the inbox's non-loud read in `EncryptingEventStore` (a missing key redacts the payload to the SHREDDED marker instead of throwing, ADR 0110 D9). So a release or auto-release must NEVER treat a redacted copy as deliverable (a copy whose payload reads as the marker is a key-unavailable refusal in the D7 split, not a message), and `quarantineInbox`'s `not-sealed` check must not be fooled by it: a redacted read is not evidence that the message is openable or that it is plain.

**Who initiates the hold (decision, confirmed by the user 2026-10-14).** The initial quarantine STAYS an operator act; an incapable node does not auto-quarantine. Reasons, in order of weight: (1) ADR 0130's core guarantee is that an incapable node APPENDS NOTHING; auto-quarantine would make every raw poll write a copy and two facts, and many incapable nodes would contend to write them; (2) without a hold the default (D4) already recovers by itself: a capable node that reaches the message delivers it in order, so auto-release only matters once someone chose to unblock the OTHER topics, which trades away that topic's flow and is the operator's policy call, not the kernel's; (3) it keeps the hold bounded by `quarantineMax` under operator control, so a burst of sealed traffic cannot fill the quarantine stream and the folded `_quarantined` unattended. A deployment that wants automatic initiation can drive `quarantineInbox` from its own `onError` handler (the refusal reports the blocked topic and `inboxSeq`); the kernel does not decide it. A hold is NOT a moderation hold: it is only permitted for a message unopenable on the quarantining node (`not-sealed` otherwise), so a capable node lifting it is always the intended outcome. To stop a message, use `discardInbox`/`releaseInbox("discard")`.

**When a capable node releases: lazily, at the one moment a delivery would happen, never on a timer of its own.** The triggers are exactly the existing delivery points, so there is no new poller, no new lease, and no new failure surface:
1. the notify scan (the post-park read `afterInboxPark`, a `send`'s wake, `TimerService.fireInbox`, `recoverAbandoned`), when the parked execution waits on a topic whose first entry is `held`;
2. the live run, when the flow reaches a receive/`select` arm on a held topic (`satisfyFromInbox` applies the same delivery rule);
3. a quarantine writes the `INBOX_WAKE_AT` row (as any sealed refusal does), so a capable node's poll reaches a parked execution that nobody else would otherwise wake. The wake row is NOT retired by an incapable node while a waited topic is held and unopenable to it (the poll backs off with `sealedBackoff` and reports first-then-every-16th "held, awaiting a capable node"); it is retired by whichever node delivers.

A topic nobody waits on is not released (nothing would consume it); it releases the first time something does. That is the same laziness as an unconsumed ordinary message.

**The act (one atomic batch).** The capable node (a) reads the copy at `heldAt` from the quarantine stream, checks its `key` matches the entry, and passes `assertDeliverable` (a node that cannot open it is not capable: it skips as above); (b) appends, under the park's conditional fence (`advanceInbox`/the notify batch, ADR 0118), ONE batch: `INBOX_RELEASED { topic, key, messageId, disposition: "deliver", auto: true }` immediately followed by `MESSAGE_CONSUMED { inboxSeq: <original>, ... }` for the copy and then the park's answer, exactly the composition the notify path already uses for any delivery. The fold sees `released` then the consumed drop in order; the cursor does not move; the dedupe window records the key. Because both facts are in one batch there is no window in which the entry is `released` but undelivered, so the manual-release crash window ("3" below) does not arise on this path; a manually `released` entry (an operator on a capable node, or a manual release followed by a crash) is delivered by the same step 1 on the next notify, unchanged.

**The `auto` marker; how authz treats it.** `auto: true` replaces `operator` (an `INBOX_RELEASED` never has both, the fold ignores a fact that has both or neither), chosen over a reserved system principal because a reserved actor name could be impersonated by a caller who sets `principal.actor`, whereas `auto` is a field only the kernel stamps (the fold honours it only from a kernel-stamped envelope, like the other facts). An automatic release is NOT a caller operation: it takes no principal, is not an `ExecutionOp`, and consults no authorizer, for the same reason the delivery of any message does not: the node is already driving this execution, and the release grants nothing, since the bytes were authorized when they were sent and it delivers the very message the cursor was going to deliver, only now able to open it. It cannot discard, cannot reorder, and cannot release anything but the topic's OLDEST `held` entry. The audit trail reads `INBOX_RELEASED auto` versus `INBOX_RELEASED operator=...`; the stamping envelope carries the node that did it. A runtime option `kernel.inbox.autoRelease` (default `true`) turns it off for a deployment that wants every hold lifted by an operator; it is a node-local policy, never read by the fold (the hold remains a shared journaled fact).

**Exactly one node releases; races.** Both the delivery and the release are one append under the park's conditional fence, and `staleInboxBatch` is extended with one more clause: a batch carrying an auto-release is refused when the topic's first entry is no longer `held` in the refolded state. Therefore: two capable nodes race, the fence admits one, the other refolds, sees the entry consumed (cursor/dedupe), and carries on with the next message, never delivering it twice (at most once, by the dedupe window and the stale-batch check); an auto-release races a manual `deliver`: the first to land wins, the loser finds the entry `released`/gone and is a no-op (manual `deliver` is idempotent); an auto-release races a manual `discard`: if the discard lands first the auto batch is stale and refolds (the message is gone, the topic is unblocked), if the auto-release lands first the discard is `invalid` (not held) and nothing is dropped; it races a notifier that built its batch before the hold or before the release: refused by the same clause (no delivery from a held topic except the first released entry). Exactly one outcome on every node.

**Liveness.** If no node that can open the message ever runs, the topic stays held, indefinitely, by design: the message stays safe and the OTHER topics keep flowing. That is documented, not hidden; the operator signal is the first-then-every-16th "held, awaiting a capable node" report and `_quarantined` on the analytics surface, and the exit is `releaseInbox("discard")`. A capable node starting later releases it on its first poll of the wake row.

#### Cursor and trim

Advancing the cursor at quarantine is what keeps the held message from pinning the stream: the inbox trim deletes the consumed prefix up to the cursor, so the original entry is reclaimable (the copy is the retained record). On the legacy shared stream the messages that arrive BEHIND the hold on T remain unconsumed and pin trimming exactly as an unconsumed hot topic does today (ADR 0110 D8's pin); per-topic streams (D10b) confine that backlog to T. Operators who quarantine should run per-topic streams.

#### Retention, copy-first

`quarantineInbox` first copies the head message verbatim into `__loom_quarantine__:<chainId>` as an `INBOX_MESSAGE` with a deterministic envelope id (`quarantine:<key>`, so a retry is a duplicate append, treated as already copied), preserving the envelope bytes and its `metadata.seal`: it is appended through the node's own store, which on an incapable node is raw (the sealed value is never opened, and an encrypting decorator must not double-seal a value that is already an envelope; S5 test), then journals `INBOX_QUARANTINED` with `heldAt`. Crash between them: an orphan copy (harmless, a retry reuses it), never a cleared head without a retained payload. The prefix `__loom_quarantine__:` joins the reserved-stream registry (S1) and `inboxStreamsOfChain`, so deletion with the chain, the compliance purge, `reclaimInbox` and the crypto subject mapping (`inboxChainOf`, same owner subject as the chain's inbox) all cover it. Copies are trimmed by prefix once every entry at or below is gone from `_quarantined` (the stream is append-only otherwise).

**Bound.** `quarantineMax` (default 256, ceiling 1024) bounds the RETAINED span of the quarantine stream per chain (head minus the oldest still-live copy, orphans included), refusal `invalid` at the cap. It also bounds the folded `_quarantined` size and therefore snapshots.

#### Verbs

- `quarantineInbox(executionId, { topic, reason? }, { principal })`: holds the topic's HEAD message (the first non-duplicate above the cursor, after journaling any duplicates ahead of it in the same atomic batch, as the notify scan does), refused `not-sealed` unless that message is sealed and unopenable on THIS node (the verb is not a general message-skipper; `discardInbox` already is that). Result: `{ messageId, inboxSeq, heldAt }`.
- `releaseInbox(executionId, { topic, messageId, disposition? }, { principal })`: `disposition` defaults to `"deliver"`; the message must be the topic's OLDEST held entry. `"deliver"` requires this node to be able to open the copy (read it, `assertDeliverable`; an incapable node gets the typed `SealedPayloadUnreadableError` and nothing is appended), then journals `INBOX_RELEASED { operator }` and runs the notify path, which delivers it by the delivery rule above, at its original position. It is what auto-release does, on demand and attributed to a principal; with auto-release on it matters only to force the release now. `"discard"` needs no ability to open (the escape hatch for a message no node can open), journals the drop, and unblocks the topic. Releasing anything not `held` is `invalid`; repeating a completed release is idempotent (nothing appended).
- **Authorization.** As `discardInbox`: a `principal` is REQUIRED (no system-grant stand-in), refused with `ExecutionDeniedError` before anything is read (no existence oracle), against the chain head's owner. New `ExecutionOp`s `"quarantine"` and `"release"` (deliver); a `"discard"` disposition is judged as `"discard"`, since it destroys the message. `executionAccessPolicy` maps the new ops to `"deny"` by default like `"discard"`. Refusals: a sibling `InboxQuarantineRefusedError` with the `InboxDiscardRefusedError` reasons (`not-parked`, `contended`, `invalid`) plus `not-sealed`. The owner must be parked (the facts land in its own log under the park's conditional fence via `advanceInbox`), bounded to existing sequences, `reason` <= 256, idempotent.

#### Interactions

- **Races and fencing across nodes.** The facts are one atomic batch under the park's conditional fence (ADR 0118), ignorable, so the park stays unanswered. A notifier that built its batch before the quarantine landed is refused by an extended `staleInboxBatch` and refolds: it refuses an entry at or below its topic's cursor (as today) AND any entry for a topic that is held, except the first released entry of its queue. Either the delivery wins (the quarantine then sees the cursor past the head: `invalid`, nothing held) or the quarantine wins (the delivery refolds and skips T). Exactly one outcome, on every node. The fold itself is not made to refuse (old logs replay as they always did); this is the runtime guard of ADR 0110 D8, extended.
- **`select` across topics:** above. **Replay:** replay serves recorded answers and reads neither the inbox nor the quarantine stream; a released message's answer is its `MESSAGE_CONSUMED` like any other (sealed in the log as any delivered payload: D4's replay refusal applies on an incapable node).
- **`discardInbox`:** unchanged. On a held topic it may skip messages ABOVE the cursor (they sit behind the hold, order among survivors is kept); it never touches held entries (`through` at or below the cursor appends nothing). Dropping a held entry is `releaseInbox` with `"discard"`.
- **TTL expiry (D10a):** applies to the messages behind the hold exactly as before (it scans above the cursor); it never expires a held entry, which is an operator-owned record bounded by `quarantineMax`, not a queue. A hold is therefore the one durable state that outlives `messageTtlMs` by design.
- **Per-topic streams (D10/D10a/D10b):** the cursor value is in either range; the hold is keyed by topic name, independent of the layout. The topic's registry entry stays live while it holds backlog; a held topic is not retired as "drained" because its cursor reaching the stream head is no longer the criterion once entries are held (retire requires an empty `_quarantined[topic]`).
- **Erasure and shred:** the copy is sealed (or byte-preserved sealed) under the chain's owner subject, the same key as the original, so a key shred destroys the original, the copy and the log together; the compliance purge deletes the quarantine stream with the chain's other streams. A plaintext held message cannot exist (`not-sealed`).
- **Continue-as-new:** `_quarantined` is carried like `_inbox` (`continuedFrom.carried.quarantined`, validated seed, invalid parts ignored, at most one `released` entry per topic; the chain id, and so the quarantine stream, survives rotation). **Fork / re-open:** a fork starts a fresh chain; it copies the quarantine stream prefix its copied log refers to (same sequence numbers) into its own chain's stream, so the folded `heldAt` stays valid (the implementer verifies this with the fork tests; the fallback if `copyPrefix` cannot, is a typed refusal to fork a chain that holds entries, never a fork with dangling holds).
- **Observability (R-c Option 2 by-product):** the sealed-refusal operator report (`isSealedUnreadable`) carries the blocked topic and the sealed message's `inboxSeq`/age so the operator knows what to quarantine; a held topic is listed on the analytics surface by `_quarantined` (no new events). A topic that stays held with no capable node reports "held, awaiting a capable node" on the same first-then-every-16th schedule.

#### Failure modes

Quarantine on a running owner: `not-parked`, retry. A sealed head that became openable meanwhile: `not-sealed`, nothing appended. Crash after the copy, before the fact: orphan copy, retry reuses it. Crash after `INBOX_QUARANTINED`: the hold is durable, nothing else pending. Crash after a MANUAL `INBOX_RELEASED`, before the delivery: the released entry is part of folded state, so ANY node's notify path (the wake row, `recoverAbandoned`, the post-park read) delivers it exactly once (the fact is the intent; delivery is the ordinary fenced `MESSAGE_CONSUMED`). An AUTOMATIC release is one atomic batch with its delivery, so a crash either appends both or neither: before the batch nothing changed and the next notify retries; after it the work is done; the copy being read but not yet delivered leaves no trace. Two capable nodes racing, or an auto-release racing a manual release/discard, are settled by the fence and `staleInboxBatch` (above).

### D10 (R-d) — A replay refusal leaves a wake row; the poll re-drives a `running` execution that carries one

**Write.** In `WorkflowRuntime.run()`'s catch for the replay refusal (the `WorkflowContext` latch, handled today by warning and rejecting the handles), call `markContended(executionId)` (same best-effort `.catch(onStorageError)`), now for BOTH `SealedPayloadUnreadableError` (replay) and the new `SealedStreamUnreadableError`. It appends no event (D4 holds). No timer store: no-op, documented (the recoverAbandoned contract is then the only recovery).

**Poll.** Today `TimerService.fireInbox` runs the notify path, which finds no unanswered park for a `running` execution and retires the row. New rule in `fireInbox`, before the notify path: if `state.status === "running"` and the row is the inbox wake (`INBOX_WAKE_AT`), do NOT retire; classify:

1. **Another node is live on it.** A lease/liveness probe says a live holder exists (the same `LeaseStore` the poll already claims under, ADR 0118 D4): leave the row, short back-off (the existing `wakeBackoff`, with its attempt cap so a row on a genuinely long-running execution does not live forever without bound reporting). The poll never supersedes a live holder.
2. **Abandoned or unowned.** Call the SAME routine `recoverAbandoned` uses for one execution (extracted as `WorkflowRuntime.redriveAbandoned(executionId, { source: "wake" })`), so fencing, the diverged-run policy and the failed/recovered accounting are shared, not re-implemented. On success the execution moves on (suspends, completes, or keeps running under the new driver) and the row is retired when the state is no longer `running`-and-stuck (the next poll sees a parked or terminal state and the ordinary rules apply; a terminal execution retires the row).

**Fencing; capable vs incapable do not fight.** The re-drive acquires the execution fence like any resume. To keep an incapable node from taking the fence just to refuse: (i) D7's `assertStreamReadable` runs BEFORE the fence acquire, from a read of the log, so a marked stream is refused with no write at all; (ii) for an UNMARKED sealed stream (the legacy case) the incapable node cannot know, so it may acquire and then refuse at replay; the acquire only bumps the fence token (a store row, not a log event), the refusal appends nothing, and the incapable node's per-execution `sealedBackoff` (the ADR 0130 map, shared, exponential, no attempt cap, bounded 1024) keeps it from retrying soon, while the row stays for a capable node. A capable node that acquires the fence after it wins, replays, passes, and proceeds; the incapable node's stale token is fenced out on its next write attempt (it has none to make). Two incapable nodes polling the same row serialize on the same lease claim. The fence bump is the only cross-node effect of a refusal and is already tolerated by every resume path (ADR 0118).

**Back-off and reporting.** Refusals reuse `sealedBackoff` and the first-then-every-16th `onError`. A re-drive that fails for another reason uses the existing `wakeBackoff` with its attempt cap and `RedriveExhaustedError`. The row is never retired by an incapable node.

**Interaction with `recoverAbandoned`.** The sweep and the poll converge on the same routine and the same backoff maps, so a refusal in one suppresses the other for the window (the sweep already skips a refused execution on this node, ADR 0130 D4). The sweep stays the safety net where no timer store exists; the wake row makes recovery timely without requiring an app to run a sweep with an `isAbandoned` predicate.

### Residual risks after this design

- A stream sealed by a writer that does not stamp `metadata.seal` keeps the pre-0130 non-inbox exposure (D7, unmarked).
- Pre-1.25.0 nodes in a mixed rollout have no marker check.
- A quarantine holds its TOPIC for every node that cannot open the held message until a capable node auto-releases it or an operator releases/discards it (D9): later messages of that topic wait behind it, by design, because that is the only way a release can keep original order. If no capable node ever runs, the topic stays held indefinitely (the other topics flow; the exit is `releaseInbox("discard")`).
- A plaintext snapshot already at rest is not rewritten.
