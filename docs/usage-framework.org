* Step 1 — Define Steps

A step is the smallest unit of work. Each step declares its id, I/O schemas, and optionally a co-located handler implementation using ~handler$()~.

** Option A: co-located handler (recommended)

Use ~handler$()~ to put the implementation next to the definition. The compiler automatically extracts this into a lazy chunk; at runtime it is called directly.

#+begin_src typescript
import { step$, handler$ } from "@loom/sdk";
import { z } from "zod";

export const FetchMetricsStep = step$({
  id: "fetch-metrics",
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.object({
    cpu: z.object({ current: z.number(), threshold: z.number() }),
    memory: z.object({ usedMb: z.number(), totalMb: z.number() }),
  }),
  handler: handler$(async (input, ctx) => {
    // ctx: { executionId, stepId, workflowId, attempt, emit }
    const data = await yourApiClient.getMetrics(input.incidentId);
    return data;
  }),
});
#+end_src

No separate ~effectRuntime.register()~ call is needed — ~registerFlow()~ auto-registers a ~LazyEffect~ for each step that carries a handler.

** Option B: separate effect registration

Use this when the effect implementation lives outside the step definition (e.g. different file, different environment, or test replacement).

#+begin_src typescript
export const FetchMetricsStep = step$({
  id: "fetch-metrics",
  toolId: "metrics-tool",    // effect registry key
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.object({ cpu: z.number() }),
});

// Wire the implementation separately:
effectRuntime.register(
  "metrics-tool",
  new ToolEffect(async (input) => {
    return { cpu: await getMetrics(input.incidentId) };
  })
);
#+end_src

~toolId~ defaults to ~id~ when omitted, so both options can co-exist in the same step: set ~toolId~ if you want a stable registry key independent of ~id~.

** Human approval step (suspend point)

Use ~ctx.suspend()~ directly in the runner — no ~HumanEffect~ registration is needed unless you want the step modelled as a named effect.

#+begin_src typescript
export const ApprovalStep = step$({
  id: "wait-for-approval",
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.unknown(),
  // No handler — suspension is triggered by ctx.suspend() in the runner
});
#+end_src

Or use ~HumanEffect~ for explicit modelling:

#+begin_src typescript
effectRuntime.register(
  "approval-gate",
  new HumanEffect({ on: "ApprovalGranted" })
);
#+end_src

* Step 2 — Define the Flow

A flow groups steps and declares its I/O schemas. Flows are pure definitions — they carry no runtime state.

#+begin_src typescript
import { flow$ } from "@loom/sdk";
import { z } from "zod";

export const InvestigateIncidentFlow = flow$({
  id: "investigate-incident",
  name: "Investigate Incident",
  version: "1.0.0",
  description: "Gathers metrics and logs, waits for approval, then remediates",
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.object({ resolved: z.boolean(), summary: z.string() }),
  steps: [FetchMetricsStep, FetchLogsStep, ApplyRemediationStep],
});
#+end_src

* Step 3 — Write the Flow Runner

The runner is an async function that receives a ~WorkflowContext~ and the typed input. It calls ~ctx.run()~ for each step and ~ctx.emit()~ for domain events. All control flow is plain TypeScript — conditionals, loops, parallel execution.

#+begin_src typescript
import type { FlowRunner } from "@loom/workflow-runtime";

const runner: FlowRunner<IncidentInput, IncidentOutput> = async (ctx, input) => {
  ctx.emit("INCIDENT_INVESTIGATION_STARTED", { incidentId: input.incidentId });

  // Run steps — idempotent; replayed from cache on resume
  const metrics = await ctx.run(FetchMetricsStep, { incidentId: input.incidentId });
  const logs    = await ctx.run(FetchLogsStep,    { incidentId: input.incidentId });

  ctx.emit("INCIDENT_ANALYSIS_COMPLETE", { metrics, logs });

  // Parallel execution
  // const [metrics, logs] = await ctx.parallel([
  //   [FetchMetricsStep, { incidentId: input.incidentId }],
  //   [FetchLogsStep,    { incidentId: input.incidentId }],
  // ]);

  // Emit domain event to update UI projection
  ctx.emit("APPROVAL_REQUESTED", { incidentId: input.incidentId, metrics, logs });

  // Suspend and wait for human decision — resumes transparently on replay
  await ctx.suspend({ on: "ApprovalGranted", correlationKey: input.incidentId });

  // Everything after suspend runs only after resume
  const remediation = await ctx.run(ApplyRemediationStep, { incidentId: input.incidentId });

  ctx.emit("INCIDENT_RESOLVED", { incidentId: input.incidentId, summary: remediation.summary });

  return { resolved: remediation.success, summary: remediation.summary };
};

// Bundle definition + runner together
export const InvestigateIncidentRegisteredFlow = {
  definition: InvestigateIncidentFlow,
  runner,
};
#+end_src

** Key rules for runner functions

1. *No side effects outside ~ctx~* — all I/O must go through ~ctx.run()~, ~ctx.emit()~, or ~ctx.suspend()~. Direct API calls are not replayed idempotently.
2. *Do not catch ~SuspendError~* — let it propagate to ~WorkflowRuntime~.
3. *Keep runner logic deterministic* — the same input + event log must always produce the same execution path.

** Bounded-concurrency parallel steps

~ctx.parallel()~ runs several steps at once and returns their results *in input order* — so the shape stays deterministic for replay no matter which step finishes first. By default it is unbounded (behaves like ~Promise.all~). Pass ~{ limit: N }~ to cap how many run concurrently — useful when the steps hit a rate-limited API or you want to avoid a thundering herd of effects.

#+begin_src typescript
// Unbounded — all pairs start immediately (default).
const [metrics, logs] = await ctx.parallel([
  [FetchMetricsStep, { incidentId: input.incidentId }],
  [FetchLogsStep,    { incidentId: input.incidentId }],
]);

// Bounded — never more than 2 in flight at once; results still in input order.
const [metrics, logs, traces] = await ctx.parallel(
  [
    [FetchMetricsStep, { incidentId: input.incidentId }],
    [FetchLogsStep,    { incidentId: input.incidentId }],
    [FetchTracesStep,  { incidentId: input.incidentId }],
  ],
  { limit: 2 },
);
#+end_src

Each parallel step is an ordinary ~ctx.run()~ under the hood, so caching, replay, and cancellation all apply exactly as they do for a sequential step.

* Step 4 — Set Up Projections

Projections are pure read models derived from the event stream. Each handler is a ~(state, event) => state~ reducer.

#+begin_src typescript
import { projection$ } from "@loom/sdk";
import type { EventEnvelope } from "@loom/sdk";

interface MetricsState {
  cpu: { current: number; threshold: number } | null;
  memory: { usedMb: number; totalMb: number } | null;
}

export const MetricsProjection = projection$({
  id: "metrics",
  name: "Metrics Projection",
  initialState: { cpu: null, memory: null } as MetricsState,
  handlers: {
    INCIDENT_ANALYSIS_COMPLETE: (state, event: EventEnvelope) => {
      const p = event.payload as { metrics: MetricsState };
      return { cpu: p.metrics.cpu, memory: p.metrics.memory };
    },
  },
});
#+end_src

Register projections with the runtime before the first event arrives:

#+begin_src typescript
projectionRuntime.register(MetricsProjection);
projectionRuntime.register(IncidentProjection);
#+end_src

* Step 5 — Bootstrap the Runtime

Create one ~WorkflowRuntime~ per application. Wire ~onEvent~ to route events into ~ProjectionRuntime~.

#+begin_src typescript
import { WorkflowRuntime } from "@loom/workflow-runtime";
import { EffectRuntime } from "@loom/effect-runtime";
import { InMemoryEventStore, InMemorySnapshotStore } from "./browserStores";
import { InMemoryProjectionRuntime } from "@loom/projection-runtime";

const effectRuntime     = new EffectRuntime();
const projectionRuntime = new InMemoryProjectionRuntime();

projectionRuntime.register(MetricsProjection);
projectionRuntime.register(IncidentProjection);

const workflowRuntime = new WorkflowRuntime({
  eventStore:    new InMemoryEventStore(),
  snapshotStore: new InMemorySnapshotStore(),
  effectRuntime,
  onEvent: (event) => projectionRuntime.handleEvent(event),
});

// Auto-registers LazyEffect for steps with handler$
workflowRuntime.registerFlow(
  InvestigateIncidentRegisteredFlow.definition,
  InvestigateIncidentRegisteredFlow.runner,
);
#+end_src

** Coalescing projection notifications (streaming bursts)

When a step streams many events in quick succession (token-by-token A2UI patches, a metrics firehose), each event normally notifies every subscriber synchronously — one re-render per event. Opt into ~coalesceNotifications~ to collapse a burst into *one notification per projection key per microtask*: the runtime keeps applying every event (state stays exact), but subscribers are woken once when the microtask drains.

#+begin_src typescript
const projectionRuntime = new InMemoryProjectionRuntime({ coalesceNotifications: true });
#+end_src

Off by default. The trade-off: subscriber updates land on a microtask rather than synchronously, so a test that reads state immediately after ~handleEvent()~ should ~await Promise.resolve()~ first. It pairs naturally with the deferred render hooks below (~useDeferredProjection~ / ~useDeferredWidgetValue~) — coalescing cuts the *number* of updates, deferral cuts their *priority*.

For server/production use, replace in-memory stores with SQLite:

#+begin_src typescript
import { SqliteEventStore } from "@loom/event-runtime";
import { SqliteSnapshotStore } from "@loom/snapshot-runtime";

const workflowRuntime = new WorkflowRuntime({
  eventStore:    new SqliteEventStore("./data/events.db"),
  snapshotStore: new SqliteSnapshotStore("./data/snapshots.db"),
  effectRuntime,
  onEvent: (event) => projectionRuntime.handleEvent(event),
});
#+end_src

  console.log("Incident resolved");
});
#+end_src

** Cancelling a running execution

Call ~handle.cancel(reason?)~ to abort a live run — for a user "Stop" button, a superseded request, or a timeout. It aborts the ~AbortSignal~ handed to in-flight effects, records a durable ~EXECUTION_CANCELLED~ event, and *rejects* the promise from ~waitForCompletion()~ — so wrap that in try/catch.

#+begin_src typescript
const handle = await workflowRuntime.start(InvestigateIncidentRegisteredFlow, {
  incidentId: "cpu-001",
});

try {
  const state = await handle.waitForCompletion();
  console.log("Completed at sequence", state.sequence);
} catch (err) {
  // Cancellation surfaces here as a rejection.
  console.log("Investigation cancelled:", err);
}

// …elsewhere, e.g. a Stop button handler:
handle.cancel("superseded by newer incident");
#+end_src

Cancellation only affects *live* work — already-persisted state and resume semantics are unchanged. The execution moves to the new ~"cancelled"~ status and the log gains an ~EXECUTION_CANCELLED~ event (plus a ~STEP_CANCELLED~ event for any step interrupted mid-flight). ~cancel()~ is idempotent.

For cancellation to actually interrupt an effect, the effect must observe its signal. Each effect receives ~ctx.signal~ (an ~AbortSignal~); long-running or I/O effects should forward it and/or check it at ~await~ points:

#+begin_src typescript
handler: handler$(async (input, ctx) => {
  // Forward the signal to fetch — the request aborts the moment cancel() fires.
  const res = await fetch(`/metrics/${input.incidentId}`, { signal: ctx.signal });
  return res.json();
}),
#+end_src

Effects that don't touch ~ctx.signal~ still run to completion, but the execution is recorded as cancelled and ~waitForCompletion()~ rejects as soon as ~cancel()~ is called.

* Step 8 — Render in React

Wrap your app in ~LoomProvider~ to share the runtimes via context. Use ~BlueprintRenderer~ to render blueprint widgets and ~useLoom~ to access runtimes anywhere in the tree.

#+begin_src typescript
// main.tsx
import { createRoot } from "react-dom/client";
import { LoomProvider } from "@loom/renderer-react";

const root = document.getElementById("root")!;
createRoot(root).render(
  <LoomProvider workflowRuntime={workflowRuntime} projectionRuntime={projectionRuntime}>
    <App />
  </LoomProvider>
);
#+end_src

#+begin_src typescript
// App.tsx
import {
  useLoom,
  BlueprintRenderer,
  defaultRegistry,
  MetricCardRenderer,
  TimelineRenderer,
  ApprovalCardRenderer,
} from "@loom/renderer-react";
import type { WidgetAction } from "@loom/renderer-react";

defaultRegistry.register("MetricCard", MetricCardRenderer);
defaultRegistry.register("Timeline", TimelineRenderer);
defaultRegistry.register("ApprovalCard", ApprovalCardRenderer);

export function App() {
  const { workflowRuntime, projectionRuntime } = useLoom();
  const [executionId, setExecutionId] = useState<string | null>(null);

  const start = async () => {
    const handle = await workflowRuntime.start(InvestigateIncidentRegisteredFlow, {
      incidentId: "cpu-001",
    });
    setExecutionId(handle.executionId);
  };

  const handleAction = (action: WidgetAction) => {
    if (action.type === "APPROVE" && executionId) {
      workflowRuntime.resume(executionId, {
        eventType: "ApprovalGranted",
        payload: { approved: true },
      });
    }
  };

  return (
    <div>
      <button onClick={start}>Start Investigation</button>
      {executionId && (
        <BlueprintRenderer
          blueprint={IncidentBlueprint}
          projectionRuntime={projectionRuntime}
          executionId={executionId}
          onAction={handleAction}
        />
      )}
    </div>
  );
}
#+end_src

** Fiber rendering (large dashboards & streaming widgets)

By default ~BlueprintRenderer~ subscribes to all of a blueprint's projections and re-traverses the whole tree on any change — simple and correct. For large dashboards, high-frequency streaming widgets, or async BYOC (bring-your-own-component) renderers, opt into *fiber mode*, which leans on React's own scheduler (no second reconciler) to render more granularly. It is fully off by default: when ~fiber~ is falsy the output is byte-identical to the current path.

Turn it on per renderer with the ~fiber~ prop — ~fiber~ (all three capabilities) or an object to pick individual ones:

#+begin_src typescript
// All three capabilities:
<BlueprintRenderer
  blueprint={IncidentBlueprint}
  projectionRuntime={projectionRuntime}
  executionId={executionId}
  fiber
/>

// Or opt into individual capabilities:
<BlueprintRenderer
  blueprint={IncidentBlueprint}
  projectionRuntime={projectionRuntime}
  executionId={executionId}
  fiber={{ granularUpdates: true, suspense: true, deferStreaming: true }}
/>
#+end_src

The three capabilities:

- ~granularUpdates~ — each widget subscribes to its own bound path, so only the widget whose slice changed re-renders (instead of the whole blueprint). This is the base of fiber mode; enabling either capability below implies it.
- ~suspense~ — each widget is wrapped in its own ~<Suspense>~ boundary, so an async BYOC component can suspend (throw a promise, or use React's ~use()~) without blanking its siblings. The fallback is the widget's ~placeholder~ prop (when it's a string) or a default skeleton.
- ~deferStreaming~ — high-frequency widgets (kind ~"StreamingText"~, or any widget with ~props.defer === true~) receive their updates via ~startTransition~, so a token firehose never blocks urgent work such as clicking Approve.

You can also set a tree-wide default on the provider; a ~BlueprintRenderer~ ~fiber~ prop overrides it:

#+begin_src typescript
<LoomProvider
  workflowRuntime={workflowRuntime}
  projectionRuntime={projectionRuntime}
  fiber={{ granularUpdates: true, deferStreaming: true }}
>
  <App />
</LoomProvider>
#+end_src

For reading projection state in your own components, ~useDeferredProjection~ is the ~startTransition~ variant of ~useProjection~ — same signature, but streamed updates are marked non-urgent:

#+begin_src typescript
import { useDeferredProjection } from "@loom/renderer-react";

// Same signature as useProjection; use ONLY for high-frequency, low-urgency state.
const surface = useDeferredProjection<AssistantSurface>(projectionRuntime, "ui", executionId);
#+end_src

Keep urgent state (an approval result) on the eager ~useProjection~ path — deferred updates can momentarily tear relative to eager ones.

One rule of thumb: leave fiber off for ordinary blueprints (behavior is unchanged); reach for it when you have a large dashboard, streaming widgets, or async BYOC components.

* Writing Custom Widget Renderers

Extend the registry with domain-specific widgets:

#+begin_src typescript
import type { WidgetRendererProps } from "@loom/renderer-react";

const ConnectionGaugeRenderer: React.FC<WidgetRendererProps> = ({ widget, value, onAction }) => {
  const connections = value as { active: number; max: number };
  const pct = (connections.active / connections.max) * 100;

  return (
    <div data-widget-kind="ConnectionGauge" data-widget-id={widget.id}>
      <h4>{widget.title ?? "Connections"}</h4>
      <progress value={pct} max={100} />
      <span>{connections.active} / {connections.max}</span>
    </div>
  );
};

defaultRegistry.register("ConnectionGauge", ConnectionGaugeRenderer);
#+end_src

Then use the widget in a blueprint:

#+begin_src typescript
import { widget } from "@loom/blueprint-runtime";

// Generic widget builder for custom kinds
const ConnectionGauge = (props: { title: string; binding: DataBinding }) =>
  widget({ kind: "ConnectionGauge", ...props });
#+end_src

*** Per-widget value hooks (for fiber-friendly renderers)

The renderers above receive their ~value~ prop from ~BlueprintRenderer~. If you write a renderer that subscribes directly — e.g. to stream a value without re-traversing the tree — use the path-granular hooks. ~useWidgetValue~ is tear-free (built on ~useSyncExternalStore~) and only re-renders when the widget's own bound slice changes; ~useDeferredWidgetValue~ is the ~startTransition~ variant for high-frequency streaming widgets.

#+begin_src typescript
import { useWidgetValue, useDeferredWidgetValue } from "@loom/renderer-react";

// Re-renders ONLY when this widget's bound path changes (not sibling slices):
const value = useWidgetValue<{ active: number; max: number }>(
  projectionRuntime,
  widget,
  executionId,
);

// Or, for a token-by-token streaming widget, defer updates so they yield to
// urgent work:
const text = useDeferredWidgetValue<string>(projectionRuntime, widget, executionId);
#+end_src

These are the same hooks fiber mode mounts per widget, so a hand-written renderer participates in granular/deferred updates automatically.

* Subscribing to Projection State in Custom Hooks

Use ~useProjection~ to read projection state outside of ~BlueprintRenderer~:

#+begin_src typescript
import { useProjection } from "@loom/renderer-react";

function StatusBanner({ executionId }: { executionId: string }) {
  const { projectionRuntime } = useLoom();
  const incident = useProjection<IncidentState>(
    projectionRuntime,
    "incident",
    executionId
  );

  return (
    <div className={`status-${incident.status}`}>
      Status: {incident.status}
    </div>
  );
}
#+end_src

For a projection that updates very frequently and isn't urgent (a live metrics ticker, a streaming answer), swap in ~useDeferredProjection~ — identical signature, but updates are marked non-urgent React transitions so they never block an interaction:

#+begin_src typescript
import { useDeferredProjection } from "@loom/renderer-react";

function MetricsTicker({ executionId }: { executionId: string }) {
  const { projectionRuntime } = useLoom();
  const metrics = useDeferredProjection<MetricsState>(
    projectionRuntime,
    "metrics",
    executionId,
  );
  return <span>CPU {metrics.cpu?.current ?? "—"}%</span>;
}
#+end_src

* Building Agentic Applications

Loom's agentic layer builds on the same steps, effects, and projections you have already seen. This section is a practical walkthrough: configure a model, call it from a flow, wrap it in an agent, give the agent tools over MCP, expose and consume agents over A2A, and drive the UI with the A2UI patch protocol.

#+begin_src bash
# Agentic packages
pnpm add @loom/llm @loom/agent @loom/mcp @loom/a2a @loom/registry
#+end_src

Two runnable examples ship with the framework:

- ~examples/cloud-command-center~ — an end-to-end UI that streams an AI analysis into the A2UI ~"ui"~ surface via patches.
- ~examples/agent-network~ — the server-side pieces (agents, MCP tools, and A2A). Run it with ~pnpm --filter @loom/agent-network start~.

** Configuring an LLM provider

A ~LlmProvider~ is the only integration point between Loom and a model backend. The shipped providers talk to their HTTP APIs through the global ~fetch~, so you do not need to install any vendor SDK.

#+begin_src typescript
import { AnthropicProvider, OpenAiProvider } from "@loom/llm";

// Anthropic — defaults to model "claude-opus-4-8" and ANTHROPIC_API_KEY
const provider = new AnthropicProvider();

// Swapping backends is a one-line change — OpenAiProvider defaults to "gpt-4o" and OPENAI_API_KEY
// const provider = new OpenAiProvider();

// Override model / key / endpoint explicitly:
const custom = new AnthropicProvider({
  model: "claude-opus-4-8",
  apiKey: process.env.MY_KEY,
  baseUrl: "https://gateway.internal/anthropic",
});
#+end_src

Because everything flows through the ~LlmProvider~ interface, you can implement your own — for a local model, a test double, or a corporate gateway — and pass it anywhere a provider is accepted:

#+begin_src typescript
import type { LlmProvider, LlmRequest, LlmResponse } from "@loom/llm";

class EchoProvider implements LlmProvider {
  async complete(request: LlmRequest): Promise<LlmResponse> {
    const last = request.messages.at(-1)?.content ?? "";
    return { content: `echo: ${last}`, stopReason: "end_turn" };
  }
  // Optional: implement stream() to yield { delta, done } chunks
}
#+end_src

** Calling an LLM from a flow step

Use ~createLlmEffect~ to turn a provider into a registrable effect. ~buildRequest~ maps your step input into an ~LlmRequest~; ~parseResponse~ (optional) maps the response back — by default it returns ~response.content~.

#+begin_src typescript
import { createLlmEffect, AnthropicProvider } from "@loom/llm";
import { step$ } from "@loom/sdk";
import { z } from "zod";

const summarize = createLlmEffect<{ logs: string[] }, { summary: string }>({
  provider: new AnthropicProvider(),
  buildRequest: (input) => ({
    messages: [{ role: "user", content: `Summarize these logs:\n${input.logs.join("\n")}` }],
    maxTokens: 512,
  }),
  parseResponse: (res) => ({ summary: res.content }),
});

effectRuntime.register("summarize-logs", summarize);

export const SummarizeStep = step$({
  id: "summarize-logs",
  inputSchema: z.object({ logs: z.array(z.string()) }),
  outputSchema: z.object({ summary: z.string() }),
});

// In a runner:
const { summary } = await ctx.run(SummarizeStep, { logs });
#+end_src

** Defining and running an agent

An agent is an ~agent$~ definition (its tools + policies) driven by a provider in a tool-using loop. ~AgentRunner~ prompts the model with the agent's tools; while the model asks to use a tool it executes each one through the ~EffectRuntime~, feeds the result back, and repeats until the model finishes or ~maxIterations~ (default 10) is hit.

#+begin_src typescript
import { agent$, tool$ } from "@loom/sdk";
import { AgentRunner } from "@loom/agent";
import { AnthropicProvider } from "@loom/llm";

const MetricsTool = tool$({
  id: "metrics-tool",
  name: "Metrics Tool",
  description: "Fetches CPU and memory metrics for an incident",
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.object({ cpu: z.number(), memory: z.number() }),
});
effectRuntime.register("metrics-tool", new ToolEffect(async (i) => getMetrics(i.incidentId)));

const InvestigatorAgent = agent$({
  id: "investigator",
  name: "Investigator Agent",
  description: "Gathers incident evidence",
  tools: [MetricsTool],
});

const runner = new AgentRunner({
  definition: InvestigatorAgent,
  provider: new AnthropicProvider(),
  effectRuntime,
  systemPrompt: "You are an incident investigator. Use the tools to gather evidence.",
});

const result = await runner.run({ prompt: "Diagnose incident cpu-001" }, ctx);
// result: { content, toolCallLog: AgentStep[], iterations }
#+end_src

The runner emits an ~AGENT_TOOL_CALL~ event for each tool invocation and a single ~AGENT_COMPLETED~ event at the end, so projections and telemetry can observe the agent's reasoning trace exactly like any other workflow events.

When the model asks for several tools in one turn, they run sequentially by default. Set ~parallelTools~ to execute them concurrently — ~true~ runs all of a turn's tool calls at once, or pass a number to cap concurrency. Results, event emission, and the messages fed back to the model are *always* kept in the model's tool-call order regardless of which finishes first, so event-sourced replay stays deterministic.

#+begin_src typescript
const runner = new AgentRunner({
  definition: InvestigatorAgent,
  provider: new AnthropicProvider(),
  effectRuntime,
  systemPrompt: "You are an incident investigator. Use the tools to gather evidence.",
  parallelTools: true,   // or a number, e.g. 3, to cap concurrency
});
#+end_src

The agent also honors cancellation: ~AgentRunner.run~ checks ~ctx.signal~ before each model round-trip, so cancelling the execution stops it before the next (expensive) LLM call.

To drop an agent directly into a flow, use ~agentStep$~ — it returns an ordinary ~StepDefinition~ you can pass to ~ctx.run~:

#+begin_src typescript
import { agentStep$ } from "@loom/agent";

export const InvestigateStep = agentStep$({
  id: "investigate",
  agent: InvestigatorAgent,
  provider: new AnthropicProvider(),
  effectRuntime,
});

// In a runner:
const report = await ctx.run(InvestigateStep, { prompt: "Diagnose incident cpu-001" });
ctx.emit("INVESTIGATION_COMPLETE", report);
#+end_src

** Giving an agent skills

A *skill* packages authored expertise — instructions (and an optional tool subset) an agent loads on demand. The ~description~ is always available for selection; the ~instructions$~ body is lazy, so only the skills relevant to a turn are pulled into context (the compiler extracts each body into its own chunk, just like ~handler$~). Group skills in a ~SkillRegistry~ and pass it to ~AgentRunner~; before each run it selects the relevant skills, emits ~SKILLS_SELECTED~, composes their instructions onto the system prompt, and adds their tools to the model's menu.

#+begin_src typescript
import { skill$, instructions$ } from "@loom/sdk";
import { AgentRunner, SkillRegistry } from "@loom/agent";

const CpuRunbook = skill$({
  id: "diagnose-cpu",
  name: "Diagnose CPU saturation",
  description: "Root-cause CPU saturation and connection-pool exhaustion",
  tags: ["cpu", "pool"],
  instructions: instructions$(`
    1. Confirm CPU% and pool utilisation via the metrics tool before acting.
    2. If the pool is exhausted, recycle it and raise the ceiling.
    3. Only scale replicas if CPU stays high after the pool recovers.
  `),
});

const runner = new AgentRunner({
  definition: InvestigatorAgent,
  provider,
  effectRuntime,
  systemPrompt: "You are an SRE.",
  skills: new SkillRegistry().register(CpuRunbook),   // selection is deterministic by default
});
#+end_src

Selection is deterministic (keyword-scored) by default, so a replayed execution reconstructs the same prompt — important because Loom re-runs the agent loop on replay. For model-driven selection, pass ~skillSelector: llmSkillSelector(provider)~; the ~SKILLS_SELECTED~ event records the choice either way. (This runtime skill is distinct from the A2A ~skills~ metadata on an agent card.)

** Using MCP tools

Instead of hand-writing every tool, connect to a Model Context Protocol server, discover its tools, and register them into the ~EffectRuntime~. The returned ~ToolDefinition[]~ can be handed straight to ~agent$~.

#+begin_src typescript
import { McpClient } from "@loom/mcp";

const client = new McpClient({ transport: "http", url: "https://tools.example.com/mcp" });
await client.connect();                         // JSON-RPC "initialize"
const toolDefs = await client.registerInto(effectRuntime);   // registers each tool as a ToolEffect

const ResearchAgent = agent$({
  id: "researcher",
  name: "Research Agent",
  description: "Answers questions using MCP tools",
  tools: toolDefs,
});

// ... run it with AgentRunner or agentStep$ as above.
// When finished:
await client.disconnect();
#+end_src

MCP tools validate their own inputs, so their generated ~ToolDefinition~ uses ~z.unknown()~; the raw JSON Schema stays available on each ~MappedMcpTool.jsonInputSchema~ if you need it.

** Exposing and calling agents over A2A

Expose any registered flow as an A2A HTTP agent with ~createA2AServer~. It serves an agent card at ~/.well-known/agent.json~, accepts tasks at ~POST /tasks/send~, and reports status at ~GET /tasks/:id~. The card is derived from the ~agent$~ definition with ~toAgentCard~ rather than hand-written, so it stays in step with the agent; the server supplies the ~url~ from its bound address.

#+begin_src typescript
import { createA2AServer, toAgentCard } from "@loom/a2a";

// version / capabilities / skills live on the agent$ definition (see agent$);
// toAgentCard derives the card and the server fills in url from its bound address.
const server = createA2AServer(
  workflowRuntime,
  InvestigateIncidentRegisteredFlow,
  toAgentCard(InvestigatorAgent),
  { port: 4100 },
);

await server.start();
console.log("Agent available at", server.url);
#+end_src

From another process, call that agent from inside a flow with ~createA2AClientEffect~. It POSTs the task and polls until the task is ~completed~ or ~failed~, all over the global ~fetch~.

#+begin_src typescript
import { createA2AClientEffect } from "@loom/a2a";

effectRuntime.register(
  "remote-investigator",
  createA2AClientEffect("http://localhost:4100", { pollIntervalMs: 500 }),
);

export const DelegateStep = step$({
  id: "delegate",
  toolId: "remote-investigator",
  inputSchema: z.unknown(),
  outputSchema: z.unknown(),
});

// In a runner:
const taskResult = await ctx.run(DelegateStep, {
  id: "task-1",
  message: { role: "user", parts: [{ type: "text", text: "Diagnose cpu-001" }] },
});
#+end_src

** Driving the UI with A2UI (patch/event protocol)

A2UI (Agent-to-UI) is a first-class protocol for patch/event-based UI updates. Rather than inventing a bespoke event per widget, an agent or flow drives a named *surface* by emitting declarative *patches* (~set~, ~merge~, ~append~, ~remove~, ~increment~) addressed by dot-path. Patches travel as ordinary ~A2UI_PATCH~ events, so every UI update is durable and replays deterministically. Import from ~@loom/a2ui~.

*** 1. Emit patches from a flow (~ctx.ui~) or a step/agent (~createA2UIEmitter~)

Inside a flow runner, ~ctx.ui~ is a ready-made ~A2UIEmitter~ bound to the default ~"ui"~ surface:

#+begin_src typescript
const runner: FlowRunner<{ prompt: string }, { done: boolean }> = async (ctx, input) => {
  ctx.ui.set("phase", "analyzing");
  ctx.ui.merge("meta", { prompt: input.prompt });

  for await (const chunk of provider.stream!(request)) {
    ctx.ui.append("answer", chunk.delta);   // grow a string token-by-token
    ctx.ui.increment("tokens");             // += 1
  }

  ctx.ui.set("phase", "done");
  return { done: true };
};
#+end_src

Anywhere else that can emit events — a step's ~EffectContext~ or an agent — wrap ~emit~ with ~createA2UIEmitter~:

#+begin_src typescript
import { createA2UIEmitter } from "@loom/a2ui";

export const AnalyzeStep = step$({
  id: "analyze",
  inputSchema: z.object({ incidentId: z.string() }),
  outputSchema: z.object({ severity: z.number() }),
  handler: handler$(async (input, ctx) => {
    const ui = createA2UIEmitter((type, payload) => ctx.emit(type, payload));  // surface defaults to "ui"
    ui.set("status", "fetching metrics");
    const metrics = await getMetrics(input.incidentId);
    ui.merge("metrics", metrics);
    ui.patch([                       // arbitrary batch, applied atomically as one event
      { op: "set", path: "status", value: "done" },
      { op: "increment", path: "steps", by: 1 },
    ]);
    return { severity: metrics.severity };
  }),
});
#+end_src

*** 2. Consume via a projection (~a2uiSurfaceProjection~)

If you already run a ~ProjectionRuntime~, register the surface as a projection and bind widgets with the ordinary ~{ projectionId, path }~ binding — ~BlueprintRenderer~ needs no changes. The ~projectionId~ is the surface id (~"ui"~).

#+begin_src typescript
import { a2uiSurfaceProjection } from "@loom/a2ui";

projectionRuntime.register(a2uiSurfaceProjection("ui"));   // id === "ui"
#+end_src

#+begin_src typescript
import { blueprint$, stack, StatusBadge, StreamingText } from "@loom/blueprint-runtime";

export const AssistantBlueprint = blueprint$({
  id: "assistant-dashboard",
  title: "Assistant",
  layout: stack({
    gap: 12,
    children: [
      StatusBadge({ title: "Phase", binding: { projectionId: "ui", path: "phase" } }),
      // StreamingText is the convenience widget for a growing string in the surface
      StreamingText({
        title: "Answer",
        binding: { projectionId: "ui", path: "answer" },
        placeholder: "Thinking…",
      }),
    ],
  }),
  projections: ["ui"],
});
#+end_src

~StreamingTextRenderer~ is pre-registered in ~defaultRegistry~ under ~"StreamingText"~, so the widget renders with no extra wiring.

*** 3. Consume standalone (~A2UIRuntime~ + ~useA2UISurface~)

For apps without a ~ProjectionRuntime~, use the framework-agnostic ~A2UIRuntime~: point ~onEvent~ at ~handleEvent~ and read a surface with the ~useA2UISurface~ hook from ~@loom/renderer-react~.

#+begin_src typescript
import { A2UIRuntime } from "@loom/a2ui";
import { useA2UISurface } from "@loom/renderer-react";

const a2ui = new A2UIRuntime();
// new WorkflowRuntime({ ..., onEvent: (e) => a2ui.handleEvent(e) })

function LiveSurface({ executionId }: { executionId: string }) {
  const surface = useA2UISurface(a2ui, executionId, "ui");
  return <pre>{JSON.stringify(surface, null, 2)}</pre>;
}
#+end_src

*** Durability and where to see it

Because patches are just events on the log, an A2UI surface is fully durable and replay-deterministic: after a suspend/resume the surface rebuilds itself by folding the same ~A2UI_PATCH~ events. The ~apps/playground~ "A2UI" tab visualizes the live surface next to the raw patch stream, and ~examples/cloud-command-center~ streams its AI analysis into the ~"ui"~ surface via patches (driving a phase ~StatusBadge~ with ~ctx.ui.set~). See ~docs/api-reference.org~ (~@loom/a2ui~) for the full API.

** Capabilities and the catalog

A *capability* wraps a runnable flow with intent-facing metadata (~capability$~) so the same unit of work is exposed as an API, a UI action, an A2A endpoint, or a workflow node. Register capabilities in a ~CapabilityCatalog~ — the shared vocabulary the Intent and Planner runtimes route over.

#+begin_src typescript
import { capability$, CapabilityCatalog } from "@loom/capability";
import { z } from "zod";

const InvestigateCapability = capability$({
  id: "investigate-incident",
  name: "Investigate Incident",
  intent: "Diagnose a production incident from metrics and logs",
  tags: ["ops", "incident", "diagnosis"],
  inputSchema: z.object({ incidentId: z.string() }),
  flow: InvestigateIncidentRegisteredFlow,
});

const catalog = new CapabilityCatalog().register(InvestigateCapability);

// Wire every capability's flow into the workflow runtime in one call
catalog.registerInto(workflowRuntime);

// Deterministic keyword discovery — no model needed
catalog.find("diagnose incident");   // → [{ capability, score }, …]

// Or invoke directly by id
const handle = await catalog.invoke(workflowRuntime, "investigate-incident", { incidentId: "cpu-001" });
#+end_src

** Intent routing (Intent Over Routes)

~IntentRuntime~ maps a natural-language intent to a capability, replacing hand-written route tables. It works fully offline with keyword matching; supply an ~LlmProvider~ to let the model pick the capability id.

#+begin_src typescript
import { IntentRuntime } from "@loom/intent";

// Offline — deterministic keyword routing (no provider)
const intent = new IntentRuntime({ catalog, workflowRuntime });

const route = await intent.route("diagnose the cpu incident");
// route: { capability, confidence, rationale? } | null

// route + workflowRuntime.start() in one step
const handle = await intent.run("diagnose the cpu incident", { incidentId: "cpu-001" });

// Upgrade to LLM routing by adding a provider — everything else is unchanged
const smart = new IntentRuntime({ catalog, provider: new AnthropicProvider(), workflowRuntime });
#+end_src

When routing runs alongside live work, pass a shared ~scheduler~ so the routing LLM call runs at ~Priority.Idle~ and yields to foreground executions. Build one with ~createScheduler({ concurrency })~ from ~@loom/scheduler~ and share the *same* instance across Intent, Planner, and any other background callers — the concurrency cap is what makes the priority lanes take effect.

#+begin_src typescript
import { createScheduler } from "@loom/scheduler";

// One shared scheduler; the finite cap enables priority ordering.
const scheduler = createScheduler({ concurrency: 4 });

const smart = new IntentRuntime({
  catalog,
  provider: new AnthropicProvider(),
  workflowRuntime,
  scheduler,   // routing LLM call is queued at Priority.Idle
});
#+end_src

** Planning multi-step goals

Where the Intent Runtime picks one capability, ~PlannerRuntime~ composes an ordered ~Plan~ of capability ids for a higher-level goal. Every id is validated against the catalog and the plan is truncated to ~maxSteps~ (default 5).

#+begin_src typescript
import { PlannerRuntime } from "@loom/planner";

const planner = new PlannerRuntime({ catalog, provider: new AnthropicProvider(), maxSteps: 4 });
// Omit provider for a deterministic heuristic plan.

const plan = await planner.plan("Resolve the CPU incident and notify the on-call engineer");
// plan: { goal, steps: [{ capabilityId, rationale? }, …] }

for (const step of plan.steps) {
  await catalog.invoke(workflowRuntime, step.capabilityId, { incidentId: "cpu-001" });
}
#+end_src

Like the Intent Runtime, ~PlannerRuntime~ accepts a shared ~scheduler~ so the planning LLM call runs at ~Priority.Idle~ and yields to live executions. Reuse the same ~createScheduler({ concurrency })~ instance you pass to Intent so all background LLM work shares one concurrency budget:

#+begin_src typescript
import { createScheduler } from "@loom/scheduler";

const scheduler = createScheduler({ concurrency: 4 });   // share across Intent + Planner

const planner = new PlannerRuntime({
  catalog,
  provider: new AnthropicProvider(),
  maxSteps: 4,
  scheduler,   // planning LLM call is queued at Priority.Idle
});
#+end_src

** Agent memory

~MemoryRuntime~ gives an agent durable recall across turns, honoring the ~ttlMs~ / ~maxEntries~ declared by ~memory$()~. Pass it to ~AgentConfig~ and set the agent's ~memoryId~; ~AgentRunner.run~ then recalls prior entries into the prompt and writes each turn back. Use ~AgentInput.memoryScope~ to partition recall per conversation or user (defaults to ~ctx.executionId~).

#+begin_src typescript
import { memory$, agent$ } from "@loom/sdk";
import { MemoryRuntime } from "@loom/memory";
import { AgentRunner } from "@loom/agent";

const IncidentMemory = memory$({ id: "incident-memory", name: "Incident Memory", ttlMs: 3_600_000, maxEntries: 200 });

const memory = new MemoryRuntime();
memory.register(IncidentMemory);

const InvestigatorAgent = agent$({
  id: "investigator",
  name: "Investigator Agent",
  tools: [MetricsTool],
  memoryId: "incident-memory",   // links the agent to the memory store
});

const runner = new AgentRunner({
  definition: InvestigatorAgent,
  provider: new AnthropicProvider(),
  effectRuntime,
  memory,                         // enables recall + write-back
});

// memoryScope keeps each user's conversation separate
await runner.run({ prompt: "What was the CPU peak?", memoryScope: "user-42" }, ctx);
await runner.run({ prompt: "And now?",               memoryScope: "user-42" }, ctx);  // recalls the prior turn
#+end_src

You can also read and write memory directly — ~read~ prunes by ~ttlMs~ then trims to ~maxEntries~:

#+begin_src typescript
memory.append("incident-memory", "user-42", { role: "user", content: "note this" });
const history = memory.read("incident-memory", "user-42");   // MemoryEntry[]
#+end_src

** Rendering to other surfaces (terminal)

Blueprints carry no framework imports, and ~traverseBlueprint~ is framework-agnostic — so the same blueprint + projection state renders to React *or* to plain text. ~@loom/renderer-terminal~ is the non-React surface.

#+begin_src typescript
import { TerminalRenderer, renderBlueprintToString } from "@loom/renderer-terminal";

// Pull projection state for an execution from the ProjectionRuntime and render to text
const renderer = new TerminalRenderer(projectionRuntime);
console.log(renderer.render(IncidentBlueprint, executionId));

// Or render from an explicit projection state map (no ProjectionRuntime needed)
const stateMap = new Map<string, unknown>([["metrics", { cpu: { current: 87 } }]]);
console.log(renderBlueprintToString(IncidentBlueprint, stateMap));
#+end_src

The ~examples/agent-network~ showcase demonstrates all five of the above — capability catalog, intent routing, a planner plan, agent memory recall, and a terminal-rendered dashboard — end to end and fully offline. Run it with ~pnpm --filter @loom/agent-network start~.

The terminal renderer uses the synchronous, pull-based ~traverseBlueprint~. If you are writing a scheduler-less renderer that mutates a target as the tree resolves (direct DOM, canvas, native), ~traverseBlueprintAsync~ (in ~@loom/blueprint-runtime~) is the push-based, interruptible counterpart: it commits nodes incrementally and cooperatively yields against a budget so the host stays responsive on large trees. You supply an ~IncrementalRenderer~ with ~createContainer~ / ~createWidget~ / ~appendChild~. React renderers do *not* need this — the fiber path already leverages React's scheduler.

* Common Pitfalls

** "Effect not registered" at runtime

If a step has neither ~handler$()~ nor a manual ~effectRuntime.register()~ call, ~ctx.run()~ will throw. Solution: add ~handler$()~ to the step definition, or call ~effectRuntime.register(toolId, effect)~ before ~start()~.

** Side effects executing twice

If you call an external API directly in the runner (not through ~ctx.run()~), it re-executes on every resume. Always wrap external calls in ~ctx.run(step, ...)~.

** Missing projection updates

Check that ~onEvent~ is wired: ~new WorkflowRuntime({ ..., onEvent: (e) => projectionRuntime.handleEvent(e) })~. Without this, projections never receive events.

** TypeScript exactOptionalPropertyTypes errors on ~step$~

When using ~handler$()~, pass undefined-free values. Use the conditional spread pattern:

#+begin_src typescript
const step = step$({
  id: "my-step",
  handler: handler$(myFn),
  ...(toolId !== undefined && { toolId }),
  inputSchema, outputSchema,
});
#+end_src
